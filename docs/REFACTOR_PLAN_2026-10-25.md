## Порядок (от безопасного к опасному)

1. **purge_all_data -> реестр шагов. ТРЕБУЕТ ТОП-МОДЕЛЬ (Opus) + adversarial-ревью:** внутри 72 try-блока, порядок под `store._lock()`, шифр-ключ shred, symlink-гонки (A5.2c1/M1/LOW1). Нейтральный перенос здесь легко ломает порядок и приватность. Список `(имя, функция)`, каждый шаг в своём
   try/except, результат агрегируется. Гард: `audit_purge_coverage` + существующие
   purge-тесты + новый тест «каждый шаг вызван ровно один раз, сбой шага не останавливает остальные».
2. **BackendService.__init__ -> фазы** (`_init_stores`, `_init_stt`, `_init_services`,
   `_init_background`). Порядок сохранить; тест порядка по AST.
3. **AudioEngine.transcribe -> конвейер** подфункций (подготовка, STT с fallback,
   постобработка). Только после характеризационных тестов на реальные формы результата.
4. **Горячий путь записи** (start/stop) — в последнюю очередь, только с живым E2E
   (потеря диктовок = шесть слоёв, см. память проекта).
5. **Один STT-процесс вместо backend+REST** — архитектурное, отдельная спека
   с adversarial-ревью дизайна до кода. Сначала метрики PR #2121 и канарейка.

## Правила

- Один PR = одно движение кода; без смены поведения. Диф «перенос + вызов».
- Перед каждым шагом: характеризационный тест (фиксирует нынешнее поведение), RED не нужен, GREEN до и после.
- Гейт: pytest затронутых файлов, flake8, `make audit-all`, `make pre-merge-check`.
- Не повторять W797: вынесенный код обязан иметь прод-вызывающего (`audit_dead_extracted_modules`).
- Живой E2E (`scripts/run_e2e_smokes.command`) для шагов 2-4.
