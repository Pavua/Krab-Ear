# Бриф для Voice Gateway: brain_mode для conversation-флоу

Контекст: голосовой ассистент Krab Ear «Разговор с AI» (WS `/v1/sessions/{id}/conversation`)
использует `BrainProxy`/`build_brain_clients()` (`app/brain_chain.py`) как «мозг», отвечающий
на реплики пользователя. Сейчас порядок провайдеров — `local → gemini → openclaw` (Main Krab —
последний фоллбэк, `va_brain_order`). Нужен переключаемый режим, чтобы Krab Ear-клиент мог
выбирать между «быстро» (как есть) и «Main Krab первым».

## Требования

1. Новая настройка `brain_mode`, 3 значения:
   - **`fast`** — текущий порядок `build_brain_clients(settings)`, поведение не меняется.
   - **`krab`** — цепочка с `openclaw`-клиентом первым (если сконфигурирован/доступен),
     остальные — фоллбэк ТОЛЬКО при жёстком failure (не при простой медленности). Потолок
     ожидания — настраиваемый `va_conversation_brain_timeout_krab_sec`, дефолт **30с**. При
     таймауте НЕ переключаться на другого провайдера — вернуть честный локализованный
     фоллбэк (паттерн `BrainProxy._fallback`), т.к. пользователь явно выбрал именно Krab.
   - **`auto`** — та же переупорядоченная цепочка, но короче таймаут на ход —
     `va_conversation_brain_timeout_auto_sec`, дефолт **12с**. При превышении — тихий graceful
     fallback на остаток fast-цепочки ТОЛЬКО для этого хода разговора; следующая реплика снова
     пробует Krab первым.
2. `GET/PUT /v1/settings/conversation` → `{brain_mode}` — простой in-memory рантайм-оверрайд
   поверх .env-дефолта (не изобретайте новый слой персистентности, если у вас уже есть паттерн
   получше — решайте сами).
3. WS-эндпоинт `/v1/sessions/{id}/conversation` дополнительно принимает опциональный query-param
   `?brain_mode=fast|krab|auto` — если передан, побеждает над серверной настройкой для ЭТОЙ
   сессии (Krab Ear/Swift будет всегда явно слать свой текущий выбор тумблера этим способом).
4. **Нужна проверка, не считайте решённым**: реально ли `openclaw`-провайдер в `.chat()`
   уважает кастомный system-prompt в `messages`, или agent-фреймворк Main Krab его
   игнорирует/переопределяет (в коммите `ac330a2`, понизившем приоритет openclaw, явно
   написано «игнорит system-prompt»)? Если игнорирует — нужен способ сделать ответы Krab
   голосово-уместными (кратко, естественная речь, без markdown/списков/эмодзи) для этого
   конкретного пути вызова. Возможно, потребуется правка и на стороне Main Krab/OpenClaw —
   для этого параллельно уходит отдельный бриф в ту сессию.
5. Цифры таймаутов (30с/12с) — стартовые дефолты, НЕ финальные — сделайте их настраиваемыми
   (env var или новый settings API), чтобы можно было откалибровать эмпирически по реальной
   латентности Main Krab в живом смоке.
6. Не должно затрагивать другие точки использования `build_brain_clients()`/`BrainProxy` в VG
   (например PSTN-флоу звонков) — скоуп строго `app/routers/conversation.py`.

## Тестирование
Контрактные unit-тесты (парсинг query-param, timeout/fallback-логика с мок-клиентами) —
достаточно на вашей стороне. Реальная латентность Main Krab проверяется живым смоком
координированно с Krab Ear-сессией (владелец организует).

## Контекст со стороны Krab Ear
Спека дизайна: `docs/superpowers/specs/2026-07-08-conversation-brain-mode-design.md` (этот
репозиторий). Swift-сторона строит сегмент-тоггл (Fast/Krab/Auto) в Conversation-табе,
шлёт `brain_mode` query-параметром на каждый WS-коннект + отдельное действие «Сделать
дефолтом», дёргающее ваш `PUT /v1/settings/conversation`.
