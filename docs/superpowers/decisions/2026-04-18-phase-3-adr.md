## Detailed rationale

### Q1 — Phone number input: Paste + manual entry

**Decision:** Support both clipboard paste and manual text input in the `CallAssistantViewController` dialer.

**Rationale:**
Paste-only creates friction when a number is not in the clipboard (e.g., read from a paper note or a second screen). Manual entry costs <1 day extra in `+Dialer.swift` and is expected by any phone-dialer UX. The "Paste from clipboard" button remains the primary action per the spec mockup; the text field simply stays editable.

**Address book integration** (Contacts framework + `CNContactPickerViewController`) deferred to Phase 3.1 — requires additional macOS privacy entitlement (`NSContactsUsageDescription`) and adds ≥5 days scope.

---

### Q2 — Human interruption: Immediate stop

**Decision:** When VAD detects incoming speech energy from the human while AI TTS is streaming, the Voice Gateway must cut off outbound audio immediately (flush the TTS output queue).

**Rationale:**
Human callers expect to be heard when they speak. Finishing the current AI word (≈100–300 ms overhead) is perceptible and feels robotic. Immediate truncation is the behaviour of every competitive voicebot (Google Duplex, Bland AI) and of natural phone conversation. The downside — clipping a partial AI utterance — is well within the acceptable UX envelope.

**Configurable barge-in threshold** (energy level, or finish-word mode) is a settings knob deferred to Phase 3.1 to keep the MVP state machine simple.

---

### Q3 — Transcript storage: Mixed history with `type="call_automation"`

**Decision:** Call automation transcripts are appended to the standard Krab Ear history NDJSON with `"type": "call_automation"` (matching the pattern already used by `"mode": "call_automation"` in the spec). No separate file.

**Rationale:**
A separate file doubles the storage code path (second `StateStore` instance, second compaction job, second UI list). Unified history keeps `HistoryService`, clipboard history, SRT export, fuzzy search, and the `HistoryPanel` working without modification. `type` filter is sufficient to scope the call-automation UI view.

**Implementation note:** The existing `StateStore` schema is schemaless NDJSON — adding `type="call_automation"` is a zero-migration, backwards-compatible change. The call-specific fields (`call_id`, `target_phone`, `outcome`, `cost_usd`) are additive payload fields.

---

### Q4 — Multi-step goals: Single-goal only MVP

**Decision:** Phase 3 supports exactly one goal per call session (e.g., "ask for Wednesday slot"). Chained or conditional intents ("if no Wed, ask Thu") are explicitly out of scope.

**Rationale:**
Chained goals require a conversation state machine inside the Krab agent LLM loop that tracks which sub-goal was satisfied and which remains. This introduces non-trivial prompt engineering, LLM hallucination risk (skipping ahead), and testing complexity (combinatorial state coverage). The single-goal constraint makes `call_check_goal_achieved()` a simple binary predicate and keeps the system prompt compact.

**Phase 3.5** defers chained goals: each sub-goal becomes a separate `call_step` in a `CallChain` object with its own system prompt + completion check.

---

### Q5 — Auto-end call duration: User-lowerable default (30 min)

**Decision:** Voice Gateway enforces a **configurable** maximum call duration. The default is 30 minutes. Users may lower it (minimum allowed: 5 minutes). Users may raise it (with an explicit "I understand costs" confirmation dialog in Settings).

**Rationale:**
A hard 30-min ceiling eliminates runaway cost in failure scenarios (stuck conversation loop, voicemail that never ends). Making it user-lowerable respects that most use cases ("ask clinic for Wed slot") need <5 min; a conservative user can set 10 min for extra safety. Making it user-raiseable (with a warning) avoids blocking edge cases like long appointment scheduling or customer support queues.

**Cost display:** the Settings panel shows the worst-case cost for the current max-duration setting to make the financial consequence visible.

**Implementation:** `KRAB_EAR_CALL_MAX_DURATION_SEC` env var + `settings.json` override. VG enforces via `asyncio.wait_for(call_loop, timeout=max_duration_sec)`.

---

### Q6 — Cost display: Pre-call mandatory + opt-in live ticker

**Decision:**
- **Pre-call cost estimate** (mandatory, cannot be dismissed without confirming or cancelling): shown before `start_call` IPC is sent.
- **Live cost ticker** during call: opt-in, off by default. Toggled in Settings (`show_call_cost_ticker: bool`).

**Rationale:**
Pre-call estimate is a compliance-adjacent feature (surprises lead to disputes) and is already part of the spec's confirmation dialog. The live ticker is a nice-to-have that adds UI refresh complexity (polling `GET /v1/calls/{id}/status` every 5 s for `cost_so_far_usd`). Keeping it opt-in avoids distracting from the transcript view during an active conversation. Power users who want budget awareness can enable it.

**Swift note:** ticker implementation is `+Cost.swift` extension; UI state is driven by a `@Published var showCostTicker` flag in the view model.

---

### Q7 — Silence >10 s: One probe, then auto-end

**Decision:** After 10 seconds of silence, Voice Gateway sends a single probe utterance ("Здравствуйте? Вы ещё здесь?") via TTS. If no response within a further 8 seconds, the call is terminated with `{status: "silent_hangup"}`.

**Rationale:**
Auto-end without probe is too aggressive — it would mishandle a caller who paused to look something up (common in "ask for a slot" scenarios). Indefinite wait is unsafe (cost + resource leak). A single probe + 8 s wait closely mirrors what a human receptionist would do. Two-probe logic deferred to Phase 3.1 as a configurable `silence_probe_count` setting.

**Voicemail interaction:** the voicemail detector (silence >3 s from answer) fires before the 10 s silence handler can; they are on separate timers and do not conflict.
