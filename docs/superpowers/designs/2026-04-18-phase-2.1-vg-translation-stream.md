## Endpoint Signature

### WebSocket

```
WS /v1/translation/stream?source_lang={lang}&target_lang={lang}&session_id={uuid}
```

Authentication: same Bearer token as existing VG endpoints (`_auth_required` dependency).

**Query params:**

| Param | Required | Values | Default |
|-------|----------|--------|---------|
| `source_lang` | No | `ru`, `en`, `es`, `auto` | `auto` |
| `target_lang` | Yes | `ru`, `en`, `es` | — |
| `session_id` | No | UUID v4 | auto-generated by VG |

### REST companions (for lifecycle control and enumeration)

```
POST   /v1/translation/sessions           — explicit start, returns {session_id}
DELETE /v1/translation/sessions/{id}      — explicit end (graceful flush)
GET    /v1/translation/language-pairs     — list supported pairs + engine info
GET    /v1/translation/audio-sources      — list enumerated audio sources
```

## Wire Protocol

### Client → Server (uplink)

**Binary frames:** raw PCM 16 kHz, mono, signed 16-bit LE (s16le), 200 ms chunks (6 400 bytes per frame). No Opus encoding in v1 (local loop, bandwidth not a constraint; avoids Opus dependency on client side).

**Text JSON frames (control):**

```jsonc
// Config — MUST be sent before first audio frame
{"type": "stream.config", "source_lang": "ru", "target_lang": "en", "audio_source": "microphone"}

// Pause audio processing (keep WS alive, flush pending output)
{"type": "pause"}

// Resume after pause
{"type": "resume"}

// Graceful close: flush remaining buffer, emit final events, close WS
{"type": "end"}
```

### Server → Client (downlink)

All downlink frames are **text JSON** following EVENT_CONTRACT_V1 envelope:
`{type: str, ts: float (UNIX epoch), data: {...}}`

```jsonc
// Partial transcript in SOURCE language — updates in-place (same seq_id = replace)
{"type": "translation.partial",      "ts": 1745001234.1, "data": {"seq_id": "abc123", "lang": "ru", "text": "Привет", "confidence": 0.91, "latency_ms": 210}}

// Final transcript in SOURCE language — committed, append to history
{"type": "translation.transcript",   "ts": 1745001234.8, "data": {"seq_id": "abc123", "lang": "ru", "text": "Привет мир", "confidence": 0.96, "offset_ms": 0, "duration_ms": 820}}

// Partial translated text in TARGET language
{"type": "translation.partial",      "ts": 1745001234.9, "data": {"seq_id": "abc123", "lang": "en", "text": "Hello w", "confidence": 0.88, "latency_ms": 290}}

// Final translated text in TARGET language
{"type": "translation.final",        "ts": 1745001235.1, "data": {"seq_id": "abc123", "lang": "en", "text": "Hello world", "confidence": 0.94, "latency_ms": 920}}

// Engine loaded/ready (sent once after first connect or after engine swap)
{"type": "translation.engine_ready", "ts": 1745001220.0, "data": {"engine": "seamless_streaming_2.5b", "source_lang": "ru", "target_lang": "en", "warmup_ms": 14200}}

// Auto-detected source language (emitted after first 1.5s of audio)
{"type": "translation.lang_detected","ts": 1745001222.5, "data": {"source_lang": "ru", "confidence": 0.97}}

// Session saved to Krab Ear history (emitted on end)
{"type": "translation.session_saved","ts": 1745001300.0, "data": {"history_id": "uuid-...", "duration_sec": 65.3, "word_count_original": 142, "word_count_translated": 138}}

// Error (non-fatal: processing resumes; fatal: WS closes after)
{"type": "translation.error",        "ts": 1745001234.0, "data": {"code": "inference_timeout|audio_source_unavailable|engine_load_failed|unsupported_lang_pair", "message": "...", "fatal": false}}
```

**Note on `seq_id`:** VG assigns a UUID per utterance (VAD speech segment). Partials and final for the same utterance share the same `seq_id`. Client replaces partial text on matching `seq_id`, appends on new `seq_id`.

## Engine Choice

### Primary: SeamlessStreaming 2.5B (Meta) — S2TT mode

**Why SeamlessStreaming over SeamlessM4T Large:**

| Criterion | SeamlessStreaming 2.5B | SeamlessM4T v2 Large |
|-----------|----------------------|---------------------|
| Mode | Streaming (EMMA decoder, incremental) | Batch-only |
| RAM | ~8 GB peak (PyTorch fp16 + MPS) | ~10 GB peak |
| Partial latency | ~200-400 ms (first token) | N/A |
| Final latency | ~800-1200 ms / sentence | ~1.5-3 s / sentence |
| RU/ES/EN quality | High (100+ languages trained) | High (same family) |
| License | CC-BY-NC 4.0 (personal OK) | CC-BY-NC 4.0 |
| MLX port | None — PyTorch+MPS only | None — PyTorch+MPS only |

**Why NOT Moshi for this endpoint:**
Moshi is EN-only, conversation-focused (duplex), 5-min buffer cap, and adds dependency complexity. Phase 2 is RU-primary S2TT — SeamlessStreaming is the correct engine.

**Why NOT mlx-whisper + local Translator chained:**
mlx-whisper is already used in Krab Ear's Python backend for standard dictation. For Phase 2, SeamlessStreaming's integrated S2TT pipeline provides lower latency (single-model inference) than a chain of Whisper → separate MT model, and better code-switching support.

**Latency targets (SeamlessStreaming, M4 Max, MPS):**

| Metric | Target | Research basis |
|--------|--------|----------------|
| First partial | ≤ 400 ms | EMMA streaming decoder first token |
| Final (per sentence) p50 | ≤ 1.2 s | SeamlessStreaming paper + MPS timing |
| Final (per sentence) p95 | ≤ 2.5 s | With longer/complex sentences |
| Engine warmup (first session) | ≤ 20 s | Model load from HF cache to MPS |
| Engine warmup (already loaded) | ≤ 500 ms | Reuse from Phase 1 `LazyConversationEngine` |

**Fallback chain:**
1. SeamlessStreaming 2.5B (primary, streaming)
2. SeamlessM4T v2 Large (batch fallback — slower but always available if 2.5B fails to load)
3. Krab Ear local pipeline: mlx-whisper STT + offline translator (if VG unavailable)

## Hardware Budget (M4 Max 36 GB)

| Scenario | VG Engine | VG Overhead | Krab Ear UI | OS + browser | Total | Safe? |
|----------|-----------|-------------|-------------|-------------|-------|-------|
| Idle (no translation) | 0 | 100 MB | 200 MB | 5 GB | ~5.5 GB | Yes |
| Active translation only | ~8 GB (SeamlessStream 2.5B, fp16, MPS) | 200 MB | 350 MB | 5 GB | ~14 GB | Yes |
| Translation + Phase 1 engine loaded | ~8 GB + 10 GB = 18 GB (two engines) | 300 MB | 400 MB | 5 GB | ~24 GB | Yes (12 GB margin) |
| Translation + Phase 1 active simultaneously | ~8 GB active | 300 MB | 400 MB | 5 GB | ~14 GB | Yes — only one active |

**Concurrent session limit:** 1 (single-user device). VG enforces `_active_translation_session` singleton — starting a new translation session reuses same engine instance.

**Engine sharing with Phase 1:** Phase 1 uses SeamlessM4T v2 Large (conversation mode); Phase 2 uses SeamlessStreaming 2.5B (s2tt mode). These are **distinct model checkpoints** but share the same `LazyConversationEngine` load/unload lifecycle. VG's existing LRU eviction policy applies: if Phase 1 conversation session ends, engine `unload()` fires after 5 min idle — freeing ~10 GB before Phase 2 loads ~8 GB.

If user starts Phase 2 while Phase 1 engine still loaded: VG evicts Phase 1 engine immediately (5s pause), then loads Phase 2 engine (~15s warmup). User sees `translation.engine_ready` event when ready.

## Integration Points

### Krab Ear Side

**New Swift file: `TranslationStreamClient.swift`**
Location: `native/KrabEarAgent/Sources/KrabEarAgent/TranslationStreamClient.swift`

Responsibilities:
- Manages `URLSessionWebSocketTask` to `ws://127.0.0.1:8090/v1/translation/stream`
- Sends control JSON frames (`stream.config`, `pause`, `resume`, `end`)
- Sends PCM binary frames captured from AVAudioEngine tap
- Decodes incoming JSON events, dispatches via delegate protocol

```swift
protocol TranslationStreamDelegate: AnyObject {
    func onPartial(seqId: String, lang: String, text: String, confidence: Float)
    func onFinal(seqId: String, lang: String, text: String, confidence: Float, latencyMs: Int)
    func onEngineReady(engine: String, warmupMs: Int)
    func onLangDetected(sourceLang: String, confidence: Float)
    func onSessionSaved(historyId: String, durationSec: Double)
    func onError(code: String, message: String, fatal: Bool)
}
```

**Phase 2.2 (deferred):** `TranslationViewController.swift` — new "Live Перевод" tab with dual-pane UI, ScreenCaptureKit audio source picker, glossary tooltips. Depends on this PR's WS contract.

### Krab Ear Python Backend Side

No changes required for Phase 2.1. The translation session is saved to Krab Ear history NDJSON when the VG session ends (VG fires `translation.session_saved` event; Swift client calls IPC `add_history_item` with `mode: "live_translation"`).

**IPC method used (existing):** `add_history_item` — accepts `{text, mode, duration_sec, extra: {original_lang, target_lang, original_text, translated_text}}`.

### OpenClaw Side

Phase 2 translation does NOT route through OpenClaw/Krab agent LLM. SeamlessStreaming is deterministic S2TT — no reasoning required. The OpenClaw channel remains unused for translation. Optional future: "Сохранить в память" button sends summary to Krab agent (out of Phase 2.1 scope).

## Event Contracts (EVENT_CONTRACT_V1)

### New EventType registrations in `KrabEar/contracts/registry.py`

```python
class EventType(str, Enum):
    # ... existing ...
    TRANSLATION_PARTIAL   = "translation.partial"    # streaming partial (source or target)
    TRANSLATION_TRANSCRIPT = "translation.transcript" # committed source-lang utterance
    TRANSLATION_FINAL     = "translation.final"      # committed target-lang translation
    TRANSLATION_ERROR     = "translation.error"      # non-fatal or fatal error
    TRANSLATION_ENGINE_READY = "translation.engine_ready"
    TRANSLATION_LANG_DETECTED = "translation.lang_detected"
    TRANSLATION_SESSION_SAVED = "translation.session_saved"
```

**Note:** Existing `TRANSLATION_COMPLETED` and `TRANSLATION_FAILED` in registry.py are for the batch translation pipeline (in-process IPC events). The new `translation.*` streaming events are WS-only and have different semantics. They are added to the registry for JSON Schema export and contract documentation, but are NOT dispatched through the in-process `EventBus` (different transport).

### Pydantic models (new file: `KrabEar/contracts/translation_stream_events.py`)

```python
class TranslationPartialData(BaseModel):
    seq_id: str
    lang: str                      # ISO-639-1: "ru", "en", "es"
    text: str
    confidence: float = 0.0
    latency_ms: int = 0

class TranslationFinalData(BaseModel):
    seq_id: str
    lang: str
    text: str
    confidence: float = 0.0
    latency_ms: int = 0

class TranslationTranscriptData(BaseModel):
    """Final committed source-language utterance (ASR output)."""
    seq_id: str
    lang: str
    text: str
    confidence: float = 0.0
    offset_ms: int = 0
    duration_ms: int = 0

class TranslationEngineReadyData(BaseModel):
    engine: str                    # "seamless_streaming_2.5b"
    source_lang: str
    target_lang: str
    warmup_ms: int

class TranslationLangDetectedData(BaseModel):
    source_lang: str
    confidence: float

class TranslationSessionSavedData(BaseModel):
    history_id: str
    duration_sec: float
    word_count_original: int
    word_count_translated: int

class TranslationErrorData(BaseModel):
    code: str                      # "inference_timeout" | "audio_source_unavailable" | ...
    message: str
    fatal: bool = False
```

**JSON Schema export:** `python -m contracts.export` auto-generates schemas to `contracts/schemas/translation.stream.*.schema.json` (PR 2.3).

### BLOCKER 3: PyTorch MPS regression on macOS 26 (Darwin 25.x)

**Context:** CLAUDE.md risk list notes open issue pytorch#167679 (MPS regression on macOS 26). The current environment reports `Darwin 25.5.0` — this IS macOS 26 (Tahoe/sequoia numbering).

**Question:** Has SeamlessStreaming been verified to run on PyTorch MPS with Darwin 25.x kernel? If MPS is broken for torch, the entire engine runs on CPU (~4-8x slower, ~20-40s/sentence latency — unusable for real-time).

**Check:** `python3 -c "import torch; print(torch.backends.mps.is_available())"` in VG venv.

**Mitigation:** CPU fallback path must be explicitly implemented in `seamless_stream_engine.py`. If MPS unavailable, emit `translation.engine_ready` with `device: "cpu"` warning; latency targets degrade to p50 ≤ 5s (batch-only mode, not streaming).

### UNKNOWN 1: `translation.partial` event disambiguation

The existing `EventType.TRANSLATION_COMPLETED` in `contracts/registry.py` covers the **batch** in-process translation. The new streaming events reuse some similar names (`translation.partial`, `translation.final`). Need to confirm there is no collision in Krab Ear's `EventBus` subscribers — streaming events are WS-transport only and should NOT be dispatched to the in-process bus.

**Decision needed:** Should streaming event types be namespaced differently (e.g., `stream.translation.*` vs `translation.*`)? Current design uses `translation.*` (consistent with spec), but requires confirming isolation.

### UNKNOWN 2: PCM vs Opus for uplink

Spec says Opus; this design proposes raw PCM s16le for v1 (simpler, no client-side Opus encoder needed, local loop has bandwidth). Need user decision before implementing.

**Trade-off:**
- Raw PCM: simpler client, +~64 kbps bandwidth (negligible on localhost), avoids Opus Swift dependency
- Opus: consistent with Phase 1 conversation endpoint (80ms frames), enables future remote/iOS use

Recommendation: raw PCM for v1, Opus for v1.1 when remote/iOS support added.

### UNKNOWN 3: ScreenCaptureKit audio source

The spec calls for system audio capture (Zoom/Teams) via ScreenCaptureKit. This requires macOS 14.1+ (Sonoma) and explicit user permission. The current worktree target is macOS 13+ (Phase 1 constraint).

**Decision needed:** Is Phase 2.1 gated behind macOS 14.1+, or does the microphone-only path satisfy Phase 2.1 acceptance? Recommend gating ScreenCaptureKit to Phase 2.4 (UI PR), keeping Phase 2.1-2.3 microphone-only for initial validation.

### UNKNOWN 4: Session ID coordination

Phase 1 sessions are created via `POST /v1/sessions` (returns `{id}`). Phase 2 translation stream introduces a parallel session namespace. Need to decide: are translation sessions tracked in the same `SessionStore` (VG's `data/gateway.db`), or a separate in-memory registry?

**Recommendation:** Separate `TranslationSessionRegistry` (in-memory, no DB persistence for v1). Rationale: translation sessions don't require call metadata (Twilio call_sid, etc.) and the existing `SessionStore` is coupled to telephony schema.
