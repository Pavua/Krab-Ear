**Отчёт.** Статус `DONE` / `DONE_WITH_CONCERNS` / `BLOCKED` / `NEEDS_CONTEXT`,

### Задача 1 — выравнивание каталога данных и точка входа

**Спека:** Р3 + Р9 + находки I2, I-D, M1, M3.

**Почему.** Каталог попадает в процесс двумя разнотипными каналами: аргумент
`--data-dir` доходит только до `StateStore` через локальную переменную `main()`,
а всё, что читает `settings.DATA_DIR`, смотрит на переменную окружения. Сегодня
оба случайно указывают в один каталог, потому что переменная есть в rest-плисте.
После включения режима REST переезжает под backend-плист и теряет её.

**Что сделать.**

1. `KrabEar/launchagents/ai.krab.ear.backend.plist.template` — в
   `EnvironmentVariables`, рядом с `PYTHONPATH`:

```xml
    <!-- S3/Р3: settings.DATA_DIR обязан совпадать с аргументом
         <hyphen><hyphen>data-dir выше. Backend передаёт каталог АРГУМЕНТОМ (он
         доходит только до StateStore), а всё, что читает settings.DATA_DIR —
         rest_server, cloud_stt, cloud_rewriter, startup_diagnostics — смотрит
         сюда. Пока REST жил отдельным юнитом, переменная была в его плисте
         (с 16-07); при слиянии процессов она обязана быть здесь, иначе
         половина процесса читает ~/.krab_ear_data, а история пишется в
         канонический каталог. Значение сверяется побайтово тестом
         test_backend_plist_data_dir_parity_S3.py. -->
    <key>KRAB_EAR_DATA_DIR</key>
    <string>__HOME__/Library/Application Support/KrabEar</string>
```

🔴 **Двойной дефис внутри XML-комментария запрещён стандартом** — `plistlib`
падает с `ExpatError: not well-formed`, а установщик умирает на `plutil -lint`.
Поэтому имя аргумента написано как `<hyphen><hyphen>data-dir`. Это не
причуда: тот же приём уже применён в `ai.krab.ear.rest.plist.template:45`.
Правило действует для любого комментария, который ты добавишь в plist.

2. В том же файле, в `ProgramArguments`, заменить

```xml
    <string>__PROJECT_ROOT__/KrabEar/backend/service.py</string>
```

на

```xml
    <string>__PROJECT_ROOT__/KrabEar/main.py</string>
```

   Причина в комментарии над массивом:

```xml

       делает service.py модулем __main__, а rest_server.py:37 импортирует
       backend.service — и при включённом in-process REST файл исполняется
       ВТОРЫМ экземпляром модуля: в процессе живут два разных класса
       BackendService. Сегодня безвредно, но любой module-level синглтон,
       добавленный в service.py, тихо раздвоится. -->
```

3. 🔴 **Ревизия потребителей старого паттерна.** Путь

### Задача 2 — устранение лок-мины в облачных модулях

**Спека:** Р3, находка I-C. 🔴 Самая тонкая задача чанка.

**Почему.** `cloud_stt.py:25` и `cloud_rewriter.py:141` строят собственные
`StateStore(settings.DATA_DIR)`. Сегодня они смотрят в несуществующий
`~/.krab_ear_data` и потому безвредны. Задача 1 сводит их на **те же файлы**, что
основной store процесса.

Фикс дедлока #1872 — per-thread depth-counter — живёт в **поле экземпляра**
(`state_store.py:111`: `self._lock_depth: dict[int, int]`). Между экземплярами он
не работает: тред, держащий лок экземпляра А и вошедший в лок экземпляра Б, не
увидит `depth > 0`, возьмёт `fcntl.flock` на новом файловом дескрипторе и
самозаклинится навсегда — вместе со всем `StateStore` (34 call-site).

Прямого пути сегодня нет, но мину взводит задача 1.

**Что сделать.**

Оба модуля используют store **только** для `load_settings()` — проверено:
`cloud_stt.py:128, 215, 275` и `cloud_rewriter.py:171, 227, 290, 367, 399`. Значит
им не нужен `StateStore` вообще.

1. В обоих модулях заменить module-level `store = StateStore(settings.DATA_DIR)`
   на инъецируемый аксессор настроек — паттерн, уже принятый в проекте
   (`privacy_mode_fn`, `settings_fn` у `TranscriptVersionManager`,
   `CollectionManager` и других):

```python
# S3/I-C: свой StateStore здесь был миной. После выравнивания DATA_DIR (задача 1)
# он смотрел бы на ТЕ ЖЕ файлы, что основной store процесса, а per-thread
# depth-counter реентерабельности (#1872) живёт в поле ЭКЗЕМПЛЯРА — между двумя
# экземплярами он не защищает: вход в лок второго из-под лока первого берёт
# flock на новом fd и заклинивает навсегда. Читаем настройки через аксессор
# владельца процесса; фоллбэк на собственный ленивый store оставлен для
# standalone-режима и тестов, где владельца нет.
_settings_fn: Callable[[], dict] | None = None


def adopt_settings_reader(settings_fn: Callable[[], dict]) -> None:
    """Подменяет источник настроек ссылкой на аксессор владельца процесса."""
    global _settings_fn
    _settings_fn = settings_fn


def _load_settings() -> dict:
    if _settings_fn is not None:
        return _settings_fn()
    return _fallback_store().load_settings()
```

   `_fallback_store()` — ленивый синглтон, создающий `StateStore(settings.DATA_DIR)`
   при первом обращении. Ленивость важна: она убирает и транзитный дубль на
   импорте. 🔴 Создание — под `threading.Lock` с double-checked проверкой:
   наивный check-then-set даст два экземпляра на одних файлах под конкурентным
   доступом, то есть ту же мину в standalone-режиме.

2. Все восемь мест `store.load_settings()` заменить на `_load_settings()`.

3. 🔴 **Точка подключения в `service.py` — БЕЗУСЛОВНАЯ и ВНЕ блока
   in-process REST.** Вызвать `adopt_settings_reader(self._cached_settings)` для
   обоих модулей в `__init__` сразу после создания `self._settings_svc`
   (строка 373).

   Соблазнительно положить вызов рядом с `adopt_external_singletons`
   (строка 815) — не делать этого: тот блок находится **внутри**
   `if REST_IN_PROCESS_ENABLED:` (строка 810). При выключенном рубильнике вызов
   бы не отработал, а `cloud_rewriter` зовётся из `engine.py` и живёт в
   backend-процессе **уже сегодня** — цель задачи не была бы достигнута.

4. **Обновить существующие тесты** — они патчат удаляемый module-level `store`:
   - `KrabEar/tests/test_cloud_stt.py` — 14 упоминаний, в основном
     `@patch("backend.cloud_stt.store.load_settings")`;
   - `KrabEar/tests/test_cloud_rewriter.py` — 52 упоминания, в основном
     `patch.object(cr, "store")`.

   Перенаправить их на `adopt_settings_reader` либо на мок `_settings_fn`. Без
   этого задача сдаётся зелёной, а CI краснеет на чужих для воркера файлах.

5. **Тест-документация** `KrabEar/tests/test_state_store_cross_instance_lock_S3.py`:
   два экземпляра `StateStore` на один временный каталог; тред берёт лок первого
   и пытается войти в лок второго; `join(timeout=...)` + `is_alive()` утверждают,
   что вход не состоялся.

   🔴 Тред обязан быть `daemon=True` и намеренно бросается застрявшим в `flock`.
   Не-daemon тред `threading._shutdown()` будет джойнить вечно на выходе
   интерпретатора — CI повиснет и упадёт по таймауту, унеся весь чанк. Написать
   это причиной в комментарии рядом.

   🔴 В докстринге теста указать: он **документирует известный класс**, а не
   проверяет фикс — красным он не станет ни до, ни после, потому что
   `state_store.py` мы не трогаем. Если когда-нибудь реентерабельность станет
   keyed-by-path, тест надо удалить, а не чинить.

6. **RED-тест задачи** — этот: после `adopt_settings_reader` ни один вызов не
   создаёт `StateStore`. Замокать конструктор, утвердить ноль вызовов. Он
   краснеет на текущем коде (module-level `store` создаётся на импорте) и
   зеленеет после правки.

**Чего НЕ делать.** Не менять `state_store.py`. Не делать `_lock_depth` полем
класса — выглядит соблазнительно, но сломает изоляцию экземпляров в тестах и не
решает случай двух процессов.

**Определение готовности:** RED-тест из пункта 6 прошёл цикл красный → зелёный;
оба существующих тест-файла зелёные; `cloud_rewriter` и `cloud_stt` читают
настройки владельца процесса.

**🔴 Конфликт с задачей 4.** Обе задачи правят регион `service.py:809-831`.
Мержить последовательно: сначала задачу 4, затем ребейз задачи 2 поверх неё.
Координатор сводит ветки сам, воркеры об этом не заботятся.

### Задача 3 — `temp_uploads` в privacy-purge

**Спека:** Р11 + находка M-B.

**Почему.** `TEMP_DIR = settings.DATA_DIR / "temp_uploads"` (`rest_server.py:783`)
не упоминается нигде в коде очистки — единственное вхождение во всём backend.

### Задача 4 — честная диагностика при сбое сборки

**Спека:** Р5 + находки I1, M-A.

**Почему.** Внешний `except` (`service.py:828-831`) ставит
`self._rest_inprocess = None`, а `_get_rest_inprocess_summary` на `None` отдаёт
словарь, байт в байт совпадающий с «рубильник выключен». ErrorBus не пушится.
Для канарейки это ложноотрицательный сигнал на две недели.

Дыра уже, чем кажется: `start()` документирован как «НИКОГДА не бросает» и
возвращает `bool` во всех ветках, значит внешний `except` ловит только сбой
сборки приложения — импорт, `adopt_external_singletons`, `create_app()`,
конструктор.

**Что сделать.**

1. `InProcessRestServer.__init__` принимает `enabled: bool` параметром и
   **перестаёт читать** `settings.REST_IN_PROCESS_ENABLED` сам
   (`rest_inprocess.py:38`). Иначе рубильник двухголовый: владелец включает
   настройкой, `service.py` конструирует сервер, а тот молча возвращает `False`.

2. В `service.py` при сбое сборки не обнулять поле, а ставить надгробие:

```python
class _RestInProcessTombstone:
    """Надгробие: сборка REST-приложения упала, лечить нечего.

    Существует, чтобы диагностика отличала «рубильник выключен» от «включён,
    но не поднялся»: без него обе ситуации давали идентичный ответ, и канарейка
    две недели видела бы штатную картину при мёртвом REST.
    """

    def __init__(self, *, enabled: bool, port: int, error: str) -> None:
        self._status = {
            "enabled": enabled,
            "running": False,
            "port": port,
            "error": error,
            "tombstone": True,
        }

    def status(self) -> dict:
        return dict(self._status)

    def stop(self, timeout: float | None = None) -> None:
        """Останавливать нечего — метод есть ради единообразия с close()."""
```

   Поле `tombstone` — не косметика: сторож задачи 7 обязан по нему отличать
   нелечимое, иначе будет вечно лечить надгробие и выдаст `rest.wedged` поверх
   уже отправленного `rest.startup_failed`.

3. Новый код ошибки `rest.startup_failed` в `error_codes.py` по образцу
   `rest.port_conflict` (строки 842-853): severity `error` (в отличие от `warn` у
   конфликта порта — там fail-open с живым легаси-REST, здесь REST не работает
   вообще), `actionable: False`, `dedupe_seconds: 300`. Пуш — из ветки `except`
   через существующий `_push_rest_error`.

4. **Обновить существующие тесты** — смена сигнатуры `__init__` (обязательный
   `enabled`, отказ от чтения `settings`) ломает пять конструкторов:
   - `KrabEar/tests/test_rest_inprocess_server_M2.py` (строки 39, 48, 67, 81, 107);
   - `KrabEar/tests/test_service_rest_inprocess_wiring_M2.py`;
   - `KrabEar/tests/test_diagnostics_rest_inprocess_M2.py`.

   Тесты, полагающиеся на `REST_IN_PROCESS_ENABLED` в конфиге, теперь передают
   значение параметром. Без этой правки задача сдаётся зелёной, а CI краснеет.

5. Новые тесты: три состояния диагностики различимы (выключено / работает /
   сборка упала); при сбое сборки ErrorBus получает `rest.startup_failed`;

мержится первой, задача 2 ребейзится поверх. Координатор сводит ветки сам.

**Чего НЕ делать.** Не менять `health_check_service.py` — он уже умеет звать

### Задача 5 — дренаж запросов и посчитанный бюджет останова

**Спека:** Р7 + находки C3, I-F, M-E.

**Почему.** `stop()` не ждёт хендлеры, и это не недосмотр, а свойство стека:
werkzeug 3.1.8 отдаёт `ThreadedWSGIServer` с `daemon_threads = True`, а
`socketserver._Threads.append` ранним `return` выбрасывает daemon-треды из
реестра — `server_close()` джойнит пустой список, `block_on_close = True`
бесполезен.

Вред не мгновенный: `stop()` не рвёт принятые соединения, закрывается только
слушающий сокет. Настоящий риск — аварийная ветка `os._exit()` в
`_shutdown_backend`, где осиротевший тред обрывается посреди записи в NDJSON.
Пишут в общий store два эндпойнта: `POST /v1/vocabulary` и
`POST /v1/stt/transcribe`.

**Что сделать.**

1. **Флаг `shutting_down`, а не `server.shutdown()`.** Наивное «закрыть допуск
   через `shutdown()`» не работает: слушающий сокет остаётся открытым, ОС
   продолжает принимать соединения в backlog, клиент коннектится и молча ждёт до
   RST при `server_close()`. Voice Gateway висел бы до своего таймаута 30 с —
   дольше всего нашего бюджета, и выглядело бы как зависание Krab Ear.

   Ввести флаг в `rest_inprocess.py`, проверять его в `before_request`
   Flask-приложения и возвращать `503` с телом `{"error": "shutting_down"}`.

2. **Реестр активных запросов** через `before_request` и `teardown_request`.
   Долгоживущие стримы (`GET /v1/events`, WS `/v1/stream`) в реестр **не
   входят** — иначе дренаж выгорал бы бюджет всегда: SSE-соединение по
   определению открыто до сентинела.

3. **Дренаж с общим бюджетом** по образцу `IPCServer.stop()` (`ipc_server.py:65-129`).
   Скопировать семантику дословно, включая докстринг: бюджет — общий на все
   потоки, а не таймаут каждого `join()`; при истечении — `logger.warning` со
   счётчиком незавершённых; наверх — `bool`.

4. **Порядок в `stop()`:** рассылка сентинела SSE-подписчикам (колбэк) → дренаж
   по реестру → `shutdown()` → `server_close()`. Сентинел раньше дренажа, чтобы
   стримы закрылись сами.

5. **Порядок в `_shutdown_backend` (`service.py:223-274`):** взвод
   `shutting_down` идёт **до** `IPCServer.stop(8.0)`. Тогда восемь секунд
   IPC-дренажа работают одновременно как окно дренажа REST, а не последовательно
   с ним.

   (Остановка сторожа встанет ещё раньше — это задача 7, она правит то же место.
   Воркер задачи 5 оставляет комментарий-якорь, чтобы задача 7 знала, куда
   вставать.)

6. **Бюджет как инвариант.** `ExitTimeOut=15` в шаблоне плиста, из них уже
   заняты `_IPC_DRAIN_BUDGET_SEC = 8.0` (`service.py:220`) и
   `SHUTDOWN_JOIN_TIMEOUT_SEC = 5.0` (`rest_inprocess.py:22`). Новый бюджет
   дренажа REST обязан помещаться в остаток.

   Тест **арифметический**: сумма именованных констант ≤ значения `ExitTimeOut`,
   прочитанного из шаблона. Записать в докстринге теста прямо, что он проверяет
   только арифметику: реальный риск (STT в дренаже, скорость диска при
   компактировании) покрывается смоком SIGTERM под нагрузкой из задачи 10, а не
   этим тестом.

   Если арифметика не сходится — поднять `ExitTimeOut` в шаблоне (он и так
   правится задачей 1) и объяснить новое значение комментарием.

**Тесты:** `503` при взведённом флаге; дренаж дожидается активного запроса;
дренаж не ждёт SSE-стрим; бюджет-арифметика; `stop()` при живом SSE-клиенте не
виснет.

**Чего НЕ делать.** Не переключать `daemon_threads` в `False`: `server_close()`
тогда джойнит без таймаута, и зависший `POST /v1/stt/transcribe` повесит
останов навсегда. Не трогать `shutdown_handler.py` — обоснование в спеке Р7.

### Задача 6 — динамическое подавление моста

**Спека:** Р4 + находка C1.

**Почему.** `EventBridge` решает про себя один раз в конструкторе
(`event_bridge.py:173`): читает `REST_IN_PROCESS_ENABLED` и выключается по нему.
Мост стартует раньше (`service.py:796`), чем делается попытка поднять REST
(`service.py:827`), и `bool`-результат `start()` игнорируется.

Два дефекта разом. Первый: REST не встал (порт занят) → мост уже выключен →
SSE-подписчики Swift на `:5005` глохнут, а текст ошибки обещает «Основные
функции работают». Второй, тяжелее: если подавление одноразовое, а сторож
поднимет REST через десять секунд, мост начнёт постить в **собственный**
процесс. `emit_envelope` кладёт конверт напрямую в `_subscribers`
(`event_bus.py:210-217`), минуя листенеров — эха нет, но исходный `emit()` уже
положил тот же конверт. Каждое событие доставляется дважды: удвоенные субтитры и
партиалы при совершенно штатной диагностике.

**Что сделать.**

1. `EventBridge.__init__` перестаёт читать `REST_IN_PROCESS_ENABLED`. Вместо
   этого принимает `rest_running_fn: Callable[[], bool] | None = None` —
   аксессор, отвечающий на вопрос «слушает ли in-process REST **сейчас**».
   `None` означает «владельца нет» (standalone, тесты) и трактуется как «не
   слушает».

2. Проверка выполняется **перед отправкой каждого батча**, а не при старте.
   Killswitch `EVENT_BRIDGE_ENABLED` остаётся как был — он про сам мост.

3. `service.py`: блок подъёма REST переезжает **выше** создания моста. Проверено,
   что это безопасно: все коллабораторы, нужные блоку REST, созданы раньше
   (`store` 306, `transcriber` 337/342, `translator` 359, `_settings_svc` 373,
   `_error_bus` 498, `_tts` 586 — мост на 791). Мост получает аксессор,
   читающий `status()["running"]` у владельца in-process REST.

4. В `get_diagnostics` моста добавить состояние `suppressed` — чтобы канарейка
   отличала «мост выключен killswitch'ем» от «мост подавлен работающим REST».

**Тесты:** три ситуации из таблицы спеки Р4 (рубильник выключен → мост работает;
REST слушает → подавлен; REST не слушает → работает); подавление меняется
**динамически** между двумя батчами без пересоздания моста; при `None`-аксессоре
мост работает.

🔴 Тест на двойную доставку обязателен: поднять шину, эмитить событие при
подавленном мосте и утвердить, что подписчик получил его **ровно один раз**.
Условие именно `== 1`, не `>= 1` — иначе тест не отличает дубль.

### Задача 7 — сторож REST

**Спека:** Р6 + находки C-A, I-A, I-B, I4, I5, I6, M-A, M-D. Новый модуль
`KrabEar/backend/rest_watchdog.py`.

**Почему.** `_serve` при падении `serve_forever` пишет `_error` и логирует — и
всё: ни пуша ErrorBus, ни рестарта, ни сторожа. До включения режима `KeepAlive`
поднимал REST после любой смерти; после — не поднимает никто. При этом
`get_diagnostics` не поллится фоново ни в Python, ни в Swift: различимость
состояний в коде есть, наблюдателя нет ни одного.

**Что сделать.** Образец стиля — `KrabEar/backend/wake_word_watchdog.py`:
daemon-тред с `while not self._stop_event.wait(interval)`, эпизоды, анти-шторм
скользящим окном, эскалация через `ErrorBus.push(KrabError(...))` с полями из
`ERROR_REGISTRY`.

1. **Тик 10 с** — проверка `status()["running"]` при включённом режиме.

2. **Проба `GET /health`** раз в 30 с на loopback, таймаут 2 с.

   🔴 **Провалом считаются ТОЛЬКО таймаут и ошибка соединения.** `/health`
   (`rest_server.py:862-867`) не защищён `require_api_key` и лимитирован
   `120 per minute` по remote address, а Voice Gateway, Swift и сторож приходят
   с `127.0.0.1` и делят один бакет. Любой HTTP-ответ, включая 429 и 5xx,
   доказывает, что сервер жив.

3. 🔴 **Серия, а не одно наблюдение.** Лечение начинается после N ≥ 2 подряд
   провалов, то есть не менее 60 с нездоровья. Симметрично тридцатисекундному
   порогу staleness у сторожа wake-word, который устроен через непрерывный
   эпизод. Одиночный провал — только `logger.warning`.

   Без этого один выброс под нагрузкой (финальная транскрипция встречи держит
   CPU) убивал бы здоровый REST и рвал SSE панелей.

4. 🔴 **Занятый порт — не смерть.** `running=false` от `EADDRINUSE` неотличимо
   от «REST умер», а окно «режим включён + порт держит легаси-юнит» существует
   **по конструкции** волны, пока юнит не выгружен. Наивный сторож дал бы вечный
   шторм: каждые 10 с `restart()` → `EADDRINUSE` → новый пуш `rest.port_conflict`
   → три попытки за 600 с → `rest.wedged`, и re-arm не наступил бы никогда.

   Поэтому: сторож лечит только то, что **хотя бы раз успешно слушало** (флаг
   «был живой serve» в `InProcessRestServer`), а успешный HTTP-ответ пробы при
   `running=false` трактуется как «порт обслуживает кто-то другой» → отдельное
   состояние `port_held_externally` в диагностике, без лечения и без эскалации.

5. **Не лечить надгробие.** При `status()["tombstone"] is True` (задача 4)
   лечить нечего: сборка приложения упала. Иначе сторож выдаст `rest.wedged`
   поверх уже отправленного `rest.startup_failed` — двойная эскалация одного
   отказа.

6. **Контракт `restart()`.** Наивная реализация зависла бы на том самом отказе,
   который ловит: `stop()` зовёт `server.shutdown()`, блокирующийся **без
   таймаута**, а барьер `_serving` защищает только «тред ещё не вошёл в цикл».
   Плюс `start()` рано возвращает `True` при `self._server is not None`
   (`rest_inprocess.py:59-60`) — на залипшем-но-живом сервере повторный `start()`
   был бы тихим no-op, вечно рапортующим успех лечения.

   Поэтому `restart()` = `stop()` + `start()`, где `stop()` исполняется на
   **отдельном** треде с общим deadline; по истечении сторож идёт сразу к
   эскалации, не дожидаясь.

7. 🔴 **Терминальная защёлка.** Single-flight сериализует `stop()` и `restart()`,
   но не запрещает сторожу взять флайт **после** того, как `close()` его
   отпустил: shutdown идёт дальше (TTS и адаптеры закрыты), а сторож поднимает
   REST заново — сервер принимает запросы над полузакрытыми коллабораторами.

   Поэтому: остановка сторожа — **самый первый шаг** `_shutdown_backend`, до
   взвода `shutting_down` из задачи 5 (там оставлен комментарий-якорь); плюс
   необратимое состояние `shutting_down` в самом сторже, после которого лечение
   запрещено навсегда. Аналог maintenance-окна в `openwakeword_adapter`.

   В `close()` остановка сторожа идёт **до** `rest_inprocess.stop()`
   (`service.py:1826-1832`).

8. **Анти-шторм и re-arm.** Не более 3 лечений в окне 600 с. После непрерывного
   здорового периода счётчик обнуляется — иначе «исчерпание лечений» означало бы
   «сдаёмся навсегда», и REST оставался бы мёртвым до ручного вмешательства.

9. **Новый код ошибки** `rest.wedged` в `error_codes.py`: severity `error`,
   `actionable: False`, `dedupe_seconds: 300`. Образец полей — существующая
   запись `audio.wakeword_wedged` в том же реестре.

10. **Лог-шум.** Проба раз в 30 с проходит через штатное request-логирование
    (`rest_server.py:280`) — около 2880 строк в сутки навсегда. Исключить
    loopback-пробу из access-лога либо логировать только не-2xx.

11. Секция `rest_watchdog` в `get_diagnostics` — по образцу
    `wake_word_watchdog`.

**Тесты:** одиночный провал не лечит; N подряд — лечит; HTTP 429 не считается
провалом; `port_held_externally` при живом чужом сервере на порту; надгробие не
лечится; анти-шторм; re-arm обнуляет счётчик; лечение запрещено после
`shutting_down`; `restart()` не виснет при залипшем `stop()`.

🔴 **`make audit-all` обязателен**: задача создаёт новый модуль, а
`audit_dead_extracted_modules.py --fail-on-found` и
`audit_decorative_wiring.py --strict` валят CI на модуле без прод-импортёра или
на поле, которое никто не зовёт.

**Чего НЕ делать.** Не эскалировать в `BackendSupervisor.forceRestartBackend()` —
он перезапускает **весь** backend через `kickstart -k`, то есть теряет активную
диктовку или встречу. Деградация REST предпочтительнее потери записи владельца.

## Чанк 3 — клиенты, остатки, замеры

### Задача 8 — переподключение SSE в скретчпаде

**Спека:** Р12 (находка I-E). Единственная задача волны, трогающая Swift.

**Почему.** `QuickCapturePanelController.swift:102` создаёт
`SSESessionDelegate { [weak self] line in ... }` — только обработчик строки, без
`onComplete`. Сам делегат в докстринге говорит, что решение о переподключении
остаётся за экраном; экран его не принял.

До включения режима REST рестартовал редко. После — стрим рвётся при каждом
лечении сторожа и при самом включении. У панели встречи есть poll-фоллбэк, у
скретчпада нет ничего: панель показывает застывший текст, запись продолжается,
диагностика зелёная.

**Что сделать.** Добавить `onComplete` с переподключением и экспоненциальным
backoff. Переподключение только пока панель видима и режим активен — иначе
получится вечный цикл переподключений к мёртвому порту.

**Гейт:** `swift build -c release`. Тесты — по образцу существующих
Swift-тестов панелей, если они есть; иначе source-контракт тест, проверяющий,
что делегат создаётся с обработчиком завершения.

**Чего НЕ делать.** Не трогать `MeetingLivePanelController` — у него есть
poll-фоллбэк, и это отдельный скоуп.

### Задача 9 — остатки

**Спека:** Р10.

1. **Рабочее включение настройкой.** Строчный ключ `rest_in_process_enabled`
   есть в `DEFAULT_SETTINGS` (`config.py:1019`), но его не читает ни один
   участок прод-кода: рубильник живёт только в pydantic-поле. `set_settings`
   рапортует успех и не делает ничего.

   Для этой волны ключ — **основной способ включения** (дефолт не меняется),
   поэтому он обязан работать. Паттерн волны 58: читать
   `self._get_runtime_setting('rest_in_process_enabled', settings.REST_IN_PROCESS_ENABLED)`,
   результат передавать параметром `enabled` в `InProcessRestServer` (интерфейс
   из задачи 4). Рубильник остаётся читаемым один раз при старте — не
   live-toggle.

2. **Докстринг `StaticDeps`** (`rest_server.py:75-76`) утверждает «Путь M2:
   BackendService собирает deps из своих коллабораторов». M2 пошла подменой
   глобалов. Класс жив, используется тестами M1. Правка — только докстринг.

3. **`_rest_engine_cleanup`** (atexit, `rest_server.py:769-772`) читает голое
   `engine`. После подмены это объект backend'а — atexit закрывает его
   GigaAM-адаптер, а не свой. Дать `adopt_external_singletons` парную операцию
   освобождения и не трогать усыновлённые объекты в atexit.

**Тесты:** включение настройкой реально поднимает REST; atexit не закрывает
усыновлённый адаптер.

### Задача 10 — смок и замеры

**Спека:** Р8 + §1.3 + находки I-G, M-C, M-E.

1. **Довести смок до буквы родительской §4.5**: `POST` вместо `GET`, проверка WS
   `/v1/stream`, проверка **ответа** `set_settings` перед печатью «окружение
   облегчено» (сейчас печатает не проверяя, поэтому опечатка невидима), и сам
   ключ исправить: в смоке `llm_rewriter_enabled`, настоящий —
   `llm_rewrite_enabled`.

2. **Замеры RAM и p95** через `scripts/memory_baseline.py` до и после включения.
   Обещание серии M «минус сотни МБ дубля» до сих пор не подтверждено ни одним
   числом — либо подтвердить, либо опровергнуть явно.

3. 🔴 **Три сценария конкуренции за GPU.** Родительская §4.4 утверждала, что
   REST-транскрипция и диктовка «уже сериализуются межпроцессным flock». Это
   ложная посылка: `mlx_inter_process_lock()` возвращает no-op без
   `KRAB_EAR_MLX_INTER_PROCESS_LOCK=1` (`core/mlx_inter_lock.py:246-253`), и
   переменной нет ни в одном плисте. Сегодня они бьются за Metal свободно; после
   слияния попадут под общий `mlx_lock()`.

   Мерить надо не только диктовку:
   - латентность диктовки под конкурентным `POST /v1/stt/transcribe`;
   - **лаг снапшота живой встречи** под тем же фоном (CHUNK_STT каждые 25 с);
   - **лаг live-субтитров** под тем же фоном (flush каждые 3 с).

   Первый — разовая латентность, два других — накопление отставания. Панель
   встречи, отставшая на десятки секунд, спишется на «медленную модель», если
   этого сценария в замерах нет.

4. **Смок SIGTERM под нагрузкой** — живое доказательство бюджета из задачи 5:
   послать сигнал во время активного `POST`, убедиться, что teardown уложился в
   `ExitTimeOut` и `runtime_alive.marker` удалён штатно.

5. **Транзитный дубль на старте** зафиксировать в журнале замеров:
   `service.py:812` импортирует `rest_server` → на импорте строятся второй
   `AudioEngine` и второй `StateStore` (`rest_server.py:712-713`), которые тут же
   вытесняются `adopt_external_singletons`. Это удлиняет старт и на секунды
   создаёт второй store на живых файлах. Без записи цифры превратятся в загадку.

🔴 Все замеры — на throwaway-инстансе с временным `--data-dir`, никогда против
прод-процесса владельца.

**Спека:** §4 + находка I-D.

`scripts/migrate_to_inprocess_rest.command`, образец стиля —
