# A5.2b3 — disk-guard + retention новых снимков — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development
> (или executing-plans). Шаги — чекбоксы.

**Goal:** Закрыть два риска, зафиксированных ревью A5.2b1/b2: (1) при заполнении
диска запись журнала истории падает, а это **потеря истории**; (2) снимки нового
формата растут без ограничения (`max_copies` при ON выключен), а неудачный restore
оставляет лишний полный снимок.

**Architecture:** (a) **превентивный disk-guard** перед фазой prepare в обоих
snapshot-протоколах (создание и restore) — считаем необходимое место и отказываем
**до** записи, а не после ENOSPC; (b) **retention только для новых форматов**
(`snapshot_*`, `auto_snapshot_*`, `snapshot_prerestore_*`) с жёсткой границей
«никогда не трогать pending-маркер» и «никогда не трогать legacy `backup_*` /
`auto_backup_*`» (их инвентаризация — A5.2c, решение владельца); (c) честная
наблюдаемость: причина пропуска и свободное место видны в статусе и диагностике.

**Tech Stack:** уже в репо — `shutil.disk_usage`, существующие `encrypted_snapshot.py`
/ `auto_backup.py` / `health_check_service.py`. Новых зависимостей нет.

**База:** `origin/codex/krab-ear-v2` (содержит #2056 b1, #2058 b2, #2059 баннер).
Worktree: `.worktrees/a52b3-disk-guard`, ветка `codex/ear-a52b3-disk-guard`.

**Карточка лежит рядом с этой карточкой в worktree** (её создаст координатор) —
закоммить её первой строкой (provenance, как в b1/b2).

**Спека-канон:** `docs/superpowers/specs/2026-09-24-a5-history-at-rest-design.md` §5.1

## Принятые решения (не переигрывать)

1. **Порог места считается по фактическому размеру набора**, а не «на глаз»: сумма
   размеров 10 журналов × коэффициент записи (ENC1 base64 ≈ 1.4 к длине строки плюс
   overhead) — проще и честнее: измерить суммарный размер исходных журналов, умножить
   на 2 (снимок + страховка) и накинуть запас. Плюс **свободное место проверяется на
   целевом каталоге** (`shutil.disk_usage` по реальному пути, куда пишем), а не по
   `/`.
2. **Отказ — до первой записи.** Никаких «начали и упали»: если места не хватает,
   `prepare` не начинается, ничего не создаётся, причина машинно-читаема.
3. **Retention трогает только новые форматы.** `snapshot_*`, `auto_snapshot_*`,
   `snapshot_prerestore_*` — с границами: `auto_snapshot_*` уважает `max_copies`
   (как legacy), `snapshot_prerestore_*` — ограниченное число (предлагаю 3) самых
   свежих, **кроме** каталога, на который ссылается живой pending-маркер.
4. **Legacy `backup_*` / `auto_backup_*` при ON НЕ удаляются никогда** — там могут
   лежать plaintext-копии, инвентаризация которых принадлежит A5.2c и владельцу.
   Это должно быть закреплено тестом, а не только комментарием.
5. **OFF-профиль не меняется** — retention/disk-guard не должны трогать legacy
   поведение вообще (кроме случая 3 при ON).
6. **Наблюдаемость:** причина пропуска (`skipped_reason`) + свободное место видны в
   `get_auto_backup_status` и в `get_diagnostics`; «причина в статусе» из A5.2a
   не должна превращаться в ложь.

### Task 1: Превентивный disk-guard (создание + restore)

**Files:**
- Modify: `KrabEar/backend/encrypted_snapshot.py`
- Test: `KrabEar/tests/test_a52b3_disk_guard.py`

- [ ] **Step 1: RED**
1. Мало места (подменённый `disk_usage`) при **создании** снимка → отказ
   `snapshot_insufficient_space` **до** mkdir/записи: staging не создан, живое не
   тронуто, ничего не остаётся на диске.
2. То же при **restore** → отказ до pre-restore снимка (тот самый «лишний полный
   снимок при ENOSPC»).
3. Места хватает → снимок и restore проходят как раньше (регресс).
4. Порог считается по **целевому** каталогу: если `backups` — symlink на другой том,
   проверяется тот том (иначе гейт проверяет не тот filesystem).
5. Граница: места ровно хватает на снимок, но не хватает на страховку → отказ
   (страховка — не опция: без неё цена неудачного restore выше отказа).

- [ ] **Step 3: Реализация** — `def _ensure_space_for(*, target_dir, journal_bytes, copies, safety_factor)`;
  вызовы в `build_encrypted_snapshot` и `restore_encrypted_snapshot` **до** любой

### Task 2: Retention новых форматов

- [ ] **Step 1: RED**
1. При ON больше `max_copies` снимков `auto_snapshot_*` → лишние удаляются, N самых
   свежих целы.
2. `snapshot_prerestore_*` ограничены (предлагаю 3), но **каталог, на который
   ссылается живой pending-маркер, не удаляется ни при каком числе** (это страховка
   незавершённого restore).
3. **Legacy `backup_*` / `auto_backup_*` при ON не удаляются** (тест на отсутствие
   удаления, даже когда их больше `max_copies`).
4. OFF-профиль: поведение retention **бит-в-бит прежнее** (регресс существующих
   тестов `test_auto_backup*`).
5. Удаление не должно оставлять мусор (никаких временных каталогов) и не должно
   ломать счётчики статуса.

- [ ] **Step 2: Run** — [ ] **Step 3: Реализация** — отдельная функция
  `prune_snapshot_family(...)`; вызов из auto-backup-пути **после** успешного
  снимка (никогда не до), и **никогда** при активном pending restore.
