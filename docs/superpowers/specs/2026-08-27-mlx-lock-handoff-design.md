# Передача mlx_lock брошенному потоку — корень потери диктовок

**Дата:** 2026-08-27
**Статус:** РЕАЛИЗОВАНО (ревью дизайна — соседняя сессия, нашла дыру в §5.3)
**Класс:** sibling-asymmetry + нарушение инварианта критической секции
**Продолжает:** `2026-08-26-stt-timeout-budgets-design.md` §8 «Не-цели» — та волна
осознанно ограничила ПОСЛЕДСТВИЕ и назвала кандидатом корня «захват `mlx_lock()`
без таймаута». Здесь корень назван точно и устраняется.

## 1. Улика

Живой инцидент 2026-08-27, две потерянные диктовки владельца подряд.

`sample` зависшего backend (pid 77698): **четыре** брошенных потока
`ThreadPoolExecutor-*` стоят на `rlock_acquire` — это `mlx_lock`. При этом ВСЕ
потоки `libmlx.dylib` спят в `__psynch_cvwait`: GPU не занят, работы нет, замок
просто не отпущен.

Хронология из `logs/krab-ear-backend.out.log`:

| время | событие |
|---|---|
| 02:03:23 | `GigaAM транскрибация завершена: len=289` — **0.5 с** |
| 02:55:08 | `GigaAM chunker path: duration=27.7s → 2 chunks` → тишина |
| 02:58:01 | `handle_request завис дольше 180с (method=stop_recording)` |
| 02:58:50 | тот же чанкер → тишина |
| 03:01:50 | `handle_request завис дольше 180с (method=transcribe_paths)` |

Контрольные замеры: прямой `mlx_whisper.transcribe` на том же WAV — **6.9 с**
(движок здоров); тот же файл через backend ПОСЛЕ `safe_backend_restart.command`
— **1.2 с**. Гипотеза «мало памяти» опровергнута: воспроизводится при 59 %
свободной памяти.

Вывод: после первого зависания состояние процесса необратимо испорчено —
лечит только перезапуск.

## 2. Корень

`core/pipeline/stt_gigaam_mlx.py`, `_infer_chunk` (~164) и `_run_with_timeout` (~178):

```python
with mlx_inter_process_lock(), mlx_lock():        # критическая секция GPU
    return self._run_with_timeout(lambda: gigaam_mlx.transcribe(...))
...
except FuturesTimeoutError:
    self._executor.shutdown(wait=False, cancel_futures=True)   # поток БРОШЕН
    self._executor = None
    raise MLXTimeoutError(...)                                  # замок отпущен
```

Рабочий поток исполняет `fn()` **не** владея замком — замок держит вызывающий.
При таймауте вызывающий выходит из `with` и отпускает замок, пока брошенный
поток всё ещё внутри Metal-вызова. Следующая транскрипция берёт замок и
запускает **второй параллельный MLX-инференс** — ровно тот конкурентный доступ,
ради запрета которого `mlx_lock` и существует (`mlx_lock.py`: повреждение
`__hash_table<MTL::Resource*>` → SIGSEGV/зависание).

## 3. Почему это sibling-asymmetry

`core/mlx_subprocess.py::MLXWatchdog.run_with_timeout` **этот же баг уже чинил**
(W1358 F1 MED, сестра PR #71). Его докстринг (строки 137-162) описывает
сценарий дословно, а фикс — bounded `join(MLX_HANG_HARD_KILL_SEC)`, который
**удерживает `mlx_lock`, пока демон жив**, и только затем бросает
`MLXTimeoutError`. Компромисс там же назван честно: если поток не умер за
hard-kill окно, замок всё же отпускается, но это «строго лучше бесконечного
стола».

`stt_gigaam_mlx.py` появился позже и написал свой `_run_with_timeout` мимо
готового паттерна. Классический признак: один путь научился на инциденте,
сиблинг — нет.

## 4. Смежная находка

`core/mlx_lock.py::acquire_mlx_lock(timeout_sec)` — безопасный захват с
таймаутом — в проде **не используется ни разу**. Восемь боевых мест берут
`with mlx_lock():` вечным ожиданием. Механизм защиты существует и никогда не
исполнялся (класс «аварийный механизм с нулём срабатываний»).

Отсюда второй симптом инцидента: ожидающие не получают ошибку, а висят до
180-секундного IPC-backstop, и владелец видит «Ответ остановки не получен».

## 5. Что меняем

**5.1. `_run_with_timeout` держит замок за брошенный поток.**
При `FuturesTimeoutError` — bounded `join` рабочего потока (окно
`MLX_HANG_HARD_KILL_SEC`, уже существующая константа) ДО выхода из критической
секции. Executor не пересоздаётся, пока старый поток жив.

**5.2. Ограничение ожидания замка — ОТВЕРГНУТО в этой волне.**
Первоначально планировалось заменить `with mlx_lock()` на
`acquire_mlx_lock(timeout_sec=...)`. Отвергнуто после разбора: 5.1 устраняет
*потерю* замка, а всё оставшееся ожидание — честная очередь за GPU. Таймаут на
неё вернул бы ровно тот дефект, который разбирала спека #1956 §«Гейт
блэклиста»: диктовка во время импорта часового файла истекает по ожиданию,
**ни разу не коснувшись GPU**, обе модели уходят в `_unavailable_models`, и
владелец получает «Критическая ошибка» на здоровом стеке.

Возвращаться сюда — только с отдельным замером реальных очередей.
🔴 Порядок захвата не трогаем вовсе: `mlx_inter_process_lock()` остаётся
внешним (спека #1956 уже отвергла обёртку из-за ABBA-deadlock).

**5.3. Отравленное состояние объявляется явно — и имеет выход.**
Если поток не умер за hard-kill окно, адаптер помечается отравленным: замок
отпускается (иначе бесконечный стол), но последующие вызовы GigaAM-MLX
получают немедленный отказ вместо ожидания. `engine.py:2723` уже ловит
`MLXTimeoutError`, помечает модель недоступной и уходит на следующий адаптер —
диктовка сохраняется, пусть и другим движком.

🔴 **Выход из состояния** (дыра, найденная на ревью соседней сессией; в первой
редакции §5.3 сброс был упомянут только в рисках). Привязка к «успешному
прогреву» не работает: `_warmup()` идёт через тот же `_infer_chunk`, то есть
через отравленный гейт — замкнутый круг, состояние стало бы липким до
перезапуска процесса.

Единственный честный признак того, что Metal освободился, — завершение того
самого зависшего `future`. Он сохраняется при отравлении и опрашивается
(**не** ожидается — это и есть зависший вызов) при каждом `is_poisoned()`:
`future.done()` → отравление снимается, движок возвращается в строй без
перезапуска backend.

## 6. Критерий успеха

- Диктовка НЕ теряется даже при зависшем Metal: каскад отдаёт текст резервным
  движком.
- Ни одного `handle_request завис дольше 180с` по вине ожидания `mlx_lock`.
- После зависания процесс остаётся рабочим — перезапуск не требуется.

## 7. Не-цели

- Смена транспорта на `subprocess`. Замер 2026-08-27 на 31.4-секундной диктовке
  (полный конвейер, тот же файл): mlx — 1.86 с холодная / 0.54-0.60 с тёплые;
  subprocess — 6.47 с / 1.83-2.02 с; текст **побайтово идентичен**. Владелец
  выбрал mlx ради скорости и отдельную волну ради корня.
- Правка остальных семи мест с `with mlx_lock()`. Отдельный проход после того,
  как паттерн подтвердится на GigaAM-MLX.

## 8. Риски

- Удержание замка на hard-kill окно задерживает соседние транскрипции на
  величину окна. Приемлемо: альтернатива — порча состояния GPU.
- Отравленный флаг обязан иметь выход — механизм специфицирован в §5.3
  (опрос зависшего future). Без него это «липкое состояние без выхода» —
  известный класс из кодекса проекта.
- Опрос future вместо ожидания: если Metal не отпустит поток никогда, движок
  останется отравлен до перезапуска. Это осознанно — работать поверх живого
  зависшего потока строго опаснее.
