# Чтения истории не должны блокировать друг друга

Дата: 2026-08-13. Повод — живой отказ диктовки владельца 12:07.

## 1. Корень (доказан логом, не гипотеза)

```
12:07:50–56  ВОСЕМЬ переполнений аудиобуфера подряд
12:07:55     load_settings ждёт эксклюзивный flock — уже держит
             state_store.py:1459:_load_active_items_with_lock 9.8с   ← ×6 за 200мс
12:07:56     _load_active_items_with_lock ДЕРЖАЛ эксклюзивный flock 10.2с
12:08:14     Realtime preview worker не завершился за 1.5 с
             → «Ответ остановки не получен» у владельца
```

**226 таких строк за сутки.** Держатель — `_load_active_items_with_lock`
(`state_store.py:1457`), который на 12 600 записях владельца работает ~10 с.
Всё, что читает настройки (а privacy-гейт делает это почти в каждом
IPC-хендлере), стоит в очереди за ним.

🔴 **При этом обе стороны — ЧИСТЫЕ ЧТЕНИЯ.** `_load_active_items_unlocked`
собирает локальные словари и список, ничего общего не мутирует;
`load_settings` читает `settings.json`. Они блокируют друг друга только
потому, что `_lock()` умеет ровно один режим — `fcntl.LOCK_EX`
(`state_store.py:387`). Разделяемого режима в коде нет.

Это тот же корень, что зафиксирован в
`reference_settings_read_shares_history_lock`: прошлые волны ограничивали
ОЖИДАНИЕ (бюджеты, zero-wait для ping), но сериализацию читателей не трогали.

## 2. Решение: shared-режим для доказуемо чистых чтений

`_lock(shared=True)` → `fcntl.LOCK_SH` вместо `LOCK_EX`. Несколько читателей
держат лок одновременно; писатели по-прежнему берут `LOCK_EX` и ждут всех
читателей. Семантика записи не меняется вовсе.

Включаем ТОЧЕЧНО, не глобально. Кандидаты первой волны — только те, чья
чистота доказана чтением кода:
- `_load_active_items_with_lock` (главный виновник, 10 с удержания);
- `load_settings` (read-path; write-path `save_settings` остаётся `LOCK_EX`).

Остальные ~50 call sites НЕ трогаем в этой волне.

## 3. 🔴 Опасность, на которой такая правка обычно ломается

`_lock()` реентерабелен per-thread через depth-counter (#1872, живой
production-дедлок). Если тред возьмёт **shared**, а затем вложенно попросит
**exclusive**, счётчик увидит depth>0 и НЕ будет захватывать заново — запись
пойдёт под разделяемым локом, молча, без единой ошибки. Это тише и хуже
дедлока.

Обязательные требования:
1. Реентерабельность обязана помнить РЕЖИМ. Вложенный запрос `LOCK_EX` при
   удерживаемом `LOCK_SH` — это апгрейд, который POSIX flock не даёт
   атомарно; такой случай обязан **громко падать**, а не молча продолжать.
2. Для каждого call site, переводимого на shared, доказать отсутствие
   вложенной записи — грепом по телу, а не «на глаз».
3. Направление отказа: сомневаешься — оставляй `LOCK_EX`. Лишняя
   сериализация стоит секунд, потерянная запись владельца — необратима.

🔴 Известный путь, берущий историю ПЕРЕД настройками:
`migrate_history_encryption` → `progress_cb` → `event_bus.emit` →
`_is_privacy_mode` → `cached_settings` → `load_settings`. Ровно ради него
делали реентерабельность. Проверить его отдельным тестом.

## 4. Осознанно НЕ в скоупе

- Разделение `settings.lock` / `history.lock` (lock-ordering риск, аудит
  ~50 call sites) — по-прежнему отдельная волна.
- Кэширование разобранной истории по mtime — заманчиво, но добавляет
  инвалидацию; сперва дешёвый и обратимый shared-режим.
- Почему `_load_active_items_with_lock` вообще зовётся ВО ВРЕМЯ записи —
  вызывающего установить не удалось (все известные call sites —
  аналитика/дайджест/поиск). Отдельная задача: залогировать вызывающего.

## 5. DoD

- `_lock(shared=True)` берёт `LOCK_SH`; по умолчанию поведение побайтово
  прежнее (`LOCK_EX`).
- 🔴 Вложенный запрос exclusive при удерживаемом shared — ГРОМКОЕ исключение,
  тест обязателен. Молчаливое продолжение = провал волны.
- Два читателя из РАЗНЫХ процессов держат лок одновременно (тест с реальным
  `fcntl`, не мок) — это и есть доказательство, что сериализация ушла.
- Писатель по-прежнему ждёт читателей и наоборот (тест).
- `migrate_history_encryption` (история→настройки) не сломан (тест).
- Существующие инварианты лока зелёные:
  `test_state_store_lock_reentrancy_W_deadlock_fix.py`,
  `test_state_store_lock_invariants.py`.
