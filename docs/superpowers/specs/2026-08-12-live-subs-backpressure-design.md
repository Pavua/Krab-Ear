# Live-субтитры: backpressure бэкенда + выход из sticky-состояния оверлея

Дата: 2026-08-12. Повод — живой инцидент владельца (00:41 CEST): включил
«Live субтитры для видео», пустил русское видео на 2x. Оверлей «улетел»
(не поспевал), затем **завис пустым и не закрывался** — пришлось убирать
вручную. Параллельно бэкенд ушёл в шторм: `KRAB-EAR-BACKEND-1V` вырос до
**2451** событий, заголовок сменился на `method=live_subs_ingest`.

Требование владельца дословно: «нужно чтобы стабильно и при нагрузке
работало».

## 1. Что доказано логами

`backend.log`, 00:42–00:45 — десятки подряд:

```
ERROR: handle_request завис дольше 180с (method=live_subs_ingest)
       — backstop-таймаут, слот освобождён, рабочий поток абандонен
```

То есть **каждый** чанк системного аудио вешал IPC-хендлер на 180 секунд и
сжигал коннект-слот (лимит 64). Пока это шло, деградировал ВЕСЬ бэкенд —
включая диктовку владельца в то же окно.

## 2. F3 (Python, HIGH) — `ingest` делает STT синхронно в IPC-треде

`LiveSubsService.ingest()` (`backend/live_subs_service.py:64`) аккуратно
держит `self._lock` только на мутацию буфера — комментарий в коде прямо
объясняет, что STT намеренно вынесен из-под лока (W1770 MED). Но `_flush()`
вызывается **в том же треде вызывающего**, то есть в треде IPC-хендлера:

```python
        # Лок отпущен — _flush снимет снапшот буфера под локом и выполнит STT уже без него.
        if should_flush:
            return self._flush(sample_rate=sample_rate, target_lang=target_lang)
```

Вне лока — да. Вне IPC-треда — **нет**. При 2x-темпе (вдвое плотнее поток)
и загруженной машине STT не успевает за приходом чанков: хендлер висит,
агент шлёт следующий чанк, тот занимает следующий слот. Обратной связи нет
вовсе — фича не умеет сказать «не успеваю, пропусти окно».

### Решение: single-flight фоновый flush со слотом «последний выигрывает»

- `ingest()` НИКОГДА не выполняет STT. Достигнут порог → под локом снимает
  снапшот буфера, очищает буфер, кладёт снапшот в **слот размера 1**
  (`_pending_window`), будит фоновый воркер, **возвращается немедленно**.
- Фоновый воркер (один на сервис, daemon, стартует лениво при первом
  ingest, останавливается в `stop()`/`reset()`/`close()`): забирает снапшот
  из слота и выполняет STT + эмиссию события полностью вне IPC-тредов.
- Слот занят, приходит новый снапшот → **старый ДРОПАЕТСЯ**, новый
  перезаписывает. Субтитры эфемерны: показать свежее окно правильнее, чем
  отставать на минуту. Счётчик дропов (`dropped_windows`) — наблюдаемость,
  без него «почему пусто» снова будет неотличимо от «сломалось».
- Память ограничена: буфер + не более одного отложенного окна.

**Направление отказа**: воркер упал/не стартовал → `ingest` продолжает
принимать и дропать, НО НЕ ВИСНЕТ. Тишина в субтитрах хуже текста, но
несравнимо лучше падения всего бэкенда.

**`is_final`/`stop()`**: финальный флаш обязан быть синхронным (пользователь
остановил — он ждёт последний кусок), но с явным таймаутом ожидания
воркера, а не бесконечным. При истечении — вернуть `{"status": "stopped",
"flushed": False, "reason": "flush_timeout"}`, не виснуть.

**Контракт WS-пути не менять**: `/v1/stream` зовёт `ingest()` напрямую
(комментарий в коде) — он получает ту же немедленную семантику
автоматически.

## 3. F4 (Swift, MEDIUM) — тумблер не умеет убрать окно

```swift
func toggleLiveSubsCaptureFromMenu() {
    if systemAudioCapture.isCapturing { stopLiveSubsCapture() }
    else { startLiveSubsCapture() }
}
```
(`main+LiveSubs.swift:47`)

Тумблер завязан ТОЛЬКО на `isCapturing`. Захват отвалился сам (бэкенд не
отвечал) → `isCapturing == false` → нажатие хоткея **запускает захват
заново** вместо того, чтобы убрать висящее окно. Штатного способа закрыть
оверлей не остаётся — ровно то, с чем столкнулся владелец.

**Решение**: условие остановки — «идёт захват **ИЛИ** окно видно»:

```swift
if systemAudioCapture.isCapturing || liveSubsOverlay.isVisible {
    stopLiveSubsCapture()
} else {
    startLiveSubsCapture()
}
```

`stopLiveSubsCapture()` уже идемпотентен по обеим частям
(`systemAudioCapture.stop()` + `liveSubsOverlay.hide()`).

## 4. F5 (Swift, MEDIUM) — у оверлея нет timeout-выхода

Класс из кодекса проекта: «sticky state without an exit» — состояние,
которое гейтит собственный выход. Окно `LiveSubtitlesOverlay` показывается
в `startLiveSubsCapture()` и скрывается ТОЛЬКО явным
`stopLiveSubsCapture()`. Если захват умер молча — окно остаётся навсегда:
always-on-top, перетаскиваемое, пустое.

**Решение**: периодическая проверка (таймер 5с, живёт только пока окно
видно): окно видно И `systemAudioCapture.isCapturing == false` дольше
grace-периода (10с) → `hide()` + `logger.info` с причиной.

Grace нужен, чтобы не убить окно в нормальном окне старта/рестарта
захвата. Гейт по `isCapturing`, а НЕ по «давно не было результатов» —
иначе легитимная тишина в видео (пауза, музыка) закрывала бы субтитры.
