# Инкрементальное превью диктовки: курсор вместо скользящего окна

Дата: 2026-08-13. Повод — замер живой диктовки владельца, см. §1.

## 1. Корень (измерено, не гипотеза)

Диктовка владельца 2026-08-13 03:18:19–03:18:58, `backend.log`:

| величина | значение |
|---|---|
| длительность записи | **39.2 с** |
| превью-транскрибаций | **14** |
| суммарное время STT | **29.2 с** |
| движок | GigaAM v3, **device=cpu**, subprocess |

**75% времени записи параллельно с ней молотит CPU-тяжёлый STT.** Каждый проход
берёт скользящее окно `snapshot_audio(max_duration_sec=12.0)` — то есть первые
12 секунд речи распознавались заново ~8 раз. Через движок прошло ≈168 секунд
аудио, чтобы показать превью для 39 секунд.

Следствие — переполнение аудиобуфера (4 раза за эту запись):
`overflowed` приходит от самого PortAudio при `stream.read()`; поток захвата —
обычный Python-тред с блокирующим чтением, под насыщением CPU он не попадает в
своё окно планировщика, кольцевой буфер драйвера переполняется, сэмплы теряются.
Оба переполнения в середине записи легли ровно на превью-проходы (второе — через
6 мс после завершения одного из них).

**Почему F2 (бэкофф превью, волна 08-12) это не закрыл.** F2 реактивен и слишком
мягок: стартовый бэкофф **0.5 с** при натуральной каденции превью **≈1.45 с** —
первые два срабатывания фактически no-op, реальное торможение начинается только
с третьего переполнения (2 с). F2 остаётся как страховка, но лечит симптом.

## 2. Решение: курсор вместо окна (переиспользуем механику встреч)

🔴 **Анти-ребилд**: инкрементальный примитив в проекте УЖЕ есть и обкатан.
`AudioRecorder.snapshot_range(from_sec, to_sec)` (`recorder.py:533`) написан для
аккумулятора встреч, докстрока прямо говорит: «непересекающиеся чанки по курсору
— полный транскрипт без дедупа». `MeetingSessionService._job_chunk_stt`
(`meeting_session_service.py:1188`) применяет его так: `upto = get_duration_sec()`
→ `snapshot_range(cursor_sec, upto)` → транскрибировать → `cursor_sec = upto` →
дописать текст. Превью обязано следовать этому же паттерну, а не заводить свой.

**Отличие превью от встреч**: встречи режут раз в 25 с, превью обязано обновлять
оверлей раз в ~1.5 с. Чистый «курсор + дописывание» на такой каденции резал бы
речь каждые 1.5 с — постоянные обрывы слов на стыках. Поэтому:

### Зафиксированный префикс + живой хвост

Состояние на КАЖДЫЙ вход в `_preview_loop` (новый тред на каждую запись):
- `committed_text: str` — уже зафиксированный текст, больше не перераспознаётся;
- `cursor_sec: float` — граница фиксации.

Итерация:
1. `upto = recorder.get_duration_sec()`; `tail_sec = upto - cursor_sec`.
2. `tail_sec < MIN_TAIL_SEC (0.9)` → ждать, continue (тот же смысл, что нынешний
   гейт `duration_sec - last_refresh_duration < 0.9`).
3. `audio = recorder.snapshot_range(cursor_sec, upto)` — только НОВОЕ аудио.
4. `text = transcriber.transcribe_preview(audio, quality_profile=...)`.
5. Отображение: `_preview_text = committed_text + text` (под `_preview_lock`).
6. Фиксация, если `tail_sec >= COMMIT_MIN_SEC (3.0)` И (хвост заканчивается
   тишиной ИЛИ `tail_sec >= MAX_TAIL_SEC (8.0)`):
   `committed_text += text`; `cursor_sec = upto`.

Стоимость прохода = длина хвоста, которая циклится 0.9 → ~3 с (обычно) и не
превышает 8 с, вместо постоянных 12 с. Зафиксированная часть распознаётся ровно
один раз. Стыки приходятся на паузы в речи, а не на произвольные границы.

**Тишина в конце хвоста** определяется дёшево — RMS последних `SILENCE_TAIL_SEC
(0.4)` секунд ниже порога; отдельная транскрибация не нужна. Порог берём из уже
существующего `RealtimeSilenceFilter`/`SilenceDetector`, новый не вводим.

## 3. 🔴 Критичные края (каждый — тест)

- **Пустой текст из-за лока ≠ пустой текст из-за тишины.** `transcribe_preview`
  по своей семантике возвращает ПУСТО при неудачном захвате bounded `mlx_lock`.
  Зафиксировать такой результат = потерять кусок речи навсегда. Правило:
  фиксируем пустой текст ТОЛЬКО если хвост акустически тих (RMS ниже порога);
  иначе — не фиксируем, курсор не двигаем, отображение оставляем прежним.
- **Долгая тишина не должна растить хвост.** Тихий хвост фиксируется (курсор
  идёт вперёд, `committed_text` не меняется) — иначе после паузы в минуту хвост
  упёрся бы в 8 с и мы бы гоняли 8 с тишины каждый проход.
- **Курсор переживает паузу.** `pause_realtime_partials()` (зовут встречи) не
  должен сбрасывать `cursor_sec`/`committed_text` — иначе после снятия паузы
  речь распознается повторно и текст задвоится.
- **Сброс на новую запись.** Оба поля инициализируются при входе в
  `_preview_loop`, как уже делает `self._preview_overflow_backoff_sec`.
- **Privacy-гейт не трогаем** — он на чтении (`recording_core_service.py:1643`).
- **F2-бэкофф остаётся** страховкой; его стартовое значение НЕ меняем в этой
  волне (отдельный вопрос, см. §5).

## 4. DoD

- Диапазоны, отданные в `snapshot_range`, после фиксации **не пересекаются**
  (тест проверяет аргументы вызовов по всей последовательности итераций).
- Зафиксированный текст больше не перераспознаётся: суммарное количество
  секунд аудио, поданных в `transcribe_preview` за симулированную запись 39 с,
  падает **не менее чем в 3 раза** против текущего поведения (тест считает
  сумму `audio.size`, а не время — время нестабильно в CI).
- Пустой текст при НЕтихом хвосте → фиксации нет, курсор не двинулся,
  `_preview_text` не потерял ранее показанное.
- Тихий хвост → курсор двинулся, `committed_text` не изменился.
- Форс-фиксация при `tail_sec >= MAX_TAIL_SEC` без тишины.
- `_preview_text` равен `committed_text + text` хвоста (тест на конкатенацию).
- `pause_realtime_partials()` → курсор и текст сохраняются, дублей нет.
- Новая запись → состояние сброшено.

- Живая проверка после деплоя: диктовка ~40 с, в логе на неё приходится
