1. **Владелец ждал 180 секунд, а не час.** `IPC_REQUEST_TIMEOUT_SEC = 180.0`

   семафор-слот, но остановить чужой поток Python не умеет.
2. **Тост «Критическая ошибка» прилетел через два часа** после записи, к которой
   относился. Ложная атрибуция во времени хуже, чем долгое ожидание: владелец
   получает сигнал о событии, которое давно закрыто.
3. **Цена не ограничена тостом.** Зомби два часа удерживал MLX-локи. В логе рядом:
   `handle_ping(): count_active_items() лок занят другим держателем` (пять раз за
   час) и `conductor: would evict brain (pressure, streak=6…18)`.

### Почему внутренний watchdog не спас

`MLX_TRANSCRIBE_TIMEOUT_SEC = 45.0` и `MLX_CRASH_RECOVERY_ENABLED = True`
(`core/config.py:643,647`) уже ограничивают **каждый** вызов
`mlx_whisper.transcribe`. Значит час прошёл **вне** watchdog. Кандидаты:
захват `mlx_lock()` (RLock **без таймаута**, `engine.py:2762`), загрузка модели
до вызова, subprocess-сессия GigaAM. Данная волна корень не устраняет — она
ограничивает **последствие** (см. §8 «Не-цели»).

## 2. Настоящий дефект

`TRANSCRIBE_TIMEOUT_SEC = 3600` (`core/config.py:175`) — константа, не зависящая
ни от длительности аудио, ни от того, ждёт ли её живой человек. Применяется
одинаково в трёх местах:

| Место | Роль |
|---|---|
| `engine.py:1923` | multipass-retry по низкой уверенности |
| `engine.py:2503` | адаптеры (GigaAM, Parakeet, SenseVoice, WhisperX, Voxtral) |
| `engine.py:2568` | основной каскад whisper |

Связи между 4.7 секундами звука и 3600 секундами бюджета нет никакой.

### Наблюдаемая производительность

Живой замер из комментария `main+HotkeyRecording.swift:737`: «32-секундная
запись → STT 46.17 с». Разложение на постоянную и переменную части:

* холодная загрузка модели ≈ 40 с (не зависит от длительности);
* инференс large-v3 на M4 Max ≈ 0.2× длительности.

Отсюда форма бюджета — **аддитивная**, а не мультипликативная:
`overhead + duration × factor`. Чисто мультипликативная формула (`duration × K`)
на коротком аудио вырождается: 4.7 с × 3 = 14 с, чего не хватает даже на
загрузку модели.

## 3. Цели

1. Бюджет попытки STT масштабируется от длительности аудио.
2. Интерактивный путь (диктовка, быстрая заметка, REST с `deadline_sec`)
   получает более жёсткий бюджет, чем пакетный (импорт, bulk-reprocess, rescue).
3. Исчерпание бюджета называет **настоящую** причину, а не подменяет её
   сообщением про недоступное облако.
4. Абандоненный поток умирает за десятки секунд, а не за два часа.

Контрольная точка: на аудио инцидента (4.71 с, интерактивный путь) абандоненный
поток живёт **≈ 416 с** вместо 7184 с — сокращение в ~17 раз.

Считать «104 с вместо 3600 с» было бы нечестно: 104 с — бюджет ОДНОЙ попытки, а
поток проходит каскад (GigaAM → whisper) и затем multipass
(`STT_MAX_RETRIES=2`). Без дедлайна на весь запрос жизнь зомби равна **сумме**
бюджетов попыток. Поэтому интерактивный путь получает дедлайн (§4.6), и 416 с —
это дедлайн, а не бюджет попытки.

## 4. Архитектура

### 4.1 Новый модуль `KrabEar/core/stt_budget.py`

```python
@dataclass(frozen=True)
class STTBudget:
    profile: str                       # "interactive" | "batch"
    deadline_monotonic: float | None   # абсолютный дедлайн запроса

_current: ContextVar[STTBudget | None] = ContextVar("stt_budget", default=None)

@contextmanager
def stt_budget_scope(profile: str, deadline_sec: float | None = None): ...
def current_profile() -> str                      # "interactive", если не задан
def remaining_sec() -> float | None               # None → дедлайна нет
def resolve_attempt_timeout_sec(audio_duration_sec, settings_get) -> float
def budget_exhausted(min_useful_sec: float) -> bool
```

**Почему `ContextVar`, а не альтернативы:**

* Поле объекта (`self._budget`) исключено: `AudioEngine` — один экземпляр на все
  IPC-треды (`Transcriber.__init__`, `transcriber.py:46`). Per-request состояние
  в общем объекте = last-writer-wins гонка; кодекс называет этот класс прямо.
* Новый kwarg в `_transcribe_with_fallback` исключён: на `engine.py:1397` стоит
  явный комментарий, что тест-дабли мокают эту сигнатуру фиксированно, и именно
  поэтому `single_pass` пробрасывается условно. Ещё один такой параметр удвоит
  хрупкость.
* `ContextVar` изолирован по треду и не наследуется новыми тредами.

🔴 **Тред, в котором открывается scope, обязан быть тем же, в котором работает
STT.** Внутренние пулы `engine.py` безопасны: там читающая сторона —
`future.result(timeout=…)` в вызывающем треде, а в worker уходит только сам
инференс. Но **внешние** пулы ломают это: `rest_server.py:1781` делает
`_pool.submit(deps.transcriber.transcribe, …)`, то есть вся цепочка исполняется
в свежем worker-треде. Scope, открытый во Flask-треде на `:1746`, там не виден —
engine прочитал бы дефолт без дедлайна, и §6 оказалась бы мёртвой.

Правило для всех точек §5: scope открывается **внутри** вызываемого объекта,
а не вокруг `submit`. Для REST это тонкая обёртка:

```python
def _transcribe_with_budget(path, **kw):
    with stt_budget_scope("interactive", deadline_sec=_transcribe_timeout_sec,
                          settings_snapshot=_snapshot):
        return deps.transcriber.transcribe(path, **kw)

_future = _pool.submit(_transcribe_with_budget, _transcribe_path, **_transcribe_kwargs)
```

IPC-путь работает и без обёртки, но по совпадению: `handle_request` сам
исполняется в backstop-пуле (`ipc_server.py:303-310`), то есть scope и чтения
оказываются в одном треде. Полагаться на это совпадение нельзя — правило
«scope внутри callable» применяется единообразно, и его проверяет
runtime-тест §10.13, а не AST.

### 4.2 Формула

```
budget  = overhead_sec + duration_sec * factor(profile)
budget  = min(budget, max_sec(profile))
attempt = min(budget, remaining_sec())              # если дедлайн задан
attempt = max(attempt, _MIN_USEFUL_ATTEMPT_SEC)     # нижний кламп, см. ниже
```

Нижний кламп обязателен: без него остаток дедлайна, ушедший в минус, дал бы
`future.result(timeout=-x)` — мгновенный `TimeoutError`, неотличимый от
настоящего зависания (и, до §4.6, отравляющий блэклист). Вместо этого попытка
с бесполезным остатком вообще не сабмитится (§7).

Значения настроек **снимаются один раз при входе в scope** и живут в
`STTBudget`, а не читаются на каждой попытке. Причина не в производительности:
REST-процесс создаёт `AudioEngine(skip_gigaam_warmup=True)` без `settings_get`
(`rest_server.py:808`), поэтому `engine._settings_get` там — `lambda k, d: d`
(`engine.py:470`), и любое чтение настроек из engine в REST вернуло бы хардкод.
Снапшот берётся на стороне вызывающего, у которого доступ к настройкам есть, —
иначе пять настроек §9 были бы в REST декоративными.

`duration_sec is None` (длительность определить не удалось) → `budget = max_sec`
профиля: fail-open внутри профиля, но не в час на интерактивном пути.

### 4.3 Где считается длительность

Внутри `_transcribe_with_fallback_impl` по `chain_audio_data`:
`ndarray` → `len / 16000`; путь к файлу → `soundfile.info(...).duration` в
`try/except` (мягкий fallback на `None`).

Расчёт именно здесь, а не на входе `transcribe()`, потому что chunked-путь
(`transcribe_chunked`, включается `STT_STREAMING_ENABLED`, по умолчанию `False`)
подаёт в каскад уже нарезанный кусок — при таком размещении он бесплатно
получает бюджет на чанк. При расчёте на входе каждый из ~100 чанков часового
файла получил бы часовой бюджет.

### 4.4 Проверка формулы на дефолтах

`overhead=90`, `interactive_factor=3.0`, `interactive_max=1800`,
`batch_factor=6.0`, `batch_max=3600`:

| Аудио | Реально ≈ 40 + 0.2×dur | Интерактив | Запас | Батч |
|---|---|---|---|---|
| 4.71 с (инцидент) | 41 с | **104 с** | 2.5× | 118 с |
| 32 с (живой замер 46.17 с) | 46 с | 186 с | 4.0× | 282 с |
| 60 с | 52 с | 270 с | 5.2× | 450 с |
| 5 мин | 100 с | 990 с | 9.9× | 1890 с |
| 52 мин (прецедент 2026-08-05) | 664 с | 1800 с (потолок) | 2.7× | 3600 с |
| 1 час | 760 с | 1800 с (потолок) | 2.4× | 3600 с (потолок) |

Ни одна строка не обрывает работу, которая сегодня успевает; минимальный запас
2.4×. Величина `overhead` выбрана 90, а не 45 (= замеренная холодная загрузка):
в самом инциденте система была под memory pressure (`conductor: would evict
brain (pressure, streak=18)`), а загрузка модели с диска под нагрузкой
растягивается кратно. При `overhead=45` короткое аудио получило бы запас 1.4× —
недостаточно, чтобы отличить зависание от медленной загрузки.

### 4.5 Изменение относительно выбранного числа 180 с

В диалоге был выбран интерактивный потолок 180 с. Оставить его **жёстким
потолком** нельзя: 52-минутная диктовка (прецедент 2026-08-05, волна
recording-duration watchdog) требует ≈ 664 с и была бы оборвана. Число 180
сохраняется по существу — формула выдаёт ≈ 186–270 с ровно для типичной
диктовки 32–60 с, то есть для того случая, ради которого оно и называлось.
Потолок 1800 с работает только как защита от абсурда.

Отдельно: интерактивный бюджет **не** ограничивается сверху клиентским
таймаутом Swift (120 с, `main+HotkeyRecording.swift:732`) и backstop-ом (180 с).
После их истечения backend продолжает и сохраняет результат в историю;
обрыв бюджетом на 110–180 с уничтожил бы этот результат — регрессия хуже
исходного дефекта.

### 4.6 Дедлайн запроса

Бюджет попытки без дедлайна на запрос не решает задачу: каскад из двух моделей
плюс multipass (`STT_MULTIPASS_ENABLED=True`, `STT_MAX_RETRIES=2`,
`config.py:269,273`) складывает бюджеты. Поэтому оба профиля получают дедлайн:

```
deadline_sec = budget * request_attempts_factor        # default 4.0
```

Множитель 4.0 подобран так, чтобы каскад успел то, ради чего он существует:
GigaAM-попытка (с floor §4.7 — 200 с) + whisper (104 с) + один multipass (104 с)
= 408 с < 416 с. При множителе 2.5 fallback на whisper был бы обрублен, то есть
волна чинила бы таймаут ценой качества распознавания.

### 4.7 Бюджет-таймаут не помечает модель сломанной

🔴 Самая опасная связь этой волны. Сегодня **любой** `TimeoutError` пишет модель
в `_unavailable_models` (`engine.py:1964` multipass, `:2551` адаптеры через
широкий `except Exception`, `:2596` whisper) с TTL 300 с
(`_UNAVAILABLE_MODEL_TTL_SEC`, `engine.py:244`).

С порогом 3600 с это срабатывало исключительно редко. С порогом 104 с частота
вырастает на порядки — и легитимно медленная холодная загрузка под memory
pressure (та самая, ради которой `overhead` поднят до 90) начинает выглядеть как
«модель сломана». Обе локальные модели попадают в блэклист на пять минут →
следующая диктовка владельца через десять секунд идёт сразу в Remote →
`no_api_key` → **тост «Критическая ошибка», то есть ровно тот симптом, который
волна чинит.** Без этого различения волна становится генератором собственного
бага.

Поэтому вводится `BudgetExhaustedTimeout` (подкласс `TimeoutError`, чтобы
существующие `except` не сломались). Обработчики таймаута различают два случая:

| Причина | Блэклист | Смысл |
|---|---|---|
| watchdog MLX, GPU stall, крах воркера | пишем | модель действительно нездорова |
| исчерпан бюджет запроса | **не пишем** | нездоров запрос, а не модель |

### 4.8 Нижняя граница для adapter-ветки

У адаптеров есть собственные внутренние таймауты: GigaAM — 120 с на shortform и
180 с на загрузку модели (`core/pipeline/stt_gigaam.py:95`), 960 с на longform
(`:863`). Интерактивный бюджет для короткого аудио (104 с) оказался бы **меньше**
внутреннего: внешний `future.result` сработал бы первым, модель ушла бы в
блэклист, а subprocess продолжал бы грузить ~1.5 ГБ на GPU до своего таймаута —
осиротевший тяжёлый ресурс.

Поэтому adapter-ветка (`engine.py:2503`) применяет floor
`_ADAPTER_MIN_BUDGET_SEC = 200.0` — выше обоих внутренних порогов первой
попытки. Whisper-ветка floor не нужна: её внутренний watchdog 45 с меньше любого
бюджета.

🔴 **Встречи обязаны быть `batch`.** `meeting_session_service.py:723` завершает
живую встречу через тот же `handle_stop_recording`, то есть попадает в phase_c.
По модели §4.4 двухчасовая встреча требует ≈ 1480 с — запас к интерактивному
потолку 1800 с всего 1.2×, а встреча на 2.5 часа и длиннее обрывалась бы
гарантированно, хотя сегодня успевает. Встречи — главный источник многочасовых
записей, и интерактивным путём они не являются: живой человек результата в этот
момент не ждёт, панель встречи уже показала транскрипт по ходу.

Разделение делается по владельцу поколения записи (R2, allowlist
`dictation`/`meeting`/`quick_capture`) — он уже известен Core на входе в stop и
не требует нового параметра. Owner неизвестен → `interactive` (fail-fast).

Дефолт `interactive` выбран как fail-fast: незалейбленный путь получает
масштабируемый бюджет, а не час. Пакетные пути перечислены явно и покрыты
тестом, который проверяет наличие scope в каждом.

## 6. Связь с REST `deadline_sec` (волна W2c)

Механика не дублируется. `deadline_sec` остаётся тем же полем формы с той же
валидацией (`_resolve_transcribe_deadline_sec`, `rest_server.py:593`, 5–120 с,
мусор → 400). Меняется одно: разрешённое значение (либо дефолт 600 с)
передаётся в `stt_budget_scope(profile="interactive", deadline_sec=...)`, и
внутренние бюджеты попыток начинают им ограничиваться.

Сегодня внутренний бюджет (3600 с) **больше** внешнего REST-бюджета (600 с) —
конфигурация, в которой внутренний не может сработать никогда: REST отдаст 504 и
завершит процесс раньше. После связывания вложенность становится корректной:
`attempt ≤ request deadline`.

## 7. Поведение при исчерпании

В `_transcribe_with_fallback_impl` перед каждым следующим кандидатом:

```python
if budget_exhausted(_MIN_USEFUL_ATTEMPT_SEC):   # 5.0 с
    logger.warning("STT: бюджет запроса исчерпан — каскад прерван на %s", model_name)
    break
```

`_MIN_USEFUL_ATTEMPT_SEC = 5.0`: попытка с остатком меньше пяти секунд заведомо
бесполезна (одна загрузка модели дольше), но занимает GPU.

После прерывания — исходная ошибка «Все доступные STT-движки вышли из строя»
с указанием исчерпанного бюджета. Подмена причины сообщением про облако уже
закрыта в PR #1953 (`_remote_stt_retry_configured`); эта волна её не трогает.

Та же проверка ставится в `_maybe_multipass_retry` перед каждым кандидатом —
иначе под коротким REST-дедлайном multipass сабмитил бы попытки с нулевым
остатком.

Новый код ошибки в `ERROR_REGISTRY`: `stt.budget_exhausted`, severity `error`.

**Наблюдаемость.** При разборе этого инцидента не хватало ровно двух величин —
какой бюджет действовал и какой длительности было аудио. Поэтому:

* при входе в scope — одна INFO-строка: профиль, длительность, бюджет, дедлайн;
* `engine.py:2593` сегодня печатает `settings.TRANSCRIBE_TIMEOUT_SEC` в
  сообщении о таймауте. После перехода на вычисленный бюджет эта строка стала бы
  называть **не то число, которое сработало**, — правится в той же волне
  (иначе следующий разбор начнётся с ложного следа);
* сообщение таймаута различает исчерпание бюджета и отказ модели (§4.7).

## 8. Не-цели

* **Корень зависания не устраняется.** Почему `_transcribe_model` висел час,
  несмотря на 45-секундный watchdog, — отдельная задача (главный подозреваемый:
  `mlx_lock()` без таймаута, `engine.py:2762`; тот же класс, что инцидент
  2026-08-13 с превью-воркером). Эта волна ограничивает последствие. Записать
  в `docs/NOW.md` отдельной строкой.
* **Абандоненный поток не прерывается принудительно** — Python этого не умеет.
  Волна сокращает его жизнь, не отменяет.
* **Асинхронный путь для длинных диктовок** (чтобы Swift не отваливался на 120 с)
  — вне объёма.
* `TRANSCRIBE_TIMEOUT_SEC` **не удаляется**: остаётся дефолтом
  `stt_timeout_batch_max_sec` и последним рубежом при недоступном `settings_get`.

## 9. Настройки

`DEFAULT_SETTINGS` (`core/config.py:821`) + `_RANGE_FIELDS`
(`backend/settings_validator.py:76`) — оба обязательны по правилу wave-34:
любой новый временной тюнинг клампится, иначе `set_settings` с мусором
или NaN уводит поведение в непредсказуемое.

| Ключ | Диапазон | Дефолт |
|---|---|---|
| `stt_timeout_overhead_sec` | 5.0 – 600.0 | 90.0 |
| `stt_timeout_interactive_factor` | 0.5 – 60.0 | 3.0 |
| `stt_timeout_batch_factor` | 0.5 – 120.0 | 6.0 |
| `stt_timeout_interactive_max_sec` | 30.0 – 7200.0 | 1800.0 |
| `stt_timeout_batch_max_sec` | 60.0 – 21600.0 | 3600.0 |
| `stt_timeout_request_attempts` | 1.0 – 10.0 | 4.0 |

Нижние границы факторов (0.5) и overhead (5.0) не позволяют выставить бюджет,
при котором ни одна транскрибация не успевает, — тот же класс защиты, что у
`rt_silence_check_sec`.

## 10. План тестов (TDD, каждый RED до кода)

`KrabEar/tests/test_stt_timeout_budgets_2026_08_26.py`:

1. `resolve_attempt_timeout_sec` на аудио инцидента (4.71 с, `interactive`)
   возвращает ≈ 104 с, **не** 3600 — регрессия-тест инцидента.
2. Профиль `batch` на том же аудио даёт больший бюджет, чем `interactive`.
3. Потолок профиля применяется (52 мин → ровно `interactive_max`).
4. `duration=None` → бюджет равен потолку профиля, не бесконечности.
5. `deadline_sec` урезает бюджет ниже расчётного.
6. `remaining_sec()` монотонно убывает; после дедлайна `budget_exhausted` → True.
7. Изоляция между тредами: два треда с разными профилями не видят чужой.
8. Сброс токена: после выхода из scope профиль возвращается к дефолту, в том
   числе при исключении внутри.
9. Клампы: `set_settings` с NaN / отрицательным / 10**9 приводится к границам.
10. AST-контракт: ни одна из трёх точек `engine.py` не ссылается на
    `settings.TRANSCRIBE_TIMEOUT_SEC` напрямую — сиблинги не разойдутся снова
    (приём из PR #1953). Привязка **к именам функций**, не к номерам строк:
    номера дрейфуют, и тест начнёт проверять чужой код молча.
11. AST-контракт: каждая точка из таблицы §5 обёрнута в `stt_budget_scope`.
12. Каскад прерывается при исчерпанном дедлайне и не пробует следующего
    кандидата (фейковый каскад, счётчик попыток).
13. **Runtime-пропагация через внешний пул** (закрывает дыру AST-теста §10.11,
    который прошёл бы и при scope во Flask-треде): фейковый transcriber читает
    `current_profile()`/`remaining_sec()` из worker-треда REST-роута и получает
    заданные значения, а не дефолт.
14. Бюджет-таймаут **не** пишет модель в `_unavailable_models`; watchdog-таймаут
    (MLX GPU stall) — пишет. Регрессия §4.7: без этого теста волна порождает
    собственный баг.
15. Финализация встречи (`owner == meeting`) получает профиль `batch`, диктовка
    того же phase_c — `interactive`.
16. Нижний кламп: при отрицательном остатке дедлайна попытка не сабмитится
    вовсе, `future.result` не зовётся с отрицательным таймаутом.
17. Adapter-floor: интерактивный бюджет короткого аудио, поданный в
    adapter-ветку, не меньше `_ADAPTER_MIN_BUDGET_SEC`.
18. Снапшот настроек: engine с `settings_get = lambda k, d: d` (как в
    REST-процессе) всё равно получает значения из `STTBudget`, а не дефолты.
