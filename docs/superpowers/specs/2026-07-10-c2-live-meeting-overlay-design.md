# C2 — Live Meeting Overlay (живая панель встречи)

Дата: 2026-07-10. Статус: одобрено владельцем (брейнсторм в терминале + visual companion).
Происхождение: `docs/ROADMAP-2026H2.md` §3.4, кандидат C2. Размер: L, три подволны C2a/C2b/C2c.

## 0. Суть

Сегодня «встреча» в Krab Ear существует только постфактум: `get_meeting_report {id}` строит
отчёт (резюме + action items + спикеры) по УЖЕ завершённой записи из истории. C2 добавляет
живую часть: пока встреча идёт, плавающая панель показывает проявляющиеся action items,
чипы спикеров со временем говорения и хвост растущего транскрипта. После «Стоп» — обычный
финальный отчёт, который пересчитывает всё начисто (live-данные — черновик).

Решения владельца (2026-07-10): скоуп — **полная версия** (items + транскрипт + спикеры-лайт);
активация — **кнопка «Встреча» + повышение идущей записи на лету**; UI — **отдельная плавающая
панель** (вариант B из макетов).

## 1. Факты разведки, определившие дизайн

(read-only агент, 2026-07-10; все file:line сверены)

- **Диаризация строго batch**: `engine.py::_maybe_run_diarization` принимает только путь к
  готовому файлу, вызывается из stop_recording phase C; инкрементального пути нет. Бенчи
  (M4 Max, MPS): ~9-10.5с на прогон, причём 2.2-секундный клип = те же ~9с (фиксированный
  оверхед); CPU-фоллбэк — 7.3× длительности записи. Задокументирована история утечки памяти
  при повторных прогонах (обязательный gc+empty_cache: `engine.py:3292-3300`).
- **Полного растущего live-транскрипта в проекте НЕТ нигде**: `RealtimePartialTranscriber`
  ре-транскрибирует скользящее хвостовое окно 8с (не дельту, не накопление);
  `get_recording_state.preview_text` — хвост 12с, обрезка 900 символов.
- **`ActionItemsExtractor`** — LLM (LM Studio, конфиг `LLM_BASE_URL/LLM_MODEL`), вход — весь
  текст целиком, состояния между вызовами нет; тёплый вызов ~9-10с (прокси-бенч rewriter).
- **🔴 Metal-констрейнт**: одновременный активный инференс LM Studio + нашего MLX = зависание
  Metal GPU до ребута (задокументированный урок). Во время записи mlx-whisper молотит партиалы
  каждые 3с → любые LLM/диар-вызовы во время встречи требуют жёсткой сериализации.
- **Спящий voice-fingerprint API**: `SpeakerManager.compute_embedding/register_speaker/
  find_matching_speaker` (512-dim, cosine) — написан, выключен (`VOICE_FINGERPRINT_ENABLED=False`),
  ни разу не вызывался из пайплайна. Метки pyannote анонимны и НЕ стабильны между прогонами.
- **Архитектурный образец инкрементального live-анализа**: `RealtimeSilenceFilter` — курсор
  `_checked_up_to_sec`, анализ только нового хвоста, накопление состояния, событие + sync-геттер.
- **`get_meeting_report`** — чистая оркестрация над готовым `HistoryItem` (summary + items +
  группировка `speaker_turns`); диаризацию не считает, на незавершённую запись не работает.
- **UI-прецеденты**: `RealtimeOverlayController` — capped HUD 640×180, click-through, для списка
  не годится; `ConversationStatusOverlay` (Волна 3c) — свежий образец floating-панели с
  off-screen guard; рендер action items уже есть в `HistoryPanelController+ActionItems.swift`
  (пост-хок секция).

## 2. Архитектура (Подход 1 из брейнсторма)

### 2.1 `backend/meeting_session_service.py` — MeetingSessionService

18-я сервис-экстракция по устоявшемуся паттерну (конструктор: store + коллабораторы; методы
`handle_*`; проводка в `_build_dispatch_table`). Сервис пассивен, пока встреча не запущена —
обычная диктовка хоткеем не затрагивается вообще.

IPC (все три — privacy-гейт по стандартному паттерну, transcript-derived данные):
- `meeting_start {}` → `{ok, promoted: bool, started_at}`. Записи нет → стартует запись
  (делегат в `RecordingCoreService.handle_start_recording`) и вешает live-сессию; запись уже
  идёт → «повышение на лету»: сессия вешается сейчас, курсор аккумулятора = текущая позиция
  (начало добирается финальным отчётом). Повторный вызов при активной сессии → no-op `{ok:true}`.
  Privacy mode ON → отказ `{ok:false, skipped:"privacy_mode"}`.
- `meeting_stop {}` → `{ok, item_id?}`. Гасит live-сессию, останавливает запись обычным
  stop-путём (финальный транскрипт + ПОЛНАЯ диаризация + history item как сегодня). Если запись
  остановили в обход (хоткей/UI) — сервис узнаёт через подписку на stop и финализируется сам.
- `get_meeting_live_state {}` → `{ok, active, started_at, promoted, transcript_len,
  transcript_tail (последние ~600 симв.), items: [...], speakers: [{label, talk_sec,
  last_active_ts}], degraded: {llm: bool, diarization: bool}, last_updated_ts}`.
  Не-активная сессия → `{ok:true, active:false}`.

### 2.2 Единый GPU-слот

Один воркер-тред с очередью задач; инвариант: **на Metal не больше одной тяжёлой операции
одновременно** (в рамках meeting-механики; партиалы — см. паузу ниже).

| Задача | Такт (default) | Работа |
|---|---|---|
| CHUNK_STT | 25с | `snapshot_range(cursor, now)` → STT чанка (mlx_lock внутри engine) → конкатенация в аккумулятор |
| ITEMS_LLM | 60с, адаптивно ↑ | весь накопленный текст → `ActionItemsExtractor.extract()` → список ЗАМЕЩАЕТСЯ |
| DIAR_WINDOW | 120с | `snapshot_range(now-90с, now)` → temp WAV → диаризация окна → эмбеддинги → сшивка |

- На время ITEMS_LLM (кросс-процессный LM Studio) И DIAR_WINDOW (torch/MPS) —
  `RealtimePartialTranscriber.pause()` → `resume()`; новые методы, вызовы под существующим
  `_rt_lock` (конвенция recording lifecycle lock). Причина: Metal-констрейнт из §1 для LLM;
  для диаризации — сегодня она НИКОГДА не работает одновременно с партиалами (всегда после
  остановки записи), meeting-режим впервые совместил бы MPS-инференс с MLX-партиалами в одном
  процессе — не открываем этот класс риска, просто паузим (диар-окно ~9-12с раз в 2 мин).
- После каждого DIAR_WINDOW — обязательный `gc.collect()+torch.mps.empty_cache()` (паттерн §1).
- ITEMS_LLM интервал адаптивен: `max(60, len(text)/120)` секунд — на длинной встрече вызовы реже.
- Пропуск такта: если задача не успела до следующего тика своего типа — тик пропускается
  (без очереди-лавины), выставляется degraded-флаг соответствующего типа.
- **Brain-lease**: `meeting_start` захватывает lease LM Studio (`backend/brain_lease.py`) на всю
  встречу, `meeting_stop` возвращает поведение к обычному циклу записи. Семантика: во время
  встречи мозг занят Krab Ear; Main Krab уступает. Это же снижает риск кросс-процессной драки
  за Metal. ВАЖНО: обычный recording-цикл сегодня НАОБОРОТ освобождает lease на время записи
  (`recording_core_service.py`) — meeting-сессия сознательно перекрывает это поведение, и
  восстановление обычной семантики при завершении встречи — обязательный тест.

### 2.3 TranscriptAccumulator (внутри сервиса)

- Новый метод `AudioRecorder.snapshot_range(from_sec, to_sec) -> np.ndarray` — потокобезопасный
  срез сырого буфера по диапазону (сосед существующего `snapshot_audio(max_duration_sec)`,
  O(диапазона), без полной конкатенации).
- Курсор `transcribed_up_to_sec` (образец — silence-фильтр): куски НЕ пересекаются → полный
  транскрипт = чистая конкатенация, дедупа нет по построению. Партиалы (HUD-строка) не трогаем —
  живут параллельно как сейчас.
- Хранение: в памяти сессии (list[str] + суммарная длина); на диск не пишется (privacy: живёт
  не дольше записи; финальный текст всё равно строится обычным stop-путём).

### 2.4 LiveItemsExtractor (внутри сервиса)

- Тик: если аккумулятор вырос менее чем на 200 символов с прошлого вызова — пропуск (экономия LLM).
- Вход — ВЕСЬ накопленный текст; выход — полный список, старый замещается (LLM дедупит по
  построению; никакого инкрементального merge в v1).
- Существующий `ActionItemsExtractor` без изменений (его circuit breaker — наш degraded-сигнал).
- 30-мин встреча ≈ 4-6к слов — в контекст `gemma-4-e4b-it-mlx` помещается с запасом.

### 2.5 LiveSpeakerTracker (внутри сервиса) — подволна C2b

- Тик: окно последних 90с → temp WAV 16кГц mono (в tmp-поддиректории data_dir, удаляется в
  `finally` каждого тика) → новый узкий хелпер `engine.diarize_window(path)` (переиспользует
  загрузку/кэш пайплайна + gc-паттерн; НЕ трогает `_maybe_run_diarization`).
- Для каждого сегмента окна: `SpeakerManager.compute_embedding(wav, start, end)` → сравнение с
  **сессионным** реестром (cosine, порог из настройки, default 0.72): совпал → тот же «Спикер N»,
  нет → новый «Спикер N+1». Глобальный `VOICE_FINGERPRINT_ENABLED` НЕ включаем — API зовётся
  напрямую, реестр живёт только в памяти сессии (v1: без кросс-сессионной идентичности).
- Накопление `talk_sec` по спикерам; чипы в UI честно показывают «обновлено N мин назад».
- Известные ограничения (принято владельцем): стыки окон режут реплики; короткие реплики могут
  теряться; похожие голоса могут склеиться. Финальный отчёт пересчитывает спикеров начисто
  полной диаризацией — live-чипы это черновик.

#### §2.5a Амендмент C2b (2026-07-16, живой микробенчмарк + сверка с кодом C2a)

Брейнсторм C2b (владелец: скоуп без изменений, документация — амендментом сюда).
Микробенчмарк на реальном железе (M4 Max, свободный GPU, синтетическая встреча
Milena+Yuri 118с, 16 кГц mono; `.venv_krab_ear`, torch 2.11 + pyannote 4.0.x, MPS):

| Окно | Диаризация (медиана warm, 3 прогона) | Сегментов | Спикеров |
|---|---|---|---|
| 30с | 1.5с (1.3–2.4) | 6 | 2 ✓ |
| 60с | 3.9с (3.5–3.9) | 13 | 2 ✓ |
| 90с | 6.2с (5.8–8.1) | 18 | 2 ✓ |

Загрузка pipeline из кэша — 1.4с; ХОЛОДНЫЙ первый инференс свежего процесса на 90с — ~15с
(skip-tick это переживает штатно: перепланирование от завершения). Прежняя цифра «~9-10.5с
фиксированного оверхеда» подтверждена как артефакт GPU-contention, но и «0.2с/5с» на длинные
окна не масштабируется — реальный скейл ~0.05-0.07 с/с аудио.

**Дельты дизайна по результатам (§2.5 читать с этими поправками):**

1. **Эмбеддинги — из `DiarizeOutput.speaker_embeddings`, НЕ из `SpeakerManager.compute_embedding`.**
   Живая проверка: `pyannote/embedding` (зашит в SpeakerManager) — gated-модель, HF TOS не принят,
   прод получил бы 403 на первом же вызове. При этом установленный pyannote 4.x возвращает
   центроиды спикеров окна БЕСПЛАТНО из самого диар-прогона: `DiarizeOutput.speaker_embeddings`,
   shape (n_local_speakers, 256) — wespeaker-voxceleb-resnet34-LM, уже в кэше как часть
   diarization-3.1. Один вызов на окно даёт и сегменты, и эмбеддинги; отдельного
   эмбеддинг-прохода в тике нет вообще. `engine.diarize_window(path)` возвращает
   `{segments: [...], speaker_embeddings: {label: [256 floats]}}`. Спящий voice-fingerprint API
   не трогаем совсем (не только не включаем — теперь и не вызываем).
2. **Сшивка** — cosine центроида окна против сессионного реестра (порог из
   `meeting_speaker_match_threshold`, default 0.72, как утверждено); реестр хранит скользящее
   среднее центроида по спикеру. Локальные метки окна анонимны и нестабильны — маппинг только
   через эмбеддинги.
3. **Дефолт тика = 90с (было 120с), окно = 90с** — при цене тика ~6с покрытие становится
   сплошным (тик == окно, без 30-секундных «слепых зон» между окнами, где talk_sec терялся).
   Диапазоны настроек не меняются; `_job_interval` для DIAR_WINDOW читает
   `meeting_diar_interval_sec` вместо хардкода 120.0.
4. **Фикс нестыковки C2a** (разведка подтверждена по коду): `handle_meeting_start` заполняет
   `_next_due` только для CHUNK_STT и ITEMS_LLM — DIAR_WINDOW не планируется вовсе. C2b добавляет
   его в расписание (и в ветку исполнителя `_run_due_job_once`) СТРОГО за рубильником
   `meeting_live_speakers_enabled` (default true): выключен → поведение байт-в-байт как C2a.
5. Пауза партиалов на время DIAR_WINDOW-тика (~6-8с MPS-burst) — подтверждена бенчмарком,
   остаётся как в §2.2 (паттерн `pause_realtime_partials`/`resume` уже живёт в `_job_items_llm`).

### 2.6 События и доставка в UI

- EventBus (IPC-процесс): `meeting.transcript_appended {chunk_text, total_len}`,
  `meeting.items_updated {items}`, `meeting.speakers_updated {speakers}`,
  `meeting.finalizing {}`, `meeting.finished {item_id}`.
- Доставка агенту: SSE `/v1/events` REST-процесса — события доезжают через event-мост Волны 2
  (первый настоящий потребитель конвенции «новые события агент слушает через SSE»).
- Фоллбэк (урок 2-EventBus): панель поллит `get_meeting_live_state` раз в 5с, если SSE молчит
  >15с при активной сессии; тот же вызов — при открытии панели посреди встречи.

  `.nonactivatingPanel`, draggable, позиция в UserDefaults + off-screen guard (паттерн
  ConversationStatusOverlay/RealtimeOverlayController — ≥80% пересечения с видимым экраном).
- Раскладка (вариант B): header — ⏺ таймер + «Встреча»; ряд чипов спикеров (имя + talk time +
  возраст данных); скролл-список items с типами (задача/решение/вопрос — маппинг на типы

- Глифы: только уже установленные в кодовой базе / SF Symbols (глиф-гейт AGENT-J/M обязателен

- Завершение: кнопка → `meeting_stop` → панель в состоянии «Финализирую…» → по `meeting.finished`
  (или poll) открывается существующий `MeetingReportViewController` с пост-хок отчётом.
- Точки входа: пункт меню-бара «Встреча» + кнопка в панели истории. Обе: сессии нет → старт;
  запись идёт без сессии → «повысить»; сессия активна → показать панель.
- Дисциплина: IPC строго off-main (AGENT-3), никаких `runModal()`, KrabEarTheme-токены.

#### §2.7a Амендмент C2c (2026-07-16, брейнсторм перед реализацией панели)

Решения владельца: канал — **SSE + poll по §2.6** (подтверждено при мёртвом мосте; пререквизит
закрыт тут же: `KRAB_EAR_DATA_DIR` добавлен в rest-plist, мост живой — `state: up`, коммит
`87ae84db`); rest.plist-фикс — отдельным коммитом, не гейтит панель.

Привязки §2.7 к реальным прецедентам кодовой базы (для плана):

1. **Панель**: паттерн `ConversationStatusOverlay` — `.nonactivatingPanel/.hudWindow/.utilityWindow`,
   `level = .floating`, `isMovableByWindowBackground` + pan-gesture, позиция в UserDefaults
   (`KrabEar_MeetingLivePanelPosition`), off-screen guard ≥80% пересечения c visibleFrame.
2. **SSE**: общий `SSESessionDelegate` (как `LiveSubtitlesOverlay`), endpoint
   `/v1/events` REST-процесса, обработка строк на `@MainActor`. У LiveSubs авто-реконнекта
   нет — для панели фоллбэк ИЗ §2.6 и есть реконнект: SSE молчит >15с при активной сессии →
   poll 5с + пересоздание SSE-стрима. Разовый poll `get_meeting_live_state` при каждом
   открытии панели (initial state).
3. **Точки входа**: пункт меню-бара «Встреча» (`rebuildStatusMenu` + `@objc`-хендлер в
   `main+MeetingPanel.swift`) и `ThemeSecondaryButton` в `topActionsRow` панели истории.
   Обе: `meeting_start` идемпотентен на backend-стороне (already_active/promoted) —
   Swift-логика тонкая: вызвал → показал панель.
4. **Финализация**: `meeting_stop` → «Финализирую…» → `meeting.finished {item_id}` (или poll
   показал inactive) → `get_meeting_report {id}` → существующий `MeetingReportViewController`
   в ОТДЕЛЬНОМ titled-окне (сейчас умеет только sheet поверх окна истории — добавляется
   standalone-презентация; sheet-путь `+MeetingMode.swift` не меняется).
5. **Граница труда**: поведение/раскладка на KrabEarTheme-токенах — Claude/Sonnet;
   визуальная полировка панели — отдельный agy/Gemini-бриф ПОСЛЕ мержа поведения
   (в скоуп волны не входит). Глифы — только SF Symbols, уже встречающиеся в кодовой базе.
6. **IPC из панели** — строго off-main (канон `+ExportSelection.swift`:
   `DispatchQueue.global` → `ipcClient.call` → `nonisolated(unsafe)` → `main.async`).

`meeting_chunk_stt_interval_sec` (25, 10–120), `meeting_items_interval_sec` (60, 30–600),

## 3. Деградации и ошибки

- **LLM недоступен/circuit open** → items замирают, `degraded.llm=true`, бейдж на панели;
  встреча продолжается.
- **Диар-тик не успел/упал** → пропуск, `degraded.diarization=true`, чипы стареют с меткой.
- **Privacy mode включили посреди встречи** → live-обработка останавливается (слот дренируется),
  события прекращаются, `get_meeting_live_state` возвращает gated-ответ; запись продолжается
  по обычным правилам privacy.
- **Финальный пост-хок extract упал** → в финальный отчёт подставляются последние live-items
  (деградация лучше пустоты); помечается в отчёте.
- **Крах backend посреди встречи** → сессия не переживает (v1), панель показывает ошибку через
  существующий error-toast путь; запись — судьба как у обычной записи сегодня.
- **Panel закрыта юзером** → сессия ПРОДОЛЖАЕТСЯ (панель переоткрывается из меню с полным
  состоянием через `get_meeting_live_state`).

## 4. Тестирование

- **Юниты**: курсор аккумулятора (стыки без дыр/перекрытий, промоушен посреди записи);
  сериализация GPU-слота (fake-задачи: никогда две одновременно, приоритеты, пропуск тактов);
  pause/resume партиалов вокруг LLM-вызова (source-contract + unit); замещение items;
  сшивка спикеров на fake-эмбеддингах (совпадение/новый/порог); brain-lease перекрытие и
  восстановление обычной семантики после `meeting_stop`.
- **Dispatch/privacy**: стандартные dispatch-invariant тесты на 3 новых метода + privacy-гейт
  тесты (включая mid-meeting включение privacy).
- **Source-contract (Swift)**: панель реально подписана на SSE + poll-фоллбэк реально взводится;
  `meeting_stop` реально вызывается кнопкой (класс «test-validates-the-hole» под запретом).
- **Живой e2e (обязателен)**: throwaway-backend; синтетическая «встреча двух голосов» генерится
  Silero-тулчейном из 3a (`wake_word_models/train_krab.py`-инфраструктура: два спикера,
  осмысленные RU-фразы с задачами/решениями) → `meeting_start` → события приходят, транскрипт
  растёт, спикеров ровно 2 после сшивки → `meeting_stop` → финальный отчёт как сегодня.
  LLM-часть e2e — при живом LM Studio (ручной гейт), иначе мок.
- **ubuntu-CI**: всё тяжёлое за моками; mlx-masking и teardown-правила CLAUDE.md обязательны.

## 5. Подволны и порядок

1. **C2a — backend-ядро** (M): сервис + IPC + GPU-слот + аккумулятор (`snapshot_range`) +
   items + события + pause/resume партиалов + brain-lease + тесты. Работает без спикеров.
2. **C2b — спикеры-лайт** (M): `diarize_window` + эмбеддинг-сшивка + speakers в state/событиях +
   рубильник. Самый рисковый кусок изолирован; провал C2b не блокирует C2a+C2c.
3. **C2c — Swift-панель** (M): панель + меню/кнопки + SSE/poll + финализация → отчёт.

Релиз: v2.9.0 после C2a+C2c (спикеры могут доехать v2.9.x, если C2b задержится).

## 6. Не-цели v1

- Кросс-сессионная идентичность спикеров («это снова Павел») — API есть, отложено.
- Редактирование/чекбоксы items в live-панели (только копирование) — пост-хок отчёт богаче.
- Эвристический extractor без LLM.
- Перевод live-контента; экспорт live-состояния; выживание сессии при рестарте backend.
- Изменение существующего пост-хок Meeting Mode (он остаётся финальной истиной).
