## 2. F1 — диаризация на короткой диктовке

**Факт** (разведка по коду): на обычном пути транскрибации гейтов по
длительности НЕТ вовсе. `recording_core_service.py:2801` читает
`diarization_enabled` и безусловно тащит его до `pipeline(audio_path)`
(`engine.py:3557`). Единственные существующие гейты — `is_preview` и
отсутствие HF-токена.

**Ключевой факт безопасности**: встречи диаризуются ДРУГИМ путём —
`MeetingSessionService` → `engine.diarize_window()` (`engine.py:3591`),
а не `_maybe_run_diarization()`. Гейт на обычном пути встречи не ломает.

**Прецедент в этом же коде**: `DIARIZED_MIN_DURATION_SEC: float = 120.0`
(`core/config.py:153`) — уже существующий min-duration гейт, но только для
opt-in longform-пути (`DIARIZED_TRANSCRIPTION_ENABLED=False`).

**Решение**: новая настройка `diarization_min_duration_sec` (дефолт **90.0**),
проверяется в `recording_core_service.py` рядом с чтением
`diarization_enabled`. Аудио короче порога → `diarize=False`.

Почему длительность, а не «источник = диктовка»: по длительности гейт
предсказуем и не отнимает диаризацию у легитимных сценариев (запись звонка
хоткеем, импорт файла) — они длиннее. Диктовки владельца — десятки секунд.
Значение настраиваемое: `0` полностью восстанавливает прежнее поведение.

Почему 90, а не 120: живая диктовка инцидента — 42с; типичная диктовка
владельца — 10-60с. 90с оставляет запас, не задевая осмысленные
многоголосые записи.

**Направление отказа**: не смогли прочитать/распарсить длительность →
диаризуем (fail-open в сторону прежнего поведения, не в сторону тихой
потери фичи).

## 3. F2 — превью-воркер не отступает под нагрузкой

**Факт**: `_preview_loop` (`recording_core_service.py:2254`) берёт
`snapshot_audio(max_duration_sec=12.0)` и запускает ПОЛНУЮ
`transcribe_preview` каждые 0.9 секунды нового аудио. Каждый прогон GigaAM
на 12-секундном окне — ~0.85с инференса (живой замер из лога инцидента).
То есть ~65-90% времени записи занято непрерывным инференсом, который
конкурирует с потоком захвата аудио.

`poll_interval` увеличивается ТОЛЬКО при исключениях в snapshot/транскрибации
(`_POLL_BACKOFF = 1.5`, кап `_POLL_MAX = 1.5`). Переполнение аудиобуфера —
не исключение, воркер о нём не знает и продолжает молотить.

**Принцип**: если система не успевает забирать аудио, приоритет — сама
запись. Превью — украшение; терять кадры записи ради него недопустимо.

**Решение**: обратная связь по переполнению.

1. `AudioRecorder` считает переполнения: `_overflow_count` инкрементируется
   там же, где уже логируется `Переполнение аудиобуфера` (`recorder.py:584`),
   и публикуется свойством `overflow_count` (под `self._lock`, как остальные).
   Счётчик обнуляется в `start()` — он про ТЕКУЩУЮ запись.
2. `_preview_loop` перед каждой транскрибацией читает `overflow_count`.
   Вырос с прошлой итерации → это признак, что система не тянет:
   - пропустить транскрибацию этой итерации,
   - увеличить интервал: `preview_backoff_sec = min(preview_backoff_sec * 2, 8.0)`,
     старт с 0.0 (выключен),
   - залогировать один раз на эпизод (не на каждую итерацию — шторм в логе).
3. Переполнений нет N итераций подряд (N=3) → бэкофф плавно снимается
   (делится пополам до 0.0). Не резкий сброс: система могла ещё не остыть.

**Что НЕ делаем**: не выключаем превью совсем и не трогаем `max_duration_sec`
— превью полезно, речь только о поведении под перегрузом.

**Направление отказа**: `overflow_count` недоступен (легаси-фейки рекордера
в тестах, duck-typing) → `getattr(..., 0)`, бэкофф просто никогда не
включается, прежнее поведение.

## 4. Осознанно НЕ в скоупе

- **Дедуп «заиканий» в тексте.** Первая гипотеза (перекрытие чанков)
  ОПРОВЕРГНУТА чтением кода: `AudioChunker._build_chunks` режет строго
  стык-в-стык (`boundaries = [0.0] + split_points + [total_sec]`),
  `merge_results` склеивает через пробел без перекрытий. Дубли —
  следствие выброшенных переполнением кадров (микро-разрывы в аудио →
  RNNT-заикание, усугублено SNR 9 dB). Лечим причину (F2), а не симптом.
- **Необъяснённая аномалия длительности**: в логе 00:19:51 VAD видит
  `total=41.22s`, а GigaAM-чанкер через 15 мс — `duration=70.8s`. Обе
  гипотезы (перекрытие чанкера, неверный `source_sample_rate` в
  `_resample_audio_to_mono_16k`) проверены по коду и НЕ подтвердились
  (ресемплер возвращает массив как есть при `source_rate == 16000`).
  Аудиофайлы инцидента уже удалены после успешной транскрибации —
  ретроспективно не проверить. Требует отдельного контролируемого замера
  (запись через IPC + сверка длины массива с wall-clock). Заведено как
  отдельный вопрос, НЕ решается этой волной и не блокирует её.
- Внешняя нагрузка (чужой тест-сьют, Spotlight) — не наша зона.
