# GigaAM v2 → v3 апгрейд RU-STT (S-M волна)

Дата: 2026-07-20 · Автор: Opus 4.8 (спека + инвестигация) · Статус: draft → execute
Источник: живой бенч 2026-07-20 (§«Итог живого бенча» в сессии), ресёрч свежих MLX STT-моделей.

## 1. Мотивация (доказана живым бенчем)

Прод сейчас: `GigaAM-RNNT v2` (декабрь 2024), `STT_GIGAAM_MODE="rnnt"` → пакет `gigaam==0.1.0`
(PyPI) авто-префиксит в `v2_rnnt`. WER Common Voice RU ~3.8%.

Живой бенч на 5 синтетических RU-сэмплах (бытовая речь / техжаргон / числа / code-switching,
3 голоса `say`, все на MPS, эталонный текст известен):

| Сэмпл | v2 | v3_e2e_rnnt |
|---|---|---|
| technical_mixed | 0.91с | 0.88с |
| numbers_punct | 0.61с | 0.53с |
| long_paragraph | 1.40с | 1.17с |
| code_switching | 0.59с | 0.40с |

**v3 не медленнее v2, на технике/code-switching заметно быстрее.** Ключевое отличие: v3_e2e
выдаёт **пунктуацию + капитализацию + форматирование чисел** нативно («Встреча назначена на 15:30,
будет три человека. Бюджет 120 000 ₽.»), тогда как v2 отдаёт всё строчными без знаков
(«встреча назначена на пятнадцать тридцать будет три человека»). Для владельца это лучший
СТАРТОВЫЙ текст под LLM-полировку (меньше галлюцинаций чинить) и лучше при выключенном LLM.

Qwen3-ASR (Alibaba, MLX-порт `mlx-community/Qwen3-ASR-1.7B-4bit`) протестирован тем же бенчем:
точен, с пунктуацией, но ~1.8–2.3с/сэмпл (медленнее GigaAM) и допустил СМЫСЛОВУЮ ошибку
(«сжечь» вместо «смёржить»). **Решение: НЕ вводить в прод сейчас** — отдельный MLX-движок,
своя интеграция (mlx-audio dep, регистрация движка, mlx-lock), выигрыша над GigaAM v3 нет.
Задокументирован как будущий кандидат (§5).

## 2. Что реально меняется (инвестигация проведена лично)

### 2.1 Пакет и venv (главная стоимость)
`gigaam==0.1.0` (PyPI) содержит ТОЛЬКО v1/v2. v3-модели есть только в git-исходнике
(`github.com/salute-developers/GigaAM`), где:
- **torch-пин ослаблен** `torch<=2.5.1` → `torch>=2.6` (extra `[torch]`). Базовые зависимости:
  `hydra-core, numpy==2.*, omegaconf, onnx==1.19.*, onnxruntime==1.23.*, soundfile, sentencepiece`.
- Bench-venv встал с torch 2.13 и отработал — установка воспроизводима.
- **Короткие имена теперь алиасятся в `v3_`** (было `v2_`): `_download_model` в новом пакете
  делает `if model_name in short_names: model_name = f"v3_{model_name}"`. То есть после апгрейда
  venv старое `mode="rnnt"` резолвится в **`v3_rnnt`** (НЕ v2_rnnt, НЕ v3_e2e_rnnt).

### 2.2 Выбор варианта v3
Забенчен и рекомендуется **`v3_e2e_rnnt`** (end-to-end, с токенайзером — даёт пунктуацию/
капитализацию/числа). `v3_rnnt` (без e2e) НЕ забенчен и, вероятно, без нативной пунктуации.
→ `STT_GIGAAM_MODE` дефолт меняем `"rnnt"` → `"v3_e2e_rnnt"` ЯВНО (не полагаемся на алиасинг).

### 2.3 Worker (`gigaam_worker.py`) — минимальная правка
- `_handle_transcribe` УЖЕ обрабатывает и `str`, и объект с `.text` (v3 возвращает
  `TranscriptionResult.text`) — совместим без правок.
- Engine-name (`_MODE.replace("v2_","").replace("v1_","")`) на `v3_e2e_rnnt` даёт уродливое
  `gigaam-v3_e2e_rnnt`. Косметика — добавить `.replace("v3_e2e_","").replace("v3_","")` для
  чистого `gigaam-rnnt`. НЕ функциональный баг.

### 2.4 Пост-обработка текста — РЕАЛЬНОЕ взаимодействие (найдено эмпирически)
`PunctuationFixer` (regex) **идемпотентен** на пунктуированном вводе (двойной прогон = одинарный,
финальная точка добавляется только если её нет) — двойной пунктуации НЕТ. НО RU-правила писались
под всё-строчный вывод v2: правило «одиночное я → Я» (`_STANDALONE_YA_RE`) скапитализировало «я»
в СЕРЕДИНЕ предложения на выводе v3 («Слушай, я сегодня» → «Слушай, Я сегодня»). Это НЕ двойная
пунктуация, а over-correction casing'а, которого на v2 не было видно (там всё строчное).
- **Смягчающий фактор**: финальный текст у владельца доминируется LLM-полировкой (LM Studio),
  которая эту мелочь чинит; regex-fixer доминирует только при выключенном LLM. Плюс путь STT→
  fixer в live-流程 идёт НЕ безусловно (engine.py использует LLM `fix_punctuation_only`, regex-
  fixer — часть `TextPostProcessor` DEFAULT_CHAIN, применяемого настройками). Точную активность
  на GigaAM-пути подтвердить живым смоком.
- **Решение v1**: НЕ трогать `PunctuationFixer` в этой волне (риск косметический, LLM маскирует).
  Зафиксировать как известный хвост: «RU-правила fixer'а предполагают lowercase-вход v2; на
  cased-выводе v3 возможна лёгкая over-correction — кандидат сделать fixer engine-aware
  (skip casing-правил на уже-cased входе) отдельной микро-волной». НЕ блокирует апгрейд.

### 2.5 Longform (звонки/импорт > 30с) — нюанс torch-пина
Новый пакет: базовый `[torch]` extra = `torch>=2.6` (short-form transcribe — работает, забенчено).
НО `[longform]` extra требует ДРУГОЙ пин `torch==2.10.*` + `torchcodec==0.10` + `pyannote.audio==4.0`.
Worker вызывает `transcribe_longform()` только при `longform=True` (длинное аудио). Для ДИКТОВКИ
(реальный кейс владельца) longform НЕ триггерится. → Ставим базовый `[torch]`; если longform-путь
(импорт длинных звонков) сломается — отдельный follow-up с longform-extra. Проверить в смоке, что
короткая диктовка работает; longform пометить как «проверить отдельно / возможный хвост».

## 3. План реализации

**Порядок безопасного live-перехода (v2-venv НЕ разрушаем до валидации):**

1. **Обновить `scripts/install_gigaam_venv.command`**: вместо `pip install gigaam` — клонировать
   git-исходник на ПИНОВАННЫЙ коммит (не floating master — воспроизводимость) + `pip install -e .[torch]`.
   Записать точный commit SHA в скрипт и в спеку.
2. **Config**: `STT_GIGAAM_MODE` дефолт `"rnnt"` → `"v3_e2e_rnnt"` (`core/config.py` + `DEFAULT_SETTINGS`).
   Обновить устаревший комментарий (v2 3.8% → v3 e2e + бенч-цифры). Обновить `settings_validator`
   если mode валидируется по списку.
3. **Worker**: engine-name cleanup (косметика, `v3_e2e_`/`v3_` strip).
4. **TDD**: тест воркера/адаптера, что `mode="v3_e2e_rnnt"` резолвится и engine-name = `gigaam-rnnt`;
   idempotency-регресс-тест `PunctuationFixer` (фиксирует текущее поведение, страж от будущей
   двойной пунктуации). Питон-тесты + ubuntu-parity.
5. **Live-валидация БЕЗ разрушения v2**: собрать v3-venv (уже есть `~/.venv_krab_ear_gigaam_v3bench`),
   временно указать прод на него через `set_settings {stt_gigaam_venv_python: <v3bench python>}`,
   прогнать реальную диктовку через backend (не bench-скрипт) — подтвердить: RU-текст с пунктуацией,
   engine=`gigaam-rnnt`, latency в норме, пост-обработка не ломает. Затем канонично переустановить
   `~/.venv_krab_ear_gigaam` через обновлённый скрипт, вернуть `stt_gigaam_venv_python` в дефолт.
6. **Гейты**: `make audit-all`, py-тесты, ubuntu-parity. (Swift не затронут → без swift build.)
7. **Мерж** ff в codex/krab-ear-v2, деплой (backend `kickstart -k` — Python-изменение конфига),
   parity-бинарь Swift НЕ нужен (Swift не менялся). Живой смок диктовки на реальном голосе.
8. **Доки**: CLAUDE.md (GigaAM v2→v3, mode-дефолт, бенч), ROADMAP журнал + §3.5 ритуал STT-refresh
   отметить выполненным, бенч-артефакт в `docs/` или память, `docs/BENCHMARK_M4_MAX.md` если уместно.

## 4. Риски и границы
- **Не разрушать рабочий v2-venv до live-подтверждения v3** (владелец активно диктует).
- **Пиновать git-коммит** GigaAM, не master (воспроизводимость установки для DMG-получателей).
- Longform (§2.5) — отдельный возможный хвост, не блокирует диктовку.
- Пост-обработка casing (§2.4) — известный косметический хвост, LLM маскирует.
- Модель v3_e2e качается с CDN Сбера (~428 MB) — та же схема, что v2, HF-токен не нужен для short-form.

## 5. Qwen3-ASR — будущий кандидат (НЕ сейчас)
`mlx-community/Qwen3-ASR-1.7B-4bit` через `mlx-audio` (0.4.5, CLI `python -m mlx_audio.stt.generate`).
Работает, RU + пунктуация, но медленнее GigaAM v3 и допускает смысловые ошибки на техжаргоне.
Пересмотреть если: (а) появится RU-специализированный тюн, (б) понадобится единый MLX-стек STT+TTS,
(в) GigaAM перестанет обновляться. Бенч-скрипты сохранены в scratchpad на время сессии.
