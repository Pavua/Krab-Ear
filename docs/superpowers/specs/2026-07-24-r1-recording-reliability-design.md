## 1. Контекст и мотивация

Три подтверждённых факта из прода (журнал ROADMAP 2026-07-22…24 + живая форензика
при написании этой спеки):

1. **Диктовки уже терялись**: 2026-07-22 две диктовки владельца погибли при
   деплой-рестарте backend (аудио живёт только в памяти `AudioRecorder._chunks`).
   `safe_backend_restart.command` защищает только рестарты, идущие через него.
2. **Backend умирает от неустановленных причин**: минимум один негрейсфульный случай
   (07-23 ~18:04 — процесс замолчал в 18:11:47 предыдущего дня и стартовал заново без
   единой строки graceful shutdown; крэш-репортов Python нет → SIGKILL или тихий exit)
   и один странный graceful (07-22 14:05, затем 4 часа простоя до 18:10 — паттерн
   `bootout`, не kickstart). Оба события — около 18:04-18:10 в соседние дни
   (возможна ежедневная периодичность — проверит форензика).
3. **Пост-хок форензика слепа**: unified log уже ротирован, `shutdown_info.json`
   пишет только `{last_shutdown_time, clean, elapsed_ms, errors}` — ни сигнала,
   ни состояния записи, ни источника. Выяснить «кто прислал сигнал» сегодня
   невозможно в принципе; ловить надо В МОМЕНТ следующего инцидента.

Дополнительно: у codex есть незавершённая WIP-ветка
`codex/user3-recording-rescue-20260722` (1 коммит, +13207/−966, 44 файла, без
хэндоффа) — Swift state machine восстановления стопа (`RecordingStopRecovery.swift`,
679 строк + 875 строк тестов: finalize-маршруты с owner/token, preflight старта,
response-fences) + правки 29 Python-файлов. Квота codex исчерпана — забираем себе
(решение владельца 2026-07-24).

## 2. Цель и Definition of Done

**Цель**: записанное аудио (диктовка И встреча) не теряется молча ни при каком классе
смерти backend-процесса, а каждый рестарт объясним постфактум.

DoD волны:
1. `kill -9` backend посреди записи → после рестарта пользователь получает громкое
   уведомление и восстановленную запись (WAV всегда; транскрипция в history — если
   privacy-режим позволяет). Доказано живым e2e-смоком на одноразовом dev-backend.
2. Тот же сценарий для meeting-записи: аудио встречи восстановимо (тем же механизмом —
   встреча пишет в тот же `AudioRecorder`).
3. `shutdown_info.json` после любого graceful завершения содержит: какой сигнал,
   uptime, был ли активен recording/meeting в момент сигнала.
4. После НЕгрейсфульной смерти следующий старт автоматически собирает свежую
   форензику (`log show` за окно смерти + хвост собственных логов) в каталог
   `<data_dir>/forensics/` — пока unified log ещё помнит.
5. Swift-сторона: после переподнявшегося сокета агент ретраит `stop_recording` /
   спасает live-превью вместо generic-ошибки (наследие WIP codex, Фаза 2).
6. Все новые персистентные каталоги (`rescue/`, `forensics/`) покрыты
   `handle_purge_all_data` (CI-гейт `audit_purge_coverage` зелёный).

## 3. Не-цели

- НЕ чинить сам источник загадочных рестартов в этой волне (сначала инструментация;
  фикс источника — следующая волна, когда форензика его назовёт).
- НЕ строить save/restore аудио-девайсов, pre-roll (F3) и reconnect-бюджеты (F6) —
  отдельные хвосты, вне скоупа.
- НЕ переносить WIP codex «как есть»: 13k-строчный дифф с устаревшим merge-base
  (до bounded-shutdown #1891) — источник для salvage, не для wholesale-мержа.
- НЕ шифровать rescue-WAV (прецедент: `tmp_meeting/` диар-окна тоже пишутся
  нешифрованным WAV; history-шифрование — отдельная подсистема). Зафиксировать
  как осознанный v1-компромисс.

## 4. Архитектура

### 4.1 Фаза 1, компонент A — continuous spill (Python)

Во время записи `AudioRecorder._worker` инкрементально дописывает сырые фреймы
на диск; при любой смерти процесса аудио уже на диске.

- **Формат**: raw PCM float32 (как в `_chunks`, без конверсии) в
  `<data_dir>/rescue/<session_id>.f32.part` + JSON-сайдкар
  `<session_id>.meta.json` `{sample_rate, channels, started_at_iso, source}`
  (`source`: `dictation|meeting|unknown` — проставляет вызыватель старта
  (`RecordingCoreService`/`MeetingSessionService`), recorder сам его не знает;
  при отсутствии — `unknown`).
  Raw без заголовка переживает обрыв на любом байте (выравнивание по 4 байта
  при финализации). WAV собирается только при восстановлении.
- **Точка врезки**: в `_worker` сразу после `self._chunks.append(...)`,
  строго ВНЕ `self._lock` (I/O под локом запрещён — см. историю deadlock
  W1652/F3 в этом же файле). Запись через файл, открытый на старте записи;
  `flush()` после каждого чанка — Python-буфер BufferedWriter НЕ переживает
  kill, а ОС page cache переживает смерть процесса. Один syscall / 0.1с —
  бюджет подтверждается тестом (порог на среднее время дозаписи чанка).
- **Ошибки spill не убивают запись**: любой сбой записи на диск (ENOSPC и т.п.) →
  однократный WARN + отключение spill до конца текущей записи; сама запись
  продолжается (fail-open в сторону работающей диктовки — spill вспомогателен).
- **Политика удаления spill-файла** (ключевая тонкость, найдена самопроверкой):
  - обычный `stop()` → файл удаляется ТОЛЬКО после успешного персиста результата
    в history (удаляет `RecordingCoreService` в конце stop-хендлера, не recorder);
    смерть мид-транскрипции → файл жив → восстановление;
  - `abort()` при shutdown → файл СОХРАНЯЕТСЯ (это главный сценарий спасения);
  - явная отмена записи пользователем (если путь есть) → удалить сразу.
- **Настройка**: `recording_spill_enabled` в `DEFAULT_SETTINGS` (default `True`),
  читается на старте записи через `_get_runtime_setting` (не `DEFAULT_SETTINGS.get`
  — урок Wave 58).
- **Идемпотентность против двойного восстановления**: имя файла = session UUID;
  остаточный риск «персист успел, unlink не успел → дубль после рестарта»
  принимается осознанно (дубль лучше потери; направление отказа выбрано явно),
  мягкая сеть — существующий `AutoDeduplicator`.

### 4.2 Фаза 1, компонент B — восстановление на старте (Python)

При старте backend (после конструирования сервисов; сам сбор — в фоновом
треде, старт IPC не ждёт):
1. Скан `rescue/*.part`; каждый финализируется в `<session_id>.rescued.wav`.
2. Громкое уведомление: новый код `audio.recording_rescued` в `ERROR_REGISTRY`
   (severity `warn`, actionable) → ErrorBus → существующий toast-путь агента.
3. Транскрипция: если `privacy_mode_enabled` на момент восстановления —
   WAV остаётся на диске, транскрипции нет (уведомление говорит, где лежит файл);
   иначе — файл уходит в существующий механизм `transcribe_paths` (async),
   запись попадает в history обычным item'ом с префиксом заголовка
   «Восстановленная запись» (для meeting-аудио — тоже обычная транскрипция;
   реконструкция meeting-отчёта НЕ делается — см. §3), исходный WAV удаляется
   после успешного персиста (та же политика, что у spill).
4. Restart-шторм-гард: восстановление single-flight, не блокирует старт IPC
   (фоновый тред), лимит на количество одновременно восстанавливаемых файлов.

### 4.3 Фаза 1, компонент C — shutdown-форензика (Python)

1. **Расширение `shutdown_info.json`** (пишет существующий
   `GracefulShutdownHandler._persist`): + `signal` (`SIGTERM|SIGINT|close()`),
   `uptime_sec`, `recording_active`, `meeting_active`, `pid`.
   Схема аддитивная — существующие читатели не ломаются.
2. **Новый модуль `backend/shutdown_forensics.py`**: на старте сравнивает
   предыдущий `shutdown_info.json` с фактом «процесс стартует»:
   - предыдущее завершение отсутствует/`clean:false`/timestamp сильно старше
     последней активности собственных логов → классифицируется UNCLEAN;
   - при UNCLEAN — best-effort сбор в `<data_dir>/forensics/<ts>/`:
     `log show --start .. --end ..` за окно смерти (launchd/jetsam-сообщения),
     хвост `krab-ear-backend.{out,err}.log`, снимок `launchctl print` юнита;
   - retention: максимум 5 последних каталогов, старые удаляются;
   - весь сбор best-effort с таймаутом (log show бывает медленным) и никогда
     не мешает старту (фоновый тред, fail-open с WARN).
3. **Не делаем**: ctypes/SA_SIGINFO для si_pid отправителя — хрупко (подмена
   C-хендлера под CPython), отклонено на этапе спеки; если форензика (2) не
   назовёт источник после следующего инцидента — вернуться к вопросу отдельно.

### 4.4 Фаза 2 — salvage WIP codex (Swift + контрактные Python-правки)

Порядок внутри фазы:
1. **Инвентаризация**: полный дифф WIP против его merge-base; классификация
   каждого блока: (a) уже покрыто принятыми #1891/runtime-hardening,
   (b) конфликтует с Фазой 1, (c) уникальная ценность (state machine
   RecordingStopRecovery + его 875 строк тестов, preflight старта,
   response-fences).
2. **Решение per-блок**: cherry-pick / re-derive против текущего main /
   отбросить. Python-сторона WIP (29 файлов) по умолчанию re-derive:
   merge-base устарел, и Фаза 1 уже перепишет те же файлы.
3. **DoD фазы**: (a) агент после переподнявшегося сокета ретраит
   `stop_recording` (вместо generic-ошибки), включая случай «backend новый,
   аудио нет» → честное сообщение со ссылкой на rescue-механизм Фазы 1;
   (b) live-превью спасается при IPC-таймауте стопа (существующий
   `recorder_timeout`-preview путь доводится до UI);
   (c) полный конвейер ревью как для чужого кода: построчный личный гейт
   критических диффов + adversarial-ревью целого диффа перед мержем.

### 4.5 Взаимодействие фаз

Swift-ретрай (Фаза 2) и rescue (Фаза 1) сцепляются так: ретрай покрывает
«сокет умер, процесс жив» (аудио ещё в памяти — стоп довозится штатно);
rescue покрывает «процесс умер» (ретраить нечего — новый процесс отдаёт
`already_stopped`, аудио приходит через восстановление). Двойной доставки
нет: восстановление стартует только при наличии `.part`-файла, который
штатный стоп удаляет после персиста.

## 5. Порядок исполнения (поправка самопроверки)

Первоначальный «вариант A» предполагал параллельные треки Python/Swift.
Самопроверка против реального диффа WIP показала: WIP трогает 29 Python-файлов,
включая все цели Фазы 1 (`recorder.py`, `recording_core_service.py`,
`shutdown_handler.py`, `service.py`) — параллельность дала бы двойную переделку.
**Фазы строго последовательны: 1 → 2.** Внутри Фазы 1 компоненты A+B — одна
задача-цепочка (общий формат spill/восстановления), C — независимая задача,
может идти параллельно с A+B (не пересекаются по файлам, кроме аддитивной
правки `shutdown_handler._persist` — выполняется в C).

## 7. Риски

| Риск | Митигация |
|---|---|
| I/O в hot path записи (worker-цикл 0.1с) | flush ≈ мкс; тест-бюджет на дозапись чанка; fail-open отключение spill при сбоях |
| Дубль записи после восстановления | session-UUID + unlink-после-персиста; остаточный риск принят (дубль > потери), AutoDeduplicator |
| `log show` медленный/пустой на старте | таймаут + фоновый тред + fail-open; форензика best-effort по определению |
| WIP окажется несовместим глубже ожиданий | Фаза 2 начинается с инвентаризации с явным правом «отбросить и перевывести»; ценность фазы — DoD-поведение, не сохранение чужих строк |
| Rescue-WAV на диске = новый класс приватного артефакта | purge-coverage обязателен; удаление после персиста; privacy-гейт транскрипции; нешифрование зафиксировано как v1-компромисс (§3) |
| Восстановление стартует под рестарт-штормом | single-flight + не блокирует IPC-старт + лимит файлов за проход |
