# Авто-дострел отложенного stop_recording после восстановления backend

Дата: 2026-08-11. Статус: одобрено владельцем (направление — AskUserQuestion),
спека к ревью. Скоуп: Swift-агент, только путь диктовки.

## 1. Проблема

Когда `stop_recording` не смог завершиться (сокет умер, лимит 64 коннектов,
backstop-шторм — живой класс 2026-08-09), `RecordingStopCoordinator` честно
сдаётся после bounded-бюджетов (2 транспортных ретрая за ~0.75с) и агент
сохраняет generation-токен (`recordingStopRecoveryPending = true`,
`main+HotkeyRecording.swift:930`). Дальше — тост «нажмите остановку ещё раз»
и ОЖИДАНИЕ РУЧНОГО нажатия. Backend при этом может ожить через 5-30 секунд
(blip) или после рестарта; агент момент восстановления ЗНАЕТ
(`HealthMonitor` пингует каждые 3с), но ничего с ним не делает.

Самый ценный закрываемый кейс: **backend НЕ рестартовал** (сокет мигнул,
шторм коннектов рассосался) — токен жив, стоп завершится нормально, текст
диктовки вставится сам, без второго нажатия. После настоящего рестарта токен
мёртв → `unknown_generation` → уже существующая чистая самоочистка + rescue
уже спасает аудио (R1) — авто-дострел лишь избавляет от ручного нажатия ради
этой самоочистки.

Разведка 2026-08-11 (два Explore-агента, карты в этом же duty-cycle)
подтвердила анти-rebuild: весь остальной хвост инцидента 07-22 закрыт
волнами R1/R2 — ретраи, поллинг `stop_in_progress` до 5 мин, идемпотентный
backend с replay терминального ответа, rescue-тост. Дельта — ровно одна.

## 2. Дизайн (вариант A, одобрен)

### 2.1 Точка срабатывания — существующий `onHealthyPing`

`HealthMonitor.setOnHealthyPing` уже вызывается на каждом успешном ping
(заведён второй ступенью self-heal для перевзвода капа эскалаций,
`HealthMonitor.swift:135`). **Актор не трогаем.** Вся логика — в
агентской обёртке (композиция с существующим колбэком второй ступени,
не замена: у `setOnHealthyPing` один слот — wiring-код обязан вызвать ОБА
действия из одного замыкания; см. §4 риск R4).

### 2.2 Взведение и one-shot

Новое MainActor-состояние в `AgentAppDelegate`:

- `dictationStopAutoRetryArmed: Bool` — взводится в
  `retainDictationStopRecovery(...)` (момент, когда стоп сдался и токен
  сохранён) — ТОЛЬКО для `activeGenerationOwner == "dictation"`.
- `dictationStopAutoRetryBudget: Int` — начинается с 2 на «эпизод потери»
  (эпизод = непрерывный период `recordingStopRecoveryPending == true`;
  полный успех/очистка восстанавливают бюджет).

Первый `onHealthyPing` при взведённом флаге: disarm → hop на MainActor →
`attemptPendingDictationStopRecovery()`. Hop — строго fire-and-forget
(`Task { @MainActor in … }`), НЕ await из колбэка: `stopRecording()` живёт
секунды-минуты (coordinator + финализация), а `onHealthyPing` вызывается
из tick-цикла актора — await заблокировал бы ping-цикл на весь стоп.
Disarm — ДО hop'а (в самой обёртке): подряд идущие healthy ping'и (3с)
не должны наплодить очередь дублирующих MainActor-задач.

### 2.3 Гарды попытки (все обязательны)

```swift
@MainActor
func attemptPendingDictationStopRecovery() async {
    guard recordingStopRecoveryPending,
          activeGenerationOwner == "dictation",
          !isProcessing,          // ручной стоп уже в полёте — не входить
          !quickCaptureActive,    // симметрия с toggle-входом
          dictationStopAutoRetryBudget > 0
    else { return }
    dictationStopAutoRetryBudget -= 1
    logger.info("Авто-дострел отложенного stop_recording (бюджет: …)")
    await stopRecording()
}
```

`stopRecording()` не меняется: тот же путь, что и ручной повтор по toggle
(строка 208-212) — coordinator, suspend сторожей, обработка исхода.

### 2.4 Почему двойная вставка невозможна

- Ручной toggle отсекается на входе `isProcessing`-гардом
  (`main+HotkeyRecording.swift:150`) — `stopRecording()` держит
  `isProcessing = true` весь свой цикл.
- Авто-попытка проверяет `isProcessing` сама (гард выше) — симметрично.
- Оба пути на MainActor → интерливинг только на await-точках, где гарды
  уже сняли одну из сторон.
- Backend идемпотентен: повторный стоп с тем же токеном получает replay
  ЕДИНСТВЕННОГО терминального ответа (`recording_core_service.py`,
  `_replay_terminal_response`) — но до этого доводить не должно; replay —
  strait belt-and-suspenders, не основной механизм.

### 2.5 Повторные провалы, шторм, бэкофф

- Попытка снова сдалась транспортом → `retainDictationStopRecovery` снова
  взводит armed, но healthy ping не придёт, пока сокет мёртв —
  естественный бэкофф самим монитором (3с-цикл).
- Попытка сдалась терминально-невнятно (retain при живом сокете) → снова
  armed, следующий healthy ping через 3с → вторая попытка → бюджет
  исчерпан (2) → дальше ТОЛЬКО ручное нажатие (прежнее поведение).
  Кап предотвращает карусель «каждые 3с полный coordinator-цикл» на
  залипшем backend'е — тот же паттерн, что give-up cap
  `WedgedEscalationTracker`.
- Бюджет восстанавливается при: терминальном успехе стопа, `unknown_generation`
  (clear), старте новой записи.

### 2.6 UX

Авто-дострел, завершившийся вставкой текста, показывает СУЩЕСТВУЮЩИЙ
успешный путь (вставка + звук) — дополнительно ничего не изобретаем.
Единственная новая строка: если авто-дострел успел РАНЬШЕ, чем юзер нажал
хоткей повторно, его следующее нажатие начнёт НОВУЮ запись — это штатно
(состояние idle), но чтобы не удивлять, тост успеха после авто-дострела
явно говорит «Остановка достреляна автоматически» вместо молчаливой вставки.
Реализация: `stopRecording()` не знает, кто его позвал — прокинуть
булевый параметр `autoRetried: Bool = false` только для текста тоста
УСПЕШНОЙ ветки. (Если это потянет заметное разрастание сигнатур — воркеру
разрешено ограничиться log-строкой вместо тоста, отметив это в отчёте.)

### 2.7 Quick capture — осознанно НЕ в скоупе

`recordingStopRecoveryPending` используется и quick capture
(`main+QuickCapture.swift:546,581`), но там owner ≠ "dictation", свой
recovery-путь (панель с кнопкой) и меньшая UX-боль. Гард по owner отсекает.
Расширение на QC — отдельная мини-волна, если владелец попросит.

## 3. Отвергнутые варианты

- **B. Ничего не делать**: данные уже защищены rescue; но самый частый
  живой кейс (blip/шторм при живом backend) оставляет диктовку висеть до
  ручного нажатия — дёшево закрываемая реальная боль.
- **C. Очередь отложенных IPC-операций**: YAGNI — ровно одна операция
  (стоп диктовки) имеет сохраняемый токен и ценность авто-повтора.
- **D. Новый колбэк/транзишен в самом HealthMonitor-акторе**: чище
  семантически («переход fail→ok»), но требует менять актор и его
  контракт ради потребителя, которому достаточно комбинации
  armed-флага + существующего сигнала. Не проходит и кейс «монитор был
  suspended во время провала» (suspend/resume сбрасывают счётчик — переход
  невидим), а armed-флаг проходит.

## 4. Риски и их закрытие

- **R1 двойная вставка** — §2.4 (гарды + MainActor + идемпотентный backend).
- **R2 карусель попыток** — §2.5 (кап 2 + естественный бэкофф монитором).
- **R3 гонка с wedge-эскалацией**: во время `stopRecording()` монитор
  suspended (`.finalizingRecording`) — эскалация второй ступени не увидит
  «провалов» от занятого финализацией backend'а; ровно как при ручном стопе.
- **R4 затирание чужого onHealthyPing**: у `setOnHealthyPing` ОДИН слот, и
  он уже занят перевзводом капа второй ступени — wiring обязан
  КОМПОНОВАТЬ оба действия в одном замыкании; source-контракт тест
  проверяет, что оба вызова присутствуют (класс «декоративная проводка»).

## 5. Тесты (DoD)

1. armed взводится в retain (dictation) и НЕ взводится для quick capture.
2. Попытка: все 5 гардов по отдельности блокируют (5 тестов).
3. Бюджет: 2 попытки на эпизод, третьего вызова stopRecording нет;
   восстановление бюджета на очистке recovery-состояния.
4. onHealthyPing-обёртка: зовёт И перевзвод капа второй ступени, И
   авто-дострел (source-контракт против затирания слота — R4).
5. Интеграционный: retain → healthy ping → stopRecording вызван ровно один
   раз (spy), повторный healthy ping без нового retain → не вызван.
6. Полный `swift test` зелёный.

Живой e2e (после мержа): диктовка → `launchctl kickstart -k` REST-юнита не
нужен; вместо этого остановить backend на ~5с (SIGSTOP/SIGCONT процессу —
безопаснее kickstart: сокет перестаёт отвечать, потом оживает с ЖИВЫМ
токеном) в момент стопа → текст вставился без второго нажатия.
