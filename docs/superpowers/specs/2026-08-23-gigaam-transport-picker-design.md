# Пикер транспорта GigaAM в Settings — дизайн

- **Дата:** 2026-08-23
- **Ветка:** `feat/gigaam-transport-picker`
- **Статус:** дизайн утверждён владельцем, спека на ревью

---

## 0. Зачем

GigaAM v3 (RU-распознавание) умеет работать двумя транспортами:

- `subprocess` — PyTorch-воркер в изолированном venv `~/.venv_krab_ear_gigaam`, общение через stdin/stdout JSON;
- `mlx` — чистый MLX в ГЛАВНОМ процессе, модель `aystream/gigaam-mlx`, по-чанковый `mlx_lock`.

MLX-путь реализован (`core/pipeline/stt_gigaam_mlx.py`, проводка в `core/stt_router.py:441`), но переключается только правкой `settings.json` или IPC-вызовом вручную. Владельцу нужен переключатель в приложении, чтобы пробовать и откатываться без консоли.

### 0.1. Живой замер, обосновывающий существование выбора

Прогон 2026-08-23 на throwaway-инстансе, звонок 23.25 мин, один и тот же `AudioChunker` на 20с для обоих путей:

| Ось | subprocess (PyTorch) | mlx |
|---|---|---|
| Время | 55.1с (**25× realtime**) | 29.2с (**48× realtime**) |
| Расхождение текста | — (reference) | **2.9%** слов (35 замен, 7 удалений, 4 вставки на 1572 слова) |

Расхождения — орфографические варианты нечётких слов разговорной речи (`пундуля`/`пундули`, `Пашуленька`/`Пашульенька`), смысловых потерь не найдено.

🔴 **Найденная асимметрия, ради которой выбор и должен остаться выбором.** `mlx_whisper.transcribe()` держит `mlx_lock` **на весь файл** одним `with`-блоком (`core/engine.py:2763`), а `GigaAMMLXAdapter` берёт лок **по-чанково**. Замер: GigaAM-чанк 3с при **отсутствии** конкуренции — 0.07с; он же **параллельно** с 60-секундной whisper-транскрипцией — **6.71с**, то есть ждёт ровно столько, сколько идёт вся транскрипция whisper.

В режиме `subprocess` этой конкуренции нет вовсе: GigaAM в отдельном процессе со своим GPU-контекстом. Поэтому `mlx` — не безусловно лучший вариант, а компромисс «быстрее в одиночку / медленнее при пересечении с диктовкой». Владелец принял это осознанно (пересечения редки), но переключатель обязан позволять откат.

## 1. Дизайн

### C1. Размещение — отдельная статическая карточка внутри секции «STT-движки»

Секция `dictation_stt_engines` (Gemini) / `cd_stt_engines` (Claude Design) уже существует и содержит строку GigaAM с переключателем `stt_gigaam_enabled`. Пикер транспорта добавляется **второй, статической карточкой** в ту же секцию, ниже карточки движков.

**Почему отдельная карточка, а не строка внутри существующей.** Карточка движков перестраивается асинхронно (`fetchAndRebuildSTTEnginesCard` → `rebuildGeminiSTTEnginesCard`), и её разделители расставляются по индексу: `if index < engines.count - 1`. Вставка лишней строки в этот цикл сдвинула бы разделители относительно движков. Отдельная карточка снимает проблему целиком и не участвует в гонке с асинхронной перестройкой.

Видимость: карточка скрывается (`isHidden = true`), когда `stt_gigaam_enabled == false` — транспорт выключенного движка настраивать бессмысленно.

### C2. Значение транспорта — из `AgentSettings`, не из `list_stt_engines`

`stt_gigaam_transport` — обычная настройка, ровно как `quality_profile`. Поэтому она едет тем же путём, а не через список движков.

В `native/KrabEarAgent/Sources/KrabEarAgent/Models.swift` добавляется поле по установленной конвенции — **шесть точек**, все обязательны:

| Место | Что добавить |
|---|---|
| объявление (рядом со строкой 60) | `var gigaamTransport: String` |
| `Self.default` (рядом со строкой 147) | `gigaamTransport: "subprocess"` |
| парсер из payload (рядом со строкой 222) | `self.gigaamTransport = (payload["stt_gigaam_transport"] as? String) ?? Self.default.gigaamTransport` |
| параметр memberwise-init (рядом со строкой 318) | `gigaamTransport: String = "subprocess",` — 🔴 **с дефолтом**, как сиблинг `cloudRewriterProvider: String = "openai"` (`Models.swift:376`); голый параметр без дефолта сломал бы компиляцию существующих вызовов, которые его не передают |
| присваивание в init (рядом со строкой 388) | `self.gigaamTransport = gigaamTransport` |
| `toPayload()` (рядом со строкой 461) | `"stt_gigaam_transport": gigaamTransport,` |

Дефолт `"subprocess"` совпадает с `DEFAULT_SETTINGS["stt_gigaam_transport"]` в `KrabEar/core/config.py:995`.

🔴 **Уточнение про два дефолта, которое нельзя опускать.** Дефолтов в Python действительно два, и в рантайме роутера побеждает **не тот**, что берёт Swift:

| Источник | Значение | Кто читает |
|---|---|---|
| `config.py:414` — pydantic `STT_GIGAAM_TRANSPORT` | `"auto"` | **роутер** (`stt_router.py:412`, `getattr(self._settings, …)`) |
| `config.py:995` — `DEFAULT_SETTINGS` | `"subprocess"` | merge в `load_settings`/`get_settings`, то есть UI |

`DEFAULT_SETTINGS` до роутера не доходит никогда. Поэтому при отсутствии ключа в `settings.json` UI покажет «Стабильный (subprocess)», а рантайм исполнит `auto`. Эффективно это совпадает (`auto` → `in_process` не импортируется в главном venv → `subprocess`), и выбор `"subprocess"` для Swift-дефолта допустим — но формулировка «расхождения быть не должно» была бы неточной. Расхождение существует и самоликвидируется при первой же записи настроек (см. оговорку в C4).

### C3. Доступность MLX — одно поле в `list_stt_engines`, через `find_spec`

Swift не может сам узнать, установлена ли библиотека `gigaam_mlx`. Поэтому в `handle_list_stt_engines` (`KrabEar/backend/stt_management_service.py:297`) к записи `gigaam` — и **только** к ней — добавляется одно поле:

```python
"mlx_available": bool,
```

🔴 **Вычисляется строго через `importlib.util.find_spec("gigaam_mlx")`, а НЕ импортом адаптера.**

Первая редакция дизайна предлагала `try: import core.pipeline.stt_gigaam_mlx`. Это ложноположительная проверка: в самом адаптере `import gigaam_mlx` стоит **внутри методов** (`stt_gigaam_mlx.py:120` и `:213`), лениво — модуль-адаптер импортируется успешно и **без установленной библиотеки** (так и задумано: py3.12 ubuntu-parity CI работает без неё). UI показывал бы «доступно» там, где распознавание упадёт.

`find_spec` также не тянет за собой MLX/Metal — импорт библиотеки дорог и имеет побочные эффекты, а нам нужен только факт наличия.

Форма ответа это допускает: словари движков уже разнородны (`toggle_key` бывает `null`). Остальные три движка поля не получают; в Swift `STTEngineRow` появляется `mlxAvailable: Bool?` = `nil` для них.

### C4. Контрол и запись

`NSPopUpButton`, два пункта (по образцу пикера провайдера в `HistoryPanelController+CloudRewriter.swift:52`):

| Индекс | Заголовок | Значение |
|---|---|---|
| 0 | Стабильный (subprocess) | `"subprocess"` |
| 1 | Быстрый (MLX, экспериментальный) | `"mlx"` |

Значения `auto` и `in_process` сознательно не показываются: `auto` почти всегда резолвится в `subprocess`, `in_process` требует PyTorch+MPS в основном venv (нетипичный сетап).

🔴 **Оговорка про «пикер их не стирает».** `applySettingsPatch` — вопреки имени **не патч**: он берёт `settingsProvider().toPayload()` ЦЕЛИКОМ, вливает в него патч и отправляет полный словарь. Как только `stt_gigaam_transport` попадёт в `toPayload()`, его будет записывать **любое** изменение любой настройки из панели.

Практические последствия:
- явные `"auto"` / `"in_process"` в `settings.json` **выживают** — парсер round-trip'ит сырую строку, пикер её не переписывает без действия пользователя;
- но у пользователя, у которого ключа в `settings.json` **нет вообще**, первое же изменение чего угодно молча запишет `"subprocess"`, превратив неявный рантайм-`auto` в явно закреплённый `subprocess`. На типичном сетапе поведение эквивалентно (`auto` → ImportError `in_process` → `subprocess`), на редком in_process-сетапе — реальная смена транспорта.

Это не блокер (эквивалентность на типичном сетапе), но ревьюер кода не должен искать патч-семантику, которой в помощнике нет.

Обработчик:

```swift
@objc func onGigaamTransportChanged(_ sender: NSPopUpButton) {
    guard !isSyncingSettings else { return }
    let transport = sender.indexOfSelectedItem == 1 ? "mlx" : "subprocess"
    applySettingsPatch(["stt_gigaam_transport": transport])
}
```

🔴 `guard !isSyncingSettings` обязателен: `syncSettingsControls()` выставляет этот флаг перед программной установкой значений контролов (`HistoryPanelController+Settings.swift:471`). Без гварда программная синхронизация вызвала бы обработчик и записала настройку обратно — цикл обратной связи.

**Почему `applySettingsPatch`, а не сырой `ipc.call` off-main, как в соседнем `onSTTEngineToggleChanged`.** Проверено по коду: `applySettingsPatch` → `settingsUpdater` → `updateSettingsFromPanel` → `persistSettingsPayload` (`main.swift:1396`), который обновляет состояние **оптимистично** и отправляет `set_settings` внутри `Task` через **`callAsyncWithRecovery`** — единственный санкционированный механизм восстановления IPC после падения backend (CLAUDE.md, PR #1910). Сырой `ipc.call` этого восстановления не даёт. То есть `applySettingsPatch` здесь не только безопасен для main-треда, но и строго лучше.

**Рестарт backend не нужен.** Проверено живьём 2026-08-23: `SettingsService._reload_and_fire_hooks` — единая точка после всех путей сохранения — синхронно зовёт `core.config.reload_settings_from_json()`, а `STTRouter._get_gigaam_adapter_locked` пересчитывает `fingerprint = (mode, device, transport, venv_python)` на каждый вызов и пересоздаёт адаптер при изменении. Живое переключение на `mlx` подхватилось работающим процессом: RSS backend'а вырос 201 → 530 МБ сразу после первой транскрипции (MLX грузит модель в тот же процесс), субпроцесс `gigaam_worker.py` при этом не порождался.

### C5. 🔴 Честное поведение при недоступной библиотеке

Это главный содержательный пункт дизайна, а не косметика.

**Что происходит сегодня, если `stt_gigaam_transport = "mlx"`, а `gigaam_mlx` не установлена.** В `core/stt_router.py:446` ветка MLX обёрнута в `except ImportError` вокруг импорта **адаптера** — но этот импорт, как показано в C3, успешен. Поэтому `ImportError`-ветка не срабатывает, адаптер конструируется, и отказ вылезает только на первом `transcribe()`, внутри `except Exception` → `logger.warning` + `return None`. Отката на `subprocess` **нет**: GigaAM просто исчезает из каскада, и RU-распознавание молча уходит на whisper.

Пикер обязан сделать это видимым:

1. Если `mlx_available == false` — пункт «Быстрый (MLX…)» **задизейблен** с тултипом «Требуется библиотека gigaam_mlx». Это та же конвенция, что уже применяется к недоступным движкам (серый + тултип), а не скрытие пункта.

   🔴 **Одного `item.isEnabled = false` НЕДОСТАТОЧНО — обязателен `popup.menu?.autoenablesItems = false`.** У `NSMenu` авто-валидация включена по умолчанию и перезаписывает ручной `isEnabled` перед показом меню: пункт останется кликабельным. Класс уже ловили в этом репозитории — `main+CallObserver.swift:56`, находка MED-2. Без этой строки главный защитный механизм C5 не работает вообще: библиотеки нет, пункт выглядит рабочим, пользователь выбирает MLX — и получает ровно то молчаливое исчезновение GigaAM, ради предотвращения которого написан весь раздел.
2. 🔴 Если при этом **текущее значение уже `mlx`** — рядом с пикером показывается предупреждающий бейдж: **«MLX выбран, но библиотека не найдена — GigaAM отключён»**. Без этого пользователь видел бы выбранный MLX и не понимал, почему RU-распознавание стало хуже.

Случай (2) не гипотетический: значение может попасть в `settings.json` из IPC, из перенесённого конфига или из прошлой установки, где библиотека была.

Пикер **не** переписывает настройку молча — тихая правка чужого выбора хуже видимого предупреждения.

### C5a. 🔴 Проводка синхронизации — три отдельных обязательства

Без явных требований здесь волна порождает «декоративную проводку»: обработчик записи реализован, тесты зелёные, а UI протухает. Класс хронический для этого репозитория, поэтому каждое обязательство названо отдельно.

**(а) Хук синхронизации контрола.** Добавляется `syncGigaamTransportControls(settings:mlxAvailable:)` и **вызывается из `syncSettingsControls`** — по образцу сиблинга `syncCloudRewriterControls` (вызов в `HistoryPanelController+Settings.swift:595`). Без него попап не получит начальное значение и не ресинкнется после внешнего `set_settings` или `apply_profile_preset`.

**(б) Пересчёт видимости карточки.** Тумблер `stt_gigaam_enabled` живёт в **соседней** карточке, которая перестраивается асинхронно (`fetchAndRebuildSTTEnginesCard`). Значит `isHidden` карточки транспорта обязан пересчитываться **в completion этой перестройки**, а не только при построении секции. Иначе: выключил GigaAM → карточка транспорта осталась висеть.

**(в) Доставка `mlx_available` в статическую карточку.** Данные приходят асинхронно из `list_stt_engines`, а контрол построен синхронно — это разные циклы. Значение прокидывается тем же completion, что и (б): оттуда вызывается хук (а) с актуальным `mlxAvailable`.

Все три — предмет source-контракт-тестов «хук реально вызывается» (паттерн `MainErrorsWiringTests`), а не только существует.

## 3. Что осознанно НЕ делается

- **Не показываются `auto` и `in_process`** — не имеют практического смысла для владельца (см. C4), остаются доступны через `settings.json`.
- **Не добавляется автооткат `mlx` → `subprocess`** при недоступной библиотеке. Это изменение поведения STT-каскада, а не UI; оно требует отдельного решения и своей волны. Пикер ограничивается тем, чтобы сделать проблему **видимой** (C5).
- **Не трогается асимметрия `mlx_lock`** (whisper держит лок на весь файл). Это архитектурная тема со своей ценой и своим замером — отдельная волна.
- **Не меняется дефолт** `stt_gigaam_transport`. В `DEFAULT_SETTINGS` остаётся `"subprocess"`; текущее значение на машине владельца (`mlx`) выставлено осознанно и переключателем не сбрасывается.

## 4. Известные ограничения

1. **`mlx_available` отражает наличие библиотеки, а не работоспособность.** `find_spec` не проверит, что MLX реально запустится на этом железе (нужен Apple Silicon). На не-Apple-Silicon библиотека обычно и не установится, но гарантии это не даёт.
2. **Пикер не показывает, какой транспорт использовался ФАКТИЧЕСКИ** в последней транскрипции — только выбранный. Поле `last_engine` в `get_diagnostics.stt` существует, но на момент проверки возвращало `null`; его оживление — отдельная задача.

3. 🔴 **При `transport=mlx` GigaAM исчезает из `GET /v1/models` REST-процесса — даже если библиотека установлена и работает.** Найдено ревью-гейтом. Цепочка: `rest_server.py:1946` лениво импортирует `build_router as _build_router` → `stt_router_factory.py:55` конструирует `GigaAMSTTAdapter(transport="mlx")` → `_VALID_TRANSPORTS = {"auto","in_process","subprocess"}` (`stt_gigaam.py:88`) не знает `"mlx"` → `ValueError` → фабрика ловит и мягко выбрасывает GigaAM из списка.

   Это поведение существует с самой mlx-волны и **уже задокументировано комментарием в коде** (`stt_router_factory.py:59-63`: «фабрика Phase D.2 не подключена к engine — деградируем мягко»). На саму диктовку не влияет — основной стек идёт через `stt_router.get_gigaam_adapter`, а не через фабрику. Затрагивает только перечисление движков для Voice Gateway.

   Пикер этого не создаёт, но делает достижимым в один клик, поэтому ограничение фиксируется здесь явно. Правильный фикс — научить фабрику mlx-ветке — **отдельная волна**, в объём этой не входит.

   Замечание о методе: наивный `grep build_router` этот вызов НЕ находит — он лениво импортирован под алиасом `_build_router` внутри функции. Искать потребителей по имени модуля, а не только по имени функции.

4. **После неудачной попытки MLX возврат на subprocess лечит не мгновенно.** Реальное место поимки отказа — не роутер, а fallback-каскад engine: `ModuleNotFoundError` вылетает из `adapter.transcribe()`, ловится каскадом и ставит маркер GigaAM в `_unavailable_models` с TTL `_UNAVAILABLE_MODEL_TTL_SEC = 300` (`engine.py:240`). Поэтому после переключения обратно на «Стабильный» адаптер пересоздаётся сразу (по fingerprint), но RU-распознавание может ещё до 5 минут идти через whisper, пока маркер не истечёт. Самолечится по TTL; чистка маркера при смене транспорта — вне объёма волны.
