# S64-хвост: re-paste после Cmd+Shift+R (QuickReplace → буфер обмена)

Дата: 2026-07-19. Статус: спека утверждена устно (владелец выбрал вариант
«копия в буфер + подсказка»), самопроверена на Fable 5. Скоуп: **последний
незакрытый пункт S64 Inline Correction Loop** — «повторный paste без нового
цикла записи». Остальные пункты S64 уже закрыты ранее другими фичами:
`QuickEditOverlay.swift` (правка до вставки + «+ Словарь» на лету) и
`main+QuickReplace.swift` (Cmd+Shift+R, `replace_word_in_last_transcript`
с closed-loop auto-learn в `stt_hotwords`).

## Проблема

После Cmd+Shift+R исправление сохраняется в историю, но неверный текст уже
улетел в целевое приложение. Пользователю приходится вручную открывать
историю, копировать исправленный текст и вставлять. Acceptance S64:
«исправление последней фразы выполняется за 2-3 действия» — сейчас их 5+.

## Решение (одобрено владельцем из 3 вариантов)

Копия в буфер + подсказка. НЕ слепая автовставка (фокус к моменту правки
мог уйти в другое окно — риск вставки в пароль/терминал) и НЕ третья кнопка
в диалоге (лишний выбор). После успешной замены исправленный полный текст
кладётся в буфер, пользователь сам решает куда вставлять: Cmd+Shift+R →
(выделить старый текст в целевом приложении) → ⌘V. Ровно 2-3 действия.

## Изменения

Один файл: `native/KrabEarAgent/Sources/KrabEarAgent/main+QuickReplace.swift`.
Новых IPC-методов и настроек НЕТ — backend `replace_word_in_last_transcript`
уже возвращает `new_text` (полный исправленный текст) в успешном ответе
(`llm_ops_service.py`, поле присутствует только при `ok:true`; в privacy mode
backend отказывает ДО чтения истории — транскрипт в буфер в privacy mode
физически попасть не может).

1. **Success-ветка** (`ok == true`): `pasteService.putToClipboard(newText)`
   (тот же установленный метод, что «Копировать» у быстрых заметок), где
   `newText = result["new_text"] as? String`. Если `new_text` вдруг
   отсутствует/пуст (защитный guard) — буфер не трогаем, тост без хвоста.
2. **Текст тоста**: к существующему сообщению добавляется хвост
   «Скопировано — ⌘V». Глиф «⌘» установлен в кодовой базе
   (`HistoryPanelController+KeyboardShortcuts.swift`) — глиф-гейт AGENT-J/M
   пройден. Формулировка НЕ обещает «заменить» — вставка поверх старого
   текста в чужом приложении невозможна без выделения, пользователь делает
   это сам.
3. **Off-main hardening (та же функция, AGENT-3 класс)**: существующий
   `callWithRecovery` зовётся синхронно на main thread из completion
   алерта. Комментарий «< 50 ms» покрывает только happy path: на
   деградированном пути внутри — sync IPC → `backendSupervisor.
   restartIfDead()` (полный цикл рестарта backend) → повторный sync IPC,
   всё на главном потоке = AppHang. Перенести вызов в
   `DispatchQueue.global(qos: .userInitiated)`, результат (тост/алерт и
   `putToClipboard`) — обратно на main. Мы редактируем ровно эту ветку —
   это направленный hardening, не посторонний рефакторинг.

## Ошибочные пути

Не меняются. Буфер трогается ТОЛЬКО при `ok:true` — `word_not_found` /
`no_recent_history` / `item_not_found` / `missing_words` / IPC-ошибки
показывают прежние алерты, буфер пользователя не перезаписывается.

## Тесты (TDD)

Source-contract тест (образец `QuickCaptureWiringTests`) в новом/существующем
файле тестов:
- success-ветка `onReplaceWordRequested` содержит `putToClipboard` И читает
  `new_text` (оба грепа в теле функции);
- тост содержит подстроку «Скопировано»;
- IPC-вызов внутри `onReplaceWordRequested` уходит off-main: тело содержит
  `DispatchQueue.global` (и НЕ содержит прямого sync `callWithRecovery` вне
  него — формулировка грепа уточняется при написании RED-теста).

## Вне скоупа

- «Команда повторить перевод» из исходного S64 — формулировка устарела
  (относилась к до-Live-Translation эпохе); при реальной потребности —
  отдельная мини-волна.
- Автовставка в запомненное приложение-цель (вариант «Заменить и вставить»)
  — осознанно отвергнута владельцем в пользу безопасного буфера.
