## 1. Корень

`KrabEar/backend/privacy_audit.py:28`:

```python
_DEFAULT_LOG_PATH = (
    Path.home() / "Library" / "Application Support" / "KrabEar" / "privacy_audit.log"
)
```

Путь захардкожен **дважды мимо всех механизмов конфигурации**: он не читает env и не
зависит от `data_dir`. `PrivacyAuditLogger` — синглтон (`get_instance`), поэтому любой
код, зовущий `get_privacy_audit_logger()` без явного патча, пишет в боевой журнал.

Два независимых потребителя этой дыры:

1. **Тесты.** Точный подсчёт: `handle_purge_all_data` зовут **20** тестовых файлов, из них
   `privacy_audit` вообще упоминают лишь **3** — то есть **17 файлов пишут в боевой журнал
   напрямую**. `conftest.py` не изолирует его ничем. Это источник 44 907 записей.
2. **Dev-backend.** Запуск с `--data-dir <throwaway>` всё равно пишет в БОЕВОЙ журнал.
   Таких скриптов **семь** (список получен grep'ом по `--data-dir` в `scripts/`, см. §C3).
   Все они обещают в комментариях «never touches your prod data» — для этого журнала
   обещание не выполняется.

   🔴 Первая редакция спеки называла три скрипта и утверждала «все три». Четыре
   пропущенных нашёл адверсариальный гейт. Урок переносимый: список потребителей
   пишется grep'ом по механизму (`--data-dir`), а не по памяти — иначе гард закрывает
   ровно те случаи, которые автор и так помнил.

CLAUDE.md уже предписывает лекарство для этого класса — «an env var for the base path +
a throwaway forced in conftest BEFORE the app import». `privacy_audit.log` из-под правила
выпал.

## 2. Дизайн

### C1. Резолв пути — ленивая функция вместо константы

Заменить модульную константу `_DEFAULT_LOG_PATH` на функцию:

```python
_LOG_FILENAME = "privacy_audit.log"
_ENV_DIR_VAR = "KRAB_EAR_PRIVACY_AUDIT_DIR"


def _default_log_path() -> Path:
    """Базовый каталог журнала: env-переменная, иначе home-rooted дефолт.

    Пустое/пробельное значение трактуется как «не задано» — fail-safe в сторону
    боевого дефолта, чтобы опечатка в окружении не увела compliance-журнал в CWD.
    """
    raw = os.environ.get(_ENV_DIR_VAR, "")
    if raw.strip():
        return Path(raw).expanduser() / _LOG_FILENAME
    return Path.home() / "Library" / "Application Support" / "KrabEar" / _LOG_FILENAME
```

Конструктор: `self._log_path = log_path if log_path is not None else _default_log_path()`.

**Почему функция, а не чтение env в константу.** Константа вычисляется на импорте
модуля, и тогда изоляция становится зависимой от порядка импортов — ровно тот класс мин,
что уже кусал репозиторий трижды (`sys.modules`-стабы без снятия, chunk-pollution
`rest_server`, reload-вариант того же). Функция снимает зависимость от порядка целиком:
значение читается в момент создания инстанса.

**Почему `os.environ` напрямую, а не `settings` из `core/config.py`.** `privacy_audit.py`
— листовой модуль без единого проектного импорта; втягивание `config` создало бы
циклическую зависимость с `backend.service`. Имя переменной при этом совпадает с
конвенцией `KRAB_EAR_*` (`env_prefix` в `config.py:117`), так что при будущем переносе
в pydantic-настройки имя не меняется.

**Каталог, а не файл.** Переменная указывает на КАТАЛОГ: рядом с журналом живёт
`privacy_audit.key`, который берётся как `self._log_path.parent` в `_load_or_create_key`.
Ключ переезжает вместе с журналом автоматически — отдельной переменной не нужно.

**Почему НЕ переезд под `data_dir`.** Соблазнительно и закрыло бы dev-загрязнение одним
движением, но `scripts/purge_coverage_allowlist.txt:42` явно опирается на то, что журнал
home-rooted и потому не обнаруживается сканером покрытия purge. Переезд под `data_dir`
столкнул бы журнал с CI-гардом `audit_purge_coverage.py` и означал бы, что
compliance-журнал обязан стираться при wipe — прямо противоположное его назначению.
Боевой дефолт остаётся home-rooted; меняется только ВОЗМОЖНОСТЬ переопределить.

### C2. Принудительная изоляция в conftest

В `KrabEar/tests/conftest.py`, на уровне модуля, сразу после `import os` (строка 36) —
до любого импорта приложения (проверено grep'ом: ни одного `import backend`/`import core`
на уровне модуля; все 13 упоминаний `backend.`/`core.` находятся внутри фикстур, то есть
ленивые).

🔴 `tempfile`, `atexit`, `shutil` в `conftest.py` **сейчас не импортированы** — их надо
добавить вместе с блоком (проверено).

```python
_PRIVACY_AUDIT_TMPDIR = tempfile.mkdtemp(prefix="krab_ear_privacy_audit_")
os.environ["KRAB_EAR_PRIVACY_AUDIT_DIR"] = _PRIVACY_AUDIT_TMPDIR
atexit.register(shutil.rmtree, _PRIVACY_AUDIT_TMPDIR, True)
```

**Присваивание, а не `setdefault`.** `setdefault` оставил бы дыру: унаследованная от
родительской оболочки переменная (например, указывающая на боевой каталог) молча
победила бы изоляцию. Тестовое окружение не имеет права уважать внешнее значение.

**Под `pytest -n auto`** каждый xdist-воркер — отдельный процесс, импортирует conftest
сам и получает СВОЙ `mkdtemp`. Гонки за один файл между воркерами не возникает.

Плюс autouse-фикстура:

```python
@pytest.fixture(autouse=True)
def _isolate_privacy_audit_singleton():
    yield
    from backend.privacy_audit import PrivacyAuditLogger
    PrivacyAuditLogger.reset_instance()
    Path(_PRIVACY_AUDIT_TMPDIR, "privacy_audit.log").unlink(missing_ok=True)
```

Два эффекта, и они связаны: сброс синглтона не даёт тесту пронести путь/состояние в
соседний, а удаление файла держит журнал пустым — иначе `_read_chain_tip()` в
конструкторе стал бы O(N) по растущему за прогон файлу и к концу сьюта каждое создание
инстанса платило бы за десятки тысяч строк. Удалять файл БЕЗ сброса синглтона нельзя:
`_last_hash` остался бы указывать на стёртую запись. Ключ (`privacy_audit.key`) не
удаляем — он переиспользуется, генерировать 32 байта энтропии на каждый тест незачем.

**Проверено, что сброс безопасен.** Autouse-сброс синглтона опасен, если какой-нибудь
тест ставит логгер один раз на класс (`setUpClass`) — сброс после первого же метода
обесточил бы остальные. Grep показал: ни один тест не присваивает
`PrivacyAuditLogger._instance` напрямую и ни один из `test_privacy_audit*.py` /
`test_privacy_dashboard*.py` не использует `setUpClass`. Существующие тесты самого
логгера конструируют его с ЯВНЫМ `log_path`, поэтому ни изоляция, ни сброс их не задевают.

### C4. Дашборд — один поток вместо двух проходов

`_handle_get_privacy_dashboard` (`service.py:4482–4497`) делает `total_count()` +
`read_entries(limit=max(total_events, 1))` — два полных чтения файла плюс материализация
всего журнала в список ради трёх агрегатов. Заменить на один потоковый проход:

```python
def summarize(self) -> dict[str, Any]:
    """{total, last_ts, by_type} за один проход, без материализации журнала."""
```

**Честная оценка выигрыша — этот пункт НЕ является фиксом скорости дашборда.** Прямой
замер на боевом 50k-журнале: `total_count` 0.02 с + `read_entries(all)` 0.18 с ≈ **0.2 с**
из наблюдавшихся 2.0 с. Параллельная сессия независимо померила эффект архивации:
2.0 с → 1.44 с. Оба замера сходятся в одном: чтение журнала не было главным источником
задержки. Основной вклад — почти наверняка `get_storage_info` + `get_history_stats` по
12 746 записям / 527 МБ, и это **отдельная волна**, сюда не тащится.

`summarize()` делается не ради секунд, а чтобы убрать неограниченную O(N) материализацию
в список: после изоляции журнал растёт только от реальных событий, но потолка у него
по-прежнему нет. Кэш не вводится — после архивации файл маленький, кэш добавил бы
инвалидацию без выигрыша.

🔴 **Обязательный довесок: перенацелить `test_audit_failure_returns_defaults`.**
`KrabEar/tests/test_privacy_dashboard.py:465-487` симулирует отказ, ломая
`broken_audit.total_count`. После перехода дашборда на `summarize()` этот метод
перестаёт вызываться — а `summarize()` на несуществующем файле штатно вернёт
`0 / None / {}`, ровно те значения, которые тест ждёт от ветки обработки ошибки. Тест
останется **ЗЕЛЁНЫМ и перестанет проверять что-либо**: это класс
«test-validates-the-hole», против которого в репозитории есть именной CI-гард
(`audit_dispatch_test_targets.py`). Симуляцию отказа надо перевести на `summarize`,
а после — доказать, что тест снова живой: временно убрать `try/except` вокруг
audit-секции и убедиться, что он КРАСНЕЕТ.

Найдено адверсариальным гейтом. Ценность находки именно в том, что обычная страховка
«если тест упал — разбираться» здесь не срабатывает: падения не будет.

## 4. Граница с параллельной сессией

Договорённость с `xenodochial-cannon-3fc148` зафиксирована обеими сторонами.

| Зона | Владелец |
|---|---|
| Резолв пути (строка 28 → `_default_log_path()`), часть конструктора про путь, `conftest.py`, smoke-скрипты, `summarize()` | **эта волна** |
| Весь цикл `compute → write → update` в `log_event`, перечитывание chain tip из файла под локом, поведение при недоступности лока, права `600` при создании файла | **смежная волна** |

Права `600` переданы туда сознательно: файл создаётся в `open("a")` внутри `log_event`,
то есть в чужой зоне; делать это должен тот, кто переписывает открытие.

Пересечение — только строка 28 и резолв пути в конструкторе. Механику записи эта волна
не трогает; мержимся отдельными PR.

**Статус смежной волны на момент ревью:** её фикс уже закоммичен (`7923f15b`) — цепочка
перечитывает tip из файла под `flock`, добавлены константы `_LOG_FILE_MODE = 0o600` и
`_MAX_TIP_SCAN_BYTES`. Передача прав `600` принята.

🔴 **Все номера строк в этой спеке и в плане — на момент написания.** Соседний коммит
уже сдвинул `privacy_audit.py` примерно на +7 строк (константы вставлены НАД строкой 28).
Правки заданы точным ТЕКСТОМ, а не номерами, поэтому переживут мерж; но сверяться при
исполнении надо по тексту, номер — только подсказка, где искать.

**Совместимость проверена по коду обеих веток:** её дифф не трогает ни первую строку
`__init__`, ни хвост класса после `clear()` (куда встаёт `summarize()`), ни
`_load_or_create_key`. Обратно: наша autouse-фикстура, удаляющая лог-файл, её фикс не
ломает — после её правки tip берётся из файла, и удалённый файл честно даёт `None`
(то есть обоснование фикстуры «иначе `_last_hash` укажет в пустоту» после мержа
станет неактуальным, а сама фикстура — нет; докстринг при мерже поправить).

## 5. Известные ограничения

1. **Прогон через `python -m unittest` не изолируется.** `KrabEar/tests/` не пакет
   (`__init__.py` отсутствует), `conftest.py` — механизм pytest. CLAUDE.md упоминает
   unittest как альтернативный способ запуска; при нём переменная не выставится и запись
   уйдёт в боевой журнал. Не закрывается без test-aware кода в проде (проверка
   `PYTEST_CURRENT_TEST` в `privacy_audit.py` — именно тот запашок, которого стоит
   избегать). Митигация — документирование: канонический раннер репозитория и оба
   CI-гейта работают через pytest.
2. **Ретроспективно ничего не чинится.** Архив содержит 50 041 запись, где тестовое
   неотличимо от реального, и разрыв цепочки с 2026-06-03. Волна гарантирует
   достоверность только НОВОГО журнала.
3. **Окно до деплоя — ПРОВЕРЕНО, риск §0.2 НЕ реализовался.** Опасение было: не
   перезапущенный REST-процесс запишет событие с устаревшим `prev_hash`. Живая проверка
   позже в тот же день: REST перезапущен (pid сменился 40418 → 73904), а `verify_chain()`
   нового журнала — `{valid: True, checked: 146}`. Свежая цепочка цела. Требование
   деплоить с `--with-rest` остаётся, но как профилактика, а не как незакрытая дыра.

4. **Синглтон, странденный подменой модуля, фикстура не сбросит.** Если тест положил в
   `sys.modules["backend.privacy_audit"]` стаб, а `service.py` уже сделал from-import
   настоящего класса, старый объект с `_instance` для сброса недостижим. Изоляция ПУТИ
   при этом сохраняется (env выставлен до всего), протечь может только hash-состояние
   между тестами. Принимается как известное ограничение: закрывать пришлось бы обходом
   всех живых ссылок, что дороже пользы.

5. **Течь активна прямо сейчас и рефилит журнал с той же скоростью.** Замер через 18
   минут после архивации: новый журнал уже содержал 146 записей, из них **131 (90%)
   `purge_all_data`** — тот же процент, что у 22-МБ архива. Это не оценка, а факт с
   боевой машины: пока волна не задеплоена, каждый прогон тестов заново засыпает свежий
   compliance-журнал.

🔴 `test_privacy_dashboard.py` — кандидат на падение по существу: если он утверждает
что-то о `total_events`, изоляция изменит счётчик. Разбирать как настоящую находку, а не
подгонять ассерт.

```bash
scripts/pre_merge_py312_check.sh <изменённые тестовые файлы>   # ubuntu-parity
```

сканер не должен обнаружить новый file-backed store. Если обнаружит — значит резолв пути

```bash

```

🔴 `--with-rest` обязателен (§0.2) — REST второй писатель журнала. Голый
`launchctl kickstart` запрещён правилом репозитория: под активной диктовкой он
безвозвратно теряет запись.

## 7. Что осознанно НЕ делается

- **Переезд журнала под `data_dir`** — конфликт с `purge_coverage_allowlist` (§C1).
- **Фильтрация/перешивка содержимого журнала** — владелец выбрал честный архив; переписывание
  compliance-записи задним числом хуже для аудита, чем архив, и всё равно не отличило бы
  тестовые не-purge события от реальных.
- **Ротация журнала** — после изоляции рост определяется реальными событиями; вводить
  механизм под гипотетическую нагрузку рано.
- **Ускорение `get_storage_info` / `get_history_stats`** — настоящий источник 1.44 с,
  но это отдельная волна (§C4).
- **Маркировка происхождения записи (pid/процесс)** — сделала бы тестовое отличимым от
  реального и выглядит соблазнительно, но это лишняя метадата в privacy-журнале, а после
  изоляции задача решается на уровне пути. Отвергнуто как лечение симптома.
