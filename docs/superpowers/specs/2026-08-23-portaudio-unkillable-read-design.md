# Неубиваемый аудио-тред: blocking `Pa_ReadStream` без таймаута

Дата: 2026-08-23. Автор: Claude (Opus 5). Ревью v1: Fable — **REDESIGN**, все
находки прогейчены лично против кода и живых замеров, учтены ниже (§9).
Статус: **v3 — APPROVE** (ре-ревью Fable: оба CRITICAL закрыты; четыре
правки без изменения архитектуры внесены здесь).

## 1. Проблема (улики, не гипотеза)

Тред аудио-захвата навсегда застревает внутри PortAudio; `stop()` не может его
завершить; лечится только рестартом backend-процесса.

### 1.1 Масштаб (лог-анализ за 30 суток)

| Сигнатура | Случаев |
|---|---|
| `OpenWakeWordAdapter: тред слушателя не вышел за 3.0s` | **238** |
| `stop_recording: audio worker завис — отдаю recorder_timeout` | **81** |
| `handle_request завис дольше 180с (method=stop_recording)` | 7 |
| Клинов, закончившихся принудительным рестартом backend | **61%** |
| Мягкое самолечение сработало | **3.2%** (4 из 125) |

Расщепление популяции: **41.9%** клинов — в пределах 120 с ПОСЛЕ записи,
**40.7%** — вообще без записи в ±120 с (ближайшая — за часы). Значит гейт
«не открывать стрим сразу после диктовки» (W7) не может вылечить класс: он
адресует меньше половины случаев. Каждый пятый recorder-hang и wake-word клин
— одно и то же событие (совпадение в пределах 60 с).

### 1.2 Что показал sample зависшего процесса (`/tmp/backend_hang_sample_2053.txt`)

Тред `OpenWakeWordListener`, 2360 сэмплов из 2360:

```
cdata_call (_cffi_backend) → ffi_call_SYSV (libffi)
  → ReadStream (libportaudio.dylib) + 44
      → usleep → nanosleep → __semwait_signal      [2358 / 2360]
```

1. `Pa_ReadStream` — **busy-wait `usleep`-цикл без таймаута**: спит, пока ring
   buffer не наберёт запрошенные фреймы. Наполнять некому — спит вечно.
   (Отсюда же следствие для §5: опрос `read_available` не добавляет нагрузки —
   блокирующее чтение и так реализовано опросом.)
2. **В процессе НОЛЬ CoreAudio IO-тредов** (`grep -cE "IOThread|HAL_|IOProc"` →
   `0`) при живой очереди `com.apple.audio.proxy-event`. `sd.InputStream`
   открылся, `Pa_StartStream` вернул успех, но аудио-движок не запустил ввод:
   **стрим мёртв с рождения**.
3. Процесс здоров: главный тред в `accept()`, IPC отвечает.

### 1.3 Почему тред неубиваем (код)

`openwakeword_adapter.py:794-810`:

```python
with sd.InputStream(...) as stream:
    while not self._stop_event.is_set():
        audio_chunk, _ = stream.read(chunk_size)   # блокировка без таймаута
```

`_stop_event` проверяется **только между** чтениями → зависший `read()` делает
проверку недостижимой. `stop()` ставит событие и делает `join(3.0)`, но join не
прерывает C-вызов, а объект `stream` — локальная переменная, поэтому снаружи
нельзя даже позвать `abort()`. Рычага не существует.

**Тот же дефект в рекордере диктовки** — `recorder.py:597` и `:614`
(sibling-asymmetry). Callback-режим PortAudio не используется в проекте нигде.

## 2. Цели

1. Тред выходит из **read-цикла** по `stop_event` за ≤ 2×`POLL_SEC`.
   🔴 Выход из `with`-блока (`Pa_StopStream`/`Pa_CloseStream`) остаётся
   неотменяемым C-вызовом — это признанный остаточный риск (§6), покрытый
   существующими THREAD_HUNG-дискриминатором и wedged-эскалацией. Обещание
   «≤200 мс независимо от состояния CoreAudio» из v1 отозвано как перепромис.
2. «Мёртвый с рождения» стрим детектируется за секунды и **не маскируется под
   легитимную паузу**: он обязан дойти до эскалации, если не лечится (§4.3).
3. Диктовка не теряется: рекордер получает ту же прерываемость и **громкий**
   сигнал вместо тихого зависания.
4. Ни один существующий сторож не теряет своего сигнала.

## 3. Не входит в scope

Callback-режим PortAudio целиком (§5-B); вынос захвата в отдельный процесс
(§5-C); правки Swift; политики `AudioSelfHealer`/`AudioReinitCoordinator`.

## 4. Решение

### 4.1 Guarded read — прерываемость

Инвариант: **`read()` вызывается только когда `read_available >= chunk_size`**,
поэтому не может блокироваться дольше длительности чанка.

```python
while not stop_event.is_set():
    avail = _read_available_or_starved(stream)     # см. §4.4
    if avail < chunk_size:
        if stop_event.wait(POLL_SEC):             # выход за ≤ POLL_SEC
            break
        _note_starvation(...)                      # см. §4.2
        continue
    chunk, overflowed = stream.read(chunk_size)    # гарантированно не блокирует
```

Живой замер (2026-08-23, PortAudio V19.7.0-devel, sounddevice 0.5.5): открытие
стрима 106 мс, прогрев до первых кадров ≈ 0.2 с, ожидание перед `read()`
0–81 мс, `read_available` растёт 0 → 1280 → 2560 → 3840.

### 4.2 Критерий голодания (перестроен после CRITICAL-1)

🔴 **`stream.time` из критерия ИСКЛЮЧЁН.** Опровергающий эксперимент
(2026-08-23): на **остановленном** стриме `stream.time` натикал 1.005 с за
1.0 с реального времени при `read_available == 0`. `Pa_GetStreamTime` на
macOS — хост-часы, не привязанные к IO-callback (docstring sounddevice:
«Starting and stopping the stream does not affect the passage of time»).
AND-условие из v1 не сложилось бы никогда — детектор был бы мёртвым кодом,
а метрика §8 недостижимой. `stream.time` остаётся **только диагностическим
полем** в логе события.

Критерий: `read_available == 0` непрерывно дольше `stream_starve_sec`
(дефолт 3.0 с; запас ×15 к измеренному прогреву) **И** не выполняется ни одно
легитимное условие голодания:

| Легитимный источник | Обработка |
|---|---|
| **Активная запись/встреча** (`is_recording()`) | сброс таймера голодания. 🔴 Обязательно: meeting-запись НЕ снимает слушатель (амендмент C2, `d18c5e56`) — адаптер легитимно голодает всю встречу. Без гейта детектор открыл бы второй тап под записью = инцидент F6 2026-08-01 (потеря диктовки). `is_recording()` упал → fail-safe «идёт запись». |
| Sleep/wake ноутбука | `time.monotonic()` на macOS спит вместе с машиной → ложного мгновенного триггера нет; один цикл выхода после пробуждения штатен, гасится backoff (§4.3). |
| Смена/отключение устройства | голодание настоящее, выход и переоткрытие — желаемое лечение. |
| privacy / TTS / conversation | слушатель уже снят Set-причинами до голодания — до критерия не доходит. |

### 4.3 Владелец переоткрытия и лестница эскалации (после CRITICAL-2)

Прогейчено по коду: при выходе цикла `_cleanup_session_after_loop_exit()`
зануляет `_active_model` → watchdog видит `session_active = False` и,
не найдя `model is not None`, попадает в ветку «чистая пауза» →
`_reset_episode()` (`wake_word_watchdog.py:202-225`). Плюс каждая новая сессия
получает grace-окно `staleness < stale_sec` (`:245`). Итог: если бы тред просто
выходил по исключению, получился бы **тихий вечный цикл** respawn → starve →
cooldown, в котором `wedged` недостижим. v1 в этом виде уничтожала последний
рубеж.

Решение — **тред не лечит себя сам** (никакого reopen внутри цикла: это второй
лекарь того же сигнала и гонка с `_maintenance`-окном координатора):

1. Тред выходит, помечая причину: адаптер получает поле `_starved_since`
   (монотонное время) и счётчик `_consecutive_starve_exits`.

   🔴 **Жизненный цикл этих полей задан явно** (ре-ревью HIGH-1; зеркальный
   близнец бага, уже чиненного в `stop():289-296`):
   - они **переживают** `_cleanup_session_after_loop_exit()` — иначе исполнитель
     зачистит их «симметрично» остальным сессионным полям и сигнал умрёт
     в момент рождения;
   - они **НЕ переживают публичный `stop()`** — пользователь выключил wake word
     или включил privacy, слушатель снят легитимно; застывший флаг заставил бы
     watchdog дозреть до `wedged` и рестартовать backend на выключенной фиче;
   - счётчик растёт **только** на self-exit'ах цикла по голоданию, не на любых
     остановках.
2. `heartbeat()` отдаёт новый ключ `starvation_active` — сессия голодает
   **не** из-за паузы. Watchdog получает ветку `_handle_starved_stream()` по
   образцу уже существующей `_handle_blocked_start()` (W8): эпизод **не
   сбрасывается**, аномалия ведётся до `wedged`.
3. Перезапуск сессии остаётся у существующих владельцев (self-heal поллера /
   `AudioReinitCoordinator`) — новых конкурирующих лекарей не появляется.
4. 🔴 **Писатель `wedged` — ТОЛЬКО watchdog** (действующая конвенция кода:
   `wedged — домен watchdog'а, не трогаем`, `openwakeword_adapter.py:719`;
   пишут `wake_word_watchdog.py:354,368`). Адаптер лишь ведёт счётчик и
   отдаёт его в `heartbeat()`. Ветка `_handle_starved_stream` эскалирует
   **по счётчику** (`_consecutive_starve_exits >= _MAX_STARVE_EXITS`, дефолт 3,
   без единого живого чанка между выходами), а НЕ по собственному таймеру —
   два критерия и два писателя одного side-effect дали бы двойной пуш ошибки
   и разъезжающиеся пороги. ErrorBus пушится только из `_escalate()` с reason
   `"starved_stream"`. Счётчик обнуляется первым же ненулевым чанком.
5. Backoff между попытками — существующий breaker
   (`_consecutive_stream_failures` → cooldown 60 с), но теперь он **связан с
   эскалацией**, а не ведёт в тупик.

🔴 Осознанное ограничение: гипотеза «переоткрытие внутри процесса вылечит
мёртвый стрим» **не доказана** — улика §1.2 (ноль IO-тредов при живой
proxy-очереди) совместима с версией «сломан процессный сеанс coreaudiod», где
новый стрим родится таким же мёртвым. Поэтому лестница обязана доводить до
рестарта backend, а метрика §8 меряет не «ноль рестартов», а «ноль тихих
простоев».

### 4.4 `read_available` может бросать

`sounddevice._check` бросает `PortAudioError` при отрицательном коде
(`sounddevice.py:1184`). Исключение трактуется как **голодание** (не как
«гейт выключен»): иначе fail-open вернул бы нас в блокирующий `read()` — ровно
то, что чиним.

### 4.5 Политика рекордера при голодании ПОСРЕДИ диктовки

**Не переоткрывать** (дыра в аудио + рассинхрон spill). Завершать по образцу
существующего max-duration-пути: собрать `_pending_result`, закрыть spill,
поднять **новый громкий** код ErrorBus `audio.capture_starved` (сиблинг
`audio.max_duration_reached`). Пользователь обязан узнать, что захват умер, а
не диктовать в пустоту. Стоп-путь и R2-поколения не меняются.

## 5. Отклонённые альтернативы

**B. Callback-режим + очередь.** Идиоматичен, но: колбэк исполняется в
realtime-потоке (запрет на локи/логи — новый класс рисков), клин
`Pa_CloseStream` остаётся, объём правки тестов такой же, как у A (§7).
**C. Отдельный процесс захвата** (образец `mlx_whisper_worker`). Полная
изоляция, но 2–3 волны и новый IPC-контракт. **План Б**, если после A частота
не упадёт. **D. Гейт по времени после записи** — уже сделан в W7, лечит ≤42%
случаев (§1.1).

## 6. Остаточные риски (признаны, не замаскированы)

1. Клин в `Pa_StopStream`/`Pa_CloseStream` при выходе из `with`.
   `stream.abort(ignore_errors=True)` не бросает, но **может блокироваться** и
   не убирает `stop()+close()` из пути `__exit__`. Покрытие: THREAD_HUNG +
   wedged (потому и сохраняются).
2. Переоткрытие может не лечить (§4.3) — покрытие: лестница до рестарта.
3. Первый длинный прогон (встреча) — обязательный смок для нового детектора
   (правило проекта о сторожах).
4. **Медленное пробуждение внешнего интерфейса после sleep/wake** может дать
   3 подряд starve-выхода легитимно (поллер ретраит ~10 с; устройство, не
   ожившее за 30–40 с) → ложный `wedged` и рестарт backend на пустом простое.
   Принято осознанно: цена — рестарт в момент, когда захвата всё равно нет.
5. **«Хлопающий» стрим** (один живой чанк → голодание → снова) никогда не
   эскалирует: счётчик обнуляется каждым чанком. Принято осознанно —
   частичная работа лучше рестарта.

## 8. Тесты (RED обязан падать по правильной причине)

1. `read()` не вызывается, пока `read_available < chunk` (фейк считает вызовы).
2. `stop_event` во время голодания → выход за ≤ 2×POLL (жёсткий таймаут в тесте).
3. Мёртвый стрим (`read_available` всегда 0) дольше `stream_starve_sec` →
   выход с `starvation_active=True`, `stop()` возвращает **True**.
4. 🔴 Голодание при `is_recording()==True` → детектор НЕ срабатывает, тап НЕ
   переоткрывается (анти-регресс к C2/F6).
5. Легитимная тишина (буфер наполняется, чанки нулевые) → детектор молчит.
6. Watchdog: `starvation_active` → эпизод НЕ сбрасывается, ведётся аномалия;
   `_MAX_STARVE_EXITS` подряд → `wedged` + ErrorBus (путь эскалации ЖИВ).
7. Живой чанк обнуляет `_consecutive_starve_exits`.
8. `read_available` бросил `PortAudioError` → трактуется как голодание.
9. Рекордер: starve mid-recording → воркер вышел, чанки и spill целы, `stop()`
   отдал накопленное, ErrorBus получил `audio.capture_starved`.
10. Source-контракт (AST, не подстрока): в обоих файлах нет `stream.read(` без
    предшествующей проверки доступности.

## 9. Настройки, наблюдаемость, откат

- Killswitch `audio_guarded_read_enabled` (дефолт `True`) — правка касается
  ОБОИХ путей захвата; без рубильника откат = revert + redeploy.

## 11. Метрика успеха

- `OpenWakeWordAdapter: тред слушателя не вышел за 3.0s` — **0** за 72 ч
  (сейчас 3–42/сутки).
- `stop_recording: audio worker завис` — **0** (сейчас до 27/сутки).
- Принудительных рестартов backend по аудио-причине — 0; при этом каждый
  неизлечимый случай виден как `wedged` + ErrorBus (тихих простоев — 0).
- Ни одной потерянной диктовки.
