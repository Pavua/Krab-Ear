# Волна S3: флип рубильника и вывод легаси-REST — дизайн

Дата: 2026-07-31 · Статус: **СПЕКА** (черновик на ревью) · Автор: Opus 5.
Родительская спека: `2026-07-16-m-series-rest-merge-design.md` (серия M целиком).
Предшественники: M1 (app-factory, закрыта 16-07), M2 (опт-ин in-process REST,
закрыта и задеплоена 30-07, PR #1897).
Роадмап: `docs/ROADMAP-2026H2.md` §3.1.

Эта спека **уточняет и в двух местах отменяет** §5 родительской спеки. Причина —
финальное adversarial-ревью диффа M2 нашло восемь дефектов, взводящихся именно
флипом рубильника, а разведка 31-07 показала, что §5 описывает устаревшее
состояние соседнего репозитория. Родительская спека остаётся источником правды
по архитектуре слияния; эта — по составу и порядку работ S3.

## 0. Исходное состояние (проверено лично 30-31 июля)

- Рубильник `REST_IN_PROCESS_ENABLED` живёт в проде и выключен:
  `get_diagnostics.rest_in_process = {enabled:false, running:false, port:null, error:null}`.
- Мост `EventBridge` доказан живыми данными: `state=up, sent=3, dropped=0, failed=0`.
- Отдельный REST-юнит `ai.krab.ear.rest` работает (`KeepAlive=true`,
  `ThrottleInterval` не задан → действует дефолт launchd, а не 5 с как у backend-юнита).
- Весь код слияния уже в проде. **S3 — это не новая архитектура, а одна строка
  дефолта плюс закрытие восьми дефектов и операционная зачистка.**

## 1. Инвариант волны

Флип не должен менять наблюдаемое поведение системы ни для владельца, ни для
Voice Gateway — кроме исчезновения второго процесса. Всё, что было заметно
снаружи (порт, схемы ответов, SSE-подписки, auth, каталог данных), обязано
остаться побайтово тем же.

Из инварианта следует жёсткий порядок: **флип идёт последним**. Любая задача,
меняющая дефолт до закрытия блокеров, воспроизводит ровно те отказы, ради
которых волна затевается.

## 2. Решения по восьми находкам ревью M2

Нумерация сохранена из отчёта финального ревью, чтобы её можно было сверить.

### Р3 (находка 3) — `settings.DATA_DIR` не совпадает с `--data-dir`

**Проблема.** Каталог данных попадает в процесс двумя независимыми,
разнотипными каналами: backend получает его аргументом `--data-dir` (живёт в
локальной переменной `main()` и доходит только до `StateStore`), а
`rest_server.py` читает `settings.DATA_DIR` — четырьмя обращениями:
module-level `StateStore` (713), `TEMP_DIR` (783-784), `RestAuth` (413),
bridge-токен (481). Сегодня оба канала случайно указывают в один каталог,
потому что rest-плист несёт `KRAB_EAR_DATA_DIR`, а backend-плист — нет.
После флипа REST переезжает под backend-плист и теряет переменную.

Разведка подтвердила блокер эмпирически: каталог `~/.krab_ear_data` на машине
владельца существует и активно пишется (история 15.5 МБ, `temp_uploads` с
артефактами вида `<12hex>_<basename>.wav` — точный паттерн `rest_server.py:1540`).
Механизм «что угодно без `--data-dir`/`KRAB_EAR_DATA_DIR` попадает в
`~/.krab_ear_data`» реален уже сегодня.

**Решение.** Выровнять `settings.DATA_DIR` с `--data-dir` **до** того, как
`service.py` вообще импортирует `rest_server`:

1. `KRAB_EAR_DATA_DIR` добавляется в `EnvironmentVariables` backend-плиста —
   ровно та же строка, что уже есть в rest-плисте с 16-07.
2. `install_backend_launchagent.command` генерирует значение аргумента и
   значение переменной **из одной шелл-переменной**, а не из двух независимых
   мест шаблона. Дублирование пути в двух местах одного плиста — источник
   будущего дрейфа, и защищаться от него надо в генераторе, а не комментарием.
3. Source-контракт тест проверяет, что в шаблоне путь в `--data-dir` и путь в
   `KRAB_EAR_DATA_DIR` совпадают буквально. Без теста фикс невидим для
   регрессии: любой, кто уберёт строку «для чистоты», тихо вернёт блокер.

**Отвергнуто: инъекция каталога через `adopt_external_singletons`.** Она чинит
только те объекты, что перечислены явно, и всё равно оставляет фантомный
`StateStore` и `TEMP_DIR.mkdir()`, выполняемые на импорте до подмены. Путь
через переменную окружения убирает больше симптомов меньшей правкой. Явную
инъекцию стоит рассмотреть отдельной волной как hardening — она устраняет сам
класс, а не текущее проявление.

**Риск, который обязан быть закрыт исполнением.** Правка шаблона не меняет
ничего для уже установленных копий. Migrate-скрипт обязан переустановить
backend-юнит через `bootout` + `bootstrap`: `kickstart -k` **не подхватывает**
новые переменные окружения из изменённого plist. Прецедент ошибки известен —
в прошлых миграциях правили только REST-юнит.

### Р4 (находка 4) — мост выключается по настройке, а не по факту

**Проблема.** `EventBridge` сам читает `REST_IN_PROCESS_ENABLED` и выключается
по нему. Стартует мост раньше (`service.py:796`), чем делается попытка поднять
REST (`service.py:827`), и результат `start()` (он возвращает `bool`)
игнорируется. Сценарий отказа: легаси rest-агент ещё держит порт → in-process
REST не встал (fail-open) → но мост уже выключен → SSE-подписчики Swift на
`:5005` глохнут. Это живые партиалы `QuickCapturePanelController` (без
фоллбэка) и `MeetingLivePanelController`. При этом текст ошибки обещает
«Основные функции работают».

**Решение.** Мост перестаёт знать про рубильник. `EventBridge` получает
параметр подавления, `service.py` вычисляет его по **факту**: блок подъёма
REST переезжает выше создания моста, `start()` возвращает результат, и мост
подавляется только когда REST действительно слушает.

Поведение в каждом из трёх случаев:

| Ситуация | REST слушает | Мост |
|---|---|---|
| Рубильник выключен | нет | работает (как сегодня) |
| Рубильник включён, REST встал | да | подавлен — шина одна, echo невозможен |
| Рубильник включён, REST не встал | нет | работает |

Третья строка и есть фикс. Если порт занят легаси-агентом, тот жив и держит
подписчиков — мост нужен. Если порт свободен, а REST не встал по другой
причине, мост уйдёт в существующий backoff — ровно то поведение, что было до
M2. Нового поведения не вводится ни в одной ветке.

### Р5 (находка 5) — диагностика не отличает «выключено» от «упало»

**Проблема.** Внешний `except` в `service.py:828-831` ставит
`self._rest_inprocess = None`, а `_get_rest_inprocess_summary` на `None` отдаёт
`{enabled:false, running:false, port:null, error:null}` — байт в байт то же,
что при выключенном рубильнике. ErrorBus в этой ветке не пушится.

**Уточнение к формулировке ревью (проверено лично).** Дыра **уже**, чем
описано. `InProcessRestServer.start()` документирован как «НИКОГДА не бросает»
и правда возвращает `bool` во всех ветках. Значит внешний `except` ловит
только сбой сборки приложения — импорт `rest_server`,
`adopt_external_singletons`, `create_app()`, конструктор. Самый вероятный в
проде отказ (занятый порт) диагностику не ломает и ErrorBus получает
(`rest.port_conflict`). Немым остаётся структурный сбой сборки.

**Решение.** При сбое сборки поле не обнуляется, а получает лёгкий
объект-надгробие с тем же методом `status()`, возвращающим
`{enabled: true, running: false, port: <порт>, error: <причина>}`. Плюс пуш
ErrorBus новым кодом `rest.startup_failed`.

Почему надгробие, а не флаг: `HealthCheckService` не меняется вообще — он уже
умеет звать `status()` у коллаборатора. Правка локальна в `service.py`.

Почему не строить настоящий `InProcessRestServer` всегда, даже при выключенном
рубильнике: его конструирование требует `create_app()`, а тот тянет импорт
`rest_server` со всем module-level комплектом, включая `AudioEngine`. При
выключенном рубильнике это ровно тот дубль тяжёлого состояния, ради устранения
которого затевалась серия.

### Р6 (находка 6) — надзор launchd потерян и ничем не заменён

**Проблема.** `_serve` при падении `serve_forever` пишет `_error` и логирует —
и всё: ни пуша ErrorBus, ни рестарта, ни watchdog. Раньше `KeepAlive` поднимал
процесс. После флипа смерть REST полностью бесшумна, а Voice Gateway теряет
STT и TTS.

**Уточнение (проверено лично).** Дыра **шире**, чем описано: `get_diagnostics`
не поллится фоново ни в Python, ни в Swift — секция читается только когда
человек открыл панель диагностики. То есть различимость состояний в коде есть,
наблюдателя нет ни одного.

**Решение.** Собственный сторож по образцу `WakeWordWatchdog`, живущий внутри
процесса:

- тик раз в 10 с, проверка `status().running` при включённом рубильнике;
- раз в 30 с — активная проба `GET /health` на loopback с таймаутом 2 с. Без
  неё не ловится состояние «тред жив, `running=true`, но сервер не отвечает» —
  ровно тот класс, что дал живой инцидент wake-word 13 июля;
- лечение — **локальный** `restart()` самого `InProcessRestServer`, без
  единого касания процесса backend;
- анти-шторм по образцу сторожа wake-word: не более 3 лечений в окне 600 с;
- исчерпание лечений → эскалация в ErrorBus новым кодом `rest.wedged`
  (severity `error`, по образцу `audio.wakeword_wedged`) + поле в диагностике.

**Явно отвергнуто: эскалация в `BackendSupervisor.forceRestartBackend()`.**
Единственный существующий на Swift-стороне рычаг перезапускает **весь**
backend через `kickstart -k`. Для отказа REST это цена потерянной диктовки или
встречи — ровно инцидент 22 июля, ради которого написан
`safe_backend_restart.command`. Деградация REST предпочтительнее потери записи
владельца. Тот же принцип уже применён в M2 к `_exit_poisoned_rest_process`.

**Открытый вопрос для исполнения.** Сторож обязан знать про легитимные паузы,
иначе повторит ошибку сторожа wake-word, который принял запись встречи за
зависание. Кандидаты на исключение: активная запись и активная встреча.
Требуется проверить, влияют ли они на отзывчивость `/health` вообще; если нет —
исключений не вводить, лишний гейт хуже отсутствующего.

### Р7 (находка 7) — нет дренажа запросов, порядок останова инвертирован

**Проблема.** `stop()` не ждёт хендлеры. Проверено на живом окружении:
werkzeug 3.1.8 отдаёт `ThreadedWSGIServer` с `daemon_threads = True`, а
`socketserver._Threads.append` ранним `return` выбрасывает daemon-треды из
реестра — поэтому `server_close()` джойнит пустой список, и `block_on_close =
True` не спасает. Дренажа нет фактически, а не по недосмотру.

**Уточнение к механике вреда (проверено лично).** `stop()` не рвёт уже принятые
соединения — закрывается только слушающий сокет. Значит «use-after-close» не
мгновенный эффект, а окно до конца teardown. Настоящий риск — аварийная ветка
`os._exit()` в `_shutdown_backend`, где осиротевший REST-тред обрывается
интерпретатором в произвольной точке, включая середину записи в NDJSON.
Реально пишут в общий `store` два эндпойнта: `POST /v1/vocabulary` и
`POST /v1/stt/transcribe`.

**Решение.** Порядок инкапсулируется внутри `stop()`, вызываемого рано в
`close()`:

1. `server.shutdown()` — перестать принимать новые соединения;
2. рассылка сентинела SSE-подписчикам (колбэк) — чтобы долгоживущие стримы
   закрылись сами;
3. дренаж активных запросов с бюджетом по образцу `IPCServer.stop()`: реестр
   тредов, единый deadline, `logger.warning` при истечении, `bool` наверх;
4. `server_close()`.

Реестр ведётся через `before_request` и `teardown_request`. Долгоживущие
стримы (`GET /v1/events`, WS `/v1/stream`) в бюджетное ожидание **не входят** —
иначе `stop()` будет выгорать бюджет всегда: SSE-соединение по определению
открыто до сентинела.

**Это отклонение от буквы §4.2 родительской спеки**, которая требует останов
REST в `GracefulShutdownHandler` после сентинела. Обоснование: `shutdown()`
вызывается **после** `service.close()`, то есть после закрытия всех
коллабораторов. Останов REST там означал бы, что REST принимает запросы, пока
TTS-сервис и адаптеры уже закрыты, — обмен известного риска на худший.
Требование спеки «сентинел раньше останова» выполняется, но внутри `stop()`,
а не переносом вызова.

**Требует проверки при исполнении:** идемпотентность
`_broadcast_event_bus_sentinel` — после нашей ранней рассылки
`shutdown_handler` разошлёт сентинел повторно для IPC-подписчиков.

### Р8 (находка 8) — смок покрывает меньше спеки

**Проблема.** Нагрузочный смок гоняет 24 конкурентных `GET /health` вместо
`POST`, WS `/v1/stream` не проверен вообще, критерий «p95 POST не хуже на 15 %»
не имеет данных. Плюс смок выключает несуществующий ключ
`llm_rewriter_enabled` (настоящий — `llm_rewrite_enabled`) и печатает
«окружение облегчено», не проверяя ответ `set_settings`, — опечатка невидима.

**Решение.** Смок доводится до буквы §4.5 родительской спеки: `POST` вместо
`GET`, проверка WS, проверка ответа `set_settings` перед печатью, замер RAM
через `scripts/memory_baseline.py` и p95 до и после флипа. Замер RAM и p95 —
не украшение, а гейт канарейки: обещание серии M «минус сотни МБ дубля» до сих
пор не подтверждено ни одним числом.

### Р9 (находка 9) — `service.py` исполняется дважды

**Проблема (подтверждено лично).** Прод-плист запускает
`KrabEar/backend/service.py` напрямую, то есть как `__main__`. При включённом
рубильнике `rest_server.py:37` делает `from backend.service import
BackendService` — и `service.py` исполняется вторым экземпляром модуля, уже как
`backend.service`. В процессе живут два разных класса с одним именем.

Сегодня безвредно. После флипа любой module-level синглтон, добавленный в
`service.py`, тихо раздвоится — и это будет отладка на часы.

**Решение.** Плист запускает `KrabEar/main.py` (существующая точка входа,
делающая `from backend.service import main`) вместо `service.py` напрямую.
Тогда `backend.service` импортируется один раз и как модуль.

**Требует проверки:** смок гоняет `main.py`, то есть уже правильный путь, —
значит этот дефект смок не воспроизводил. При исполнении убедиться, что путь
через `main.py` не ломает разрешение `PYTHONPATH` в плисте.

### Р10 (находка 10) — остатки

Три пункта, из которых один после флипа перестаёт быть косметикой.

**Строчный ключ `rest_in_process_enabled`.** Он есть в `DEFAULT_SETTINGS`, но
его не читает ни один участок прод-кода: рубильник живёт только в pydantic-поле.
`set_settings` отрапортует успех и не сделает ничего. Родительская спека §5
при этом прямо обещает «аварийный откат setting'ом» — то есть после флипа
обещанного пути отката физически не существует. Это **собственная находка при
гейтинге**, поднимающая пункт из Minor в блокирующие.

Решение — установленный в проекте паттерн (урок волны 58, `CLAUDE.md`
«Runtime vs static settings reads»): читать
`self._get_runtime_setting('rest_in_process_enabled', settings.REST_IN_PROCESS_ENABLED)`
— runtime-значение первым, статическое как фоллбэк. Тогда откат работает:
владелец пишет `false`, перезапускает backend, получает standalone. Рубильник
остаётся тем, чем был — читаемым один раз при старте, не live-toggle.

**Докстринг `StaticDeps`** утверждает «Путь M2: BackendService собирает deps
из своих коллабораторов». M2 пошла другим путём — подменой глобалов. Класс жив,
но используется только тестами M1. Правка — докстринг.

**`_rest_engine_cleanup`** (atexit, `rest_server.py:769`) читает голое `engine`.
После подмены это объект backend'а — то есть atexit закрывает GigaAM-адаптер
backend'а, а не свой. Решение: `adopt_external_singletons` получает парную
операцию освобождения, и atexit не трогает усыновлённые объекты.

## 3. Что разведка нашла сверх списка ревью

### 3.1 Родительская спека устарела в описании Voice Gateway

§5 планирует бриф соседней сессии о том, что их лаунчер сам спавнит
`rest_server.py` через `nohup`. Это неправда с 22 июля. Проверено дословно в
их репозитории (дерево чистое, ветка `main`): `start_gateway.command` и
`start_gateway_8091.command` при недоступном `/health` вызывают **наш**
канон — `safe_backend_restart.command --with-rest`. Более того, они закрепили
это своим пиновым тестом, который запрещает им прямой `launchctl kickstart`.

**Следствие.** Настоящий межрепозиторный контракт S3 — не их спавн-скрипт, а
наш `safe_backend_restart.command`, в шапке которого написано: «флаги
(`--wait`/`--with-rest`) и exit-коды менять только по координации с
VG-сессией». Под `--with-rest` он делает `launchctl kickstart -k` на юните
`ai.krab.ear.rest` — том самом, который волна удаляет. Родительская спека этот
артефакт не упоминает вообще.

**Решение.** Правок в чужом репозитории не требуется: их вызов защищён
`|| true`. Наш `--with-rest` становится идемпотентным — пропускает kickstart с
внятным сообщением, если юнит не загружен. Флаг сохраняется как принятый, чтобы
не ломать зафиксированный тестом контракт. Бриф в сессию VG остаётся, но
меняет содержание: он информационный (что изменилось, что делать не нужно),
а не корректирующий. Рекомендация про retry-with-backoff остаётся в силе —
разведка подтвердила, что в их STT- и TTS-клиентах ретраев нет, только
переключение движка на уровне оркестратора.

### 3.2 `start_rest_service.command` в корне репозитория

Дев-скрипт прямого запуска standalone REST, в §5 отсутствует. После флипа его
случайный запуск даст конфликт за порт — переживаемый (обе стороны fail-open),
но сбивающий с толку. Решение: пометить как standalone-путь в шапке скрипта.

### 3.3 `kill_dup_gigaam.command` становится структурно ненужным

Скрипт написан против того, что module-level `engine = AudioEngine()` в
`rest_server.py` спавнит собственный воркер GigaAM. В in-process режиме дубль
невозможен архитектурно — движок общий. То есть скрипт не «станет no-op», он
теряет причину существования для дефолтной конфигурации. Решение: оставить с
явной пометкой «только standalone», не удалять — standalone-режим живёт.

### 3.4 Переменные окружения rest-юнита уже продублированы

`KRAB_EAR_TRANSCRIBE_PROMPT` и `KRAB_EAR_TTS_ENABLED` из rest-плиста уже есть в
backend-плисте. Вывод rest-юнита не потеряет настройки TTS и промпта. Проверено
разведкой — фиксирую, чтобы исполнитель не тратил на это время.

### 3.5 Deprecated-заглушки как паттерна в проекте нет

Оба существующих «deprecated»-скрипта продолжают работать, лишь перенаправляя.
Скрипта, который печатает подсказку и отказывается, в кодовой базе нет ни
одного. Для `install_rest_launchagent.command` паттерн придётся ввести, и к
нему нужен source-контракт тест по образцу существующего
`test_migration_scripts.py`.

## 4. Состав волны

Девять задач в трёх чанках. Порядок между чанками жёсткий.

**Чанк 1 — данные и наблюдаемость.**
1. `KRAB_EAR_DATA_DIR` в backend-плист, генерация из одной переменной,
   source-контракт тест (Р3).
2. Надгробие вместо `None` при сбое сборки, код `rest.startup_failed` (Р5).
3. Мост подавляется по факту старта REST (Р4).

**Чанк 2 — жизненный цикл.**
4. Дренаж и порядок останова внутри `stop()` (Р7).
5. Сторож REST с локальным `restart()`, код `rest.wedged` (Р6).
6. Остатки: рабочий откат настройкой, `StaticDeps`, освобождение усыновлённых
   объектов, запуск через `main.py` (Р9, Р10).

**Чанк 3 — флип и вывод легаси.**
7. Смок до буквы §4.5: POST, WS, проверка `set_settings`, замер RAM и p95 (Р8).
8. Флип дефолта, `migrate_to_inprocess_rest.command`, deprecated-заглушка
   `install_rest_launchagent.command`, идемпотентный `--with-rest`, пометки
   `kill_dup_gigaam.command` / `start_rest_service.command` /
   gunicorn-пути, адаптация `run_e2e_bridge_smoke.command`.
9. Документация (`CLAUDE.md`, `README.md`, `docs/IPC_API_REFERENCE.md`) и
   информационный бриф в сессию Voice Gateway.

## 5. Definition of Done

- Восемь находок ревью M2 закрыты, каждая с регрессионным тестом.
- Рубильник по умолчанию включён; `get_diagnostics.rest_in_process` показывает
  `{enabled:true, running:true}` на живом прод-процессе.
- Юнит `ai.krab.ear.rest` выгружен и его plist удалён; порт 5005 слушает
  backend-процесс.
- Откат настройкой проверен вживую: `false` → рестарт → standalone работает.
- RAM и p95 измерены до и после; результат записан в журнал волны. Обещание
  «минус сотни МБ» либо подтверждено числом, либо опровергнуто явно.
- Живой e2e: `/health`, `POST /v1/stt/transcribe`, WS `/v1/stream`, SSE
  `/v1/events` — против слитого процесса.
- Voice Gateway поднимается своим лаунчером без правок в его репозитории.

## 6. Канарейка

Две недели на владельце, как требует родительская спека §4.5. Наблюдаемые
метрики: латентность диктовки, RAM, отсутствие `rest.wedged` и
`rest.startup_failed` в ErrorBus, работоспособность живых партиалов быстрой
заметки и панели встречи (они на SSE `:5005` — самые чувствительные
потребители).

Условие отката: любой из этих сигналов деградировал → `set_settings
{rest_in_process_enabled: false}` + рестарт backend + переустановка rest-юнита.
Откат обязан быть проверен **до** начала канарейки, а не в момент, когда он
понадобится.

## 7. Риски

| Риск | Митигация |
|---|---|
| Migrate забывает `bootout`+`bootstrap` backend-юнита → переменная не подхватилась, флип взрывается | Явный шаг в скрипте + верификация каталога через `get_diagnostics` после рестарта |
| Сторож REST принимает легитимную паузу за зависание (класс инцидента wake-word 16-07) | Первая длинная запись и первая встреча — обязательный смок-кейс сторожа |
| Дренаж выгорает бюджет на долгоживущих стримах | Стримы исключены из реестра по конструкции; тест на `stop()` при живом SSE |
| Флип на машине, где легаси-юнит ещё жив | `rest.port_conflict` + fail-open уже работают; migrate сносит юнит до флипа |
| Правка `--with-rest` ломает контракт с VG | Флаг сохраняется, меняется только тело; их пиновый тест проверяет строку вызова, а не наше поведение |
| Свежая установка из DMG получает старый шаблон | Релиз S3 обязан пересобрать DMG; проверить в чек-листе релиза |

## 8. Не-цели

- Явная инъекция `data_dir` в `adopt_external_singletons` — отдельная волна
  hardening после S3.
- Удаление standalone-режима, gunicorn-пути, межпроцессного MLX-flock — нет.
- Миграция хрупких тест-файлов на фабрику — по-прежнему не в серии M.
- Правки в репозитории Voice Gateway — только информационный бриф.
- Правка устаревших мест `README.md`, не связанных с REST (счётчик методов,
  битая ссылка) — не смешивать скоупы; вынести отдельной задачей, если владелец
  захочет.
