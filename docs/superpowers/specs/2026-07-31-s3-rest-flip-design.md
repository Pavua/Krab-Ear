Ревью дизайна: раунд 1 — Opus 5 (12 находок), раунд 2 — Fable 5 (15 находок).

## 1. Объём, инвариант и признанные исключения

### 1.1 Что волна делает и чего НЕ делает

**Делает:** закрывает дефекты, взводящиеся включением режима, и включает режим
**у владельца** — настройкой, на одной машине, с выгруженным (но не удалённым)
легаси-юнитом.

**НЕ делает: не меняет дефолт `REST_IN_PROCESS_ENABLED`.**

Обоснование — два независимых довода, сошедшихся в одной точке.

*Правило проекта.* `CLAUDE.md` и роадмап §3.1 требуют для рискованных флипов
дефолта двухнедельную канарейку владельца с именованными метриками **до** смены
дефолта. Дефолт — это то, что получают получатели DMG, у которых нет ни сторожа
в поле зрения, ни возможности откатить. Канарейка существует ровно затем, чтобы
они не стали подопытными.

*Физика launchd (находка ревью C-B).* Пока легаси-юнит загружен с
`KeepAlive=true`, launchd воскрешает REST на 5005, и in-process сервер физически
не займёт порт. Значит порядок «флип → проверка → снос юнита» неисполним:
проверять нечего, `{enabled:true, running:true}` недостижимо. Исполнитель либо
зафиксировал бы `running:false` и волна встала, либо сделал бы `bootout` «для
проверки» — то есть снос по эффекту, вне плана и без пути назад.

Следствие: **легаси-юнит не удаляется в этой волне.** Он выгружается
(`bootout`), plist остаётся на диске — это и есть механизм отката на всё время
канарейки.

Смена дефолта, удаление plist, deprecated-заглушка установщика, идемпотентный
`--with-rest`, пометки скриптов и обновление документации переезжают в
**отдельный короткий шаг после канарейки** (§7).

### 1.2 Инвариант

Включение не должно менять наблюдаемое поведение ни для владельца, ни для Voice
Gateway — кроме исчезновения второго процесса. Порт, схемы ответов,
SSE-подписки, auth, каталог данных остаются прежними.

### 1.3 Признанные исключения из инварианта

Два места, где инвариант невыполним. Фиксируются явно, а не замалчиваются.

**Конкуренция за GPU становится реальной сериализацией.** Родительская §4.4
утверждает: «REST-transcribe и диктовка уже сериализуются межпроцессным flock —
конкуренция не новая». Это ложная посылка: `mlx_inter_process_lock()` возвращает
no-op без `KRAB_EAR_MLX_INTER_PROCESS_LOCK=1` (`core/mlx_inter_lock.py:246-253`),
и переменной нет ни в одном из четырёх плистов (проверено грепом: ноль
вхождений). Сегодня они бьются за Metal свободно; после слияния попадут под
общий `mlx_lock()`.

Задеты не только диктовки (находка ревью I-G). Под тот же лок попадают
периодические конвейеры с каденс-дедлайнами: живая встреча (CHUNK_STT каждые
25 с) и live-субтитры (flush каждые 3 с). Тридцатисекундный REST-transcribe от
Voice Gateway задерживает не разовую операцию, а копит отставание аккумулятора
встречи и лаг субтитров — качественно другой эффект. Замеры обязаны включать оба
сценария, иначе канарейка спишет отставание панели встречи на «медленную
модель».

**Доступность REST падает с гарантии launchd до best-effort.** До включения
`KeepAlive=true` поднимает REST после любой смерти неограниченно. После —
только внутрипроцессный сторож с анти-штормом. Классы отказов, лечившиеся
перезапуском процесса (утечка дескрипторов, испорченное состояние `limiter` или
`Sock`), локальным рестартом не лечатся. Это принятая цена отказа от эскалации
в перезапуск всего backend.

## 2. Решения по находкам

### Р3 — `settings.DATA_DIR` не совпадает с `--data-dir`

**Проблема.** Каталог попадает в процесс двумя разнотипными каналами: backend
получает его аргументом `--data-dir` (живёт в локальной переменной `main()` и
доходит только до `StateStore`), а всё, что читает `settings.DATA_DIR`, смотрит
на переменную окружения. Сегодня оба случайно указывают в один каталог, потому
что rest-плист несёт `KRAB_EAR_DATA_DIR`, а backend-плист — нет.

**Радиус поражения (находка ревью I2).** Правка меняет `settings.DATA_DIR` для
**всего процесса**. Полный список потребителей, каждый обязан быть проверен:

| Файл:строка | Что читает | Эффект правки |
|---|---|---|
| `rest_server.py:713` | module-level `StateStore` | фантомный store исчезает |
| `rest_server.py:783-784` | `TEMP_DIR` + `mkdir` | загрузки идут в канонический каталог |
| `rest_server.py:413` | `RestAuth` | Bearer-токены начинают находиться |
| `rest_server.py:481` | bridge-токен | мост находит свой токен |
| `cloud_stt.py:25` | свой `StateStore` → ключи облачных STT | **смена семантики + лок** |
| `cloud_rewriter.py:141` | свой `StateStore` → ключи и провайдер | **смена семантики + лок** |
| `startup_diagnostics.py:279,337,624` | проверки диска, путь сокета | проверяют правильный каталог |

Сегодня `~/.krab_ear_data/settings.json` **не существует** (проверено), поэтому
облачные модули читают пустоту. После правки начнут читать канонический файл.
Приватностный гейт `engine._cloud_rewrite_allowed()` не трогается, но
исполнитель обязан зафиксировать в журнале ожидаемое новое поведение каждой из
семи строк.

**🔴 Лок-мина (находка ревью I-C, подтверждена дословно).** Р3 впервые сводит
несколько экземпляров `StateStore` на одни и те же файлы **внутри одного
процесса**. Фикс дедлока #1872 — per-thread depth-counter — живёт в **поле
экземпляра** (`state_store.py:111`: `self._lock_depth: dict[int, int]`). Значит
он не защищает между экземплярами: тред, держащий лок экземпляра А и вошедший в
лок экземпляра Б, не увидит `depth > 0`, возьмёт `fcntl.flock` на новом файловом
дескрипторе и самозаклинится навсегда — вместе со всем `StateStore` (34
call-site). Тот же механизм, что уложил прод в #1872, но недосягаемый для его
фикса.

Прямого пути сегодня не найдено (rewrite-путь не под локом) — это мина, а не
активный баг. Но взводит её именно эта волна.

Поэтому **инъекция store в `cloud_stt` и `cloud_rewriter` поднимается из
не-целей в состав волны** (задача 2). Они должны получать store владельца
процесса, а не строить свой. Плюс инвариант-тест: ни один путь не держит лок
одного экземпляра при входе в лок другого.

**Решение по каталогу.** Выровнять `settings.DATA_DIR` с `--data-dir` до того,
как `service.py` импортирует `rest_server`:

1. `KRAB_EAR_DATA_DIR` в `EnvironmentVariables` backend-плиста — та же строка,
   что в rest-плисте с 16-07.
2. Source-контракт тест: путь в `--data-dir` и в `KRAB_EAR_DATA_DIR` совпадают
   буквально. Без теста фикс невидим для регрессии.

**Уточнение (находка ревью M1).** Переписывать генератор не нужно:
`install_backend_launchagent.command:71` уже делает единственную подстановку
`sed -e "s|__HOME__|$HOME|g"`, обе строки вывелись бы из одного `__HOME__`.
Защита здесь — тест, а не правка рабочего `sed`.

**🔴 Busy-гейт обязателен (находка ревью I-D, подтверждена).** Спека v2
предписывала звать `install_backend_launchagent.command` вместо собственной
последовательности `launchctl` — это верно против `kickstart -k`. Но этот скрипт
делает **безусловный** `bootout` живого backend (строки 60-64), без проверки
записи и встречи, которая есть в `safe_backend_restart.command` (`busy_reason()`,
строки 55-70). Запуск в момент диктовки — точное повторение инцидента 22 июля:
аудио в памяти потеряно, в GUI «Backend не ответил».

Поэтому любой шаг волны, приводящий к переустановке юнита, **начинается с
busy-проверки** по образцу `safe_backend_restart.command` (с поддержкой
`--wait N`) и только затем зовёт установщик.

**Уточнение атрибуции (находка ревью M3).** Живой REST с 16-07 пишет в
канонический каталог — в его плисте есть переменная. Свежие записи в
`~/.krab_ear_data` — след прогонов тестов и смоков, а не прод-процесса. Механизм
сформулирован верно, неверна была атрибуция улики.

**Объединено с Р9** — обе правки трогают один шаблон и требуют одной
переустановки юнита.

### Р9 — `service.py` исполняется дважды

Прод-плист запускает `KrabEar/backend/service.py` напрямую, то есть как
`__main__` (`ai.krab.ear.backend.plist.template:26`). При включённом рубильнике
`rest_server.py:37` делает `from backend.service import BackendService` — и
`service.py` исполняется вторым экземпляром модуля, уже как `backend.service`.
В процессе живут два разных класса с одним именем.

Сегодня безвредно. После включения любой module-level синглтон, добавленный в
`service.py`, тихо раздвоится.

**Решение.** Плист запускает `KrabEar/main.py` — существующую точку входа.
Убедиться, что путь через неё не ломает разрешение `PYTHONPATH` в плисте.

### Р5 — диагностика не отличает «выключено» от «упало»

**Проблема.** Внешний `except` (`service.py:828-831`) ставит
`self._rest_inprocess = None`, а `_get_rest_inprocess_summary` на `None` отдаёт
словарь, байт в байт совпадающий с «рубильник выключен». ErrorBus не пушится.

**Уточнение.** Дыра уже, чем описано в исходной находке: `start()` документирован
как «НИКОГДА не бросает» и возвращает `bool` во всех ветках (`rest_inprocess.py:51-109`).
Значит внешний `except` ловит только сбой сборки приложения. Занятый порт
диагностику не ломает и ErrorBus получает (`rest.port_conflict`).

**Решение.** При сбое сборки поле не обнуляется, а получает лёгкое надгробие с
тем же `status()`, возвращающим `{enabled: <решение владельца>, running: false,
port: <порт>, error: <причина>, tombstone: true}`. Плюс пуш ErrorBus кодом
`rest.startup_failed`. `HealthCheckService` не меняется.

Поле `tombstone` — не косметика: сторож обязан по нему отличать нелечимое
(находка ревью M-A). Иначе при структурном сбое сборки он будет вечно лечить
надгробие и выдаст `rest.wedged` поверх уже отправленного `rest.startup_failed` —
двойная эскалация одного отказа.

**Рубильник перестаёт быть двухголовым (находка ревью I1).** Сейчас
`InProcessRestServer.__init__` читает `settings.REST_IN_PROCESS_ENABLED` сам
(`rest_inprocess.py:38`) и `start()` отказывается стартовать по своей копии.
В связке с Р10 это дало бы два разных ответа: владелец включает настройкой,
`service.py` конструирует сервер, а тот пишет «выключен рубильником» и молча
возвращает `False`. Поэтому `__init__` принимает `enabled: bool` **параметром**.

### Р7 — дренаж запросов и порядок останова

**Проблема.** `stop()` не ждёт хендлеры. Проверено: werkzeug 3.1.8 отдаёт
`ThreadedWSGIServer` с `daemon_threads = True`, а `socketserver._Threads.append`
ранним `return` выбрасывает daemon-треды из реестра — `server_close()` джойнит
пустой список, `block_on_close = True` бесполезен.

**Механика вреда.** `stop()` не рвёт принятые соединения — закрывается только
слушающий сокет. Настоящий риск — аварийная ветка `os._exit()` в
`_shutdown_backend`, где осиротевший тред обрывается в произвольной точке,
включая середину записи в NDJSON. Пишут в общий store два эндпойнта:
`POST /v1/vocabulary` и `POST /v1/stt/transcribe`.

**Бюджет обязан быть посчитан (находка ревью C3).** `ExitTimeOut=15`, из них уже
занято `_IPC_DRAIN_BUDGET_SEC = 8.0` плюс `SHUTDOWN_JOIN_TIMEOUT_SEC = 5.0` плюс
закрытие коллабораторов плюс семь шагов персистенса. Превышение → SIGKILL →
обрыв посреди записи плюс переживший `runtime_alive.marker`, который волна R1
строила как **редкий** признак грязной смерти.

**🔴 Механизм admission-close выбран явно (находка ревью I-F).** Версия v2
обещала «долгий POST получает 503 на входе» через `server.shutdown()`. Это
нереализуемо как написано: `shutdown()` лишь выводит serve-loop, слушающий сокет
остаётся открытым, ОС продолжает принимать соединения в backlog. Клиент
успешно коннектится и молча ждёт до RST при `server_close()` — то есть Voice
Gateway висел бы до своего таймаута 30 с, что длиннее всего нашего бюджета, и
выглядело бы как «Krab Ear завис».

Выбран флаг `shutting_down`, проверяемый в `before_request` и возвращающий 503,
**пока сервер ещё обслуживает**. Только после этого — `shutdown()`.

Порядок останова:

1. остановка сторожа REST (см. Р6) — самый первый шаг `_shutdown_backend`;
2. взвод флага `shutting_down` — новые запросы получают 503 немедленно;
3. `IPCServer.stop(8.0)` — его восемь секунд работают одновременно как окно
   дренажа REST, а не последовательно с ним;
4. в `close()`: рассылка сентинела SSE-подписчикам, дренаж активных запросов по
   реестру с общим deadline (образец — `IPCServer.stop()`), `shutdown()`,
   `server_close()`.

Реестр ведётся через `before_request` и `teardown_request`. Долгоживущие стримы
(`GET /v1/events`, WS `/v1/stream`) в бюджетное ожидание не входят — иначе
`stop()` выгорал бы бюджет всегда.

Суммарный бюджет фиксируется как инвариант. **Тест арифметический** (находка
ревью M-E): сумма именованных констант ≤ `ExitTimeOut` из шаблона. Реальный риск
(STT в дренаже, скорость диска при компактировании) покрывается не им, а смоком
SIGTERM под нагрузкой. Записать это прямо, чтобы DoD не создавал иллюзию
покрытия.

**Отклонение от буквы родительской §4.2**, требующей останов REST в
`GracefulShutdownHandler` после сентинела. Обоснование: `shutdown()` вызывается
**после** `service.close()`, то есть после закрытия коллабораторов. Останов там
означал бы, что REST принимает запросы при закрытых TTS и адаптерах.

**Требует проверки:** идемпотентность `_broadcast_event_bus_sentinel` —
`shutdown_handler` разошлёт сентинел повторно.

### Р4 — мост подавляется по факту, динамически

**Проблема.** `EventBridge` сам читает рубильник и выключается по нему. Мост
стартует раньше (`service.py:796`), чем делается попытка поднять REST
(`service.py:827`), и результат `start()` игнорируется. Легаси-агент держит порт
→ REST не встал → мост уже выключен → SSE-подписчики Swift на `:5005` глохнут.

**Почему одноразового решения мало (находка ревью C1).** Если подавление
вычисляется один раз, а сторож поднимает REST позже, мост начинает постить
в собственный процесс. `emit_envelope` кладёт конверт напрямую в `_subscribers`
(`event_bus.py:210-217`), минуя листенеров — эха нет, но исходный `emit()` уже
положил тот же конверт. **Каждое событие доставляется дважды.** Владелец видит
удвоенные субтитры и партиалы при штатной диагностике.

Сценарий проще, чем в отчёте: легаси-агент не нужен, достаточно чтобы REST не
встал при старте по любой причине.

**Решение.** Подавление динамическое: мост перед отправкой каждого батча
спрашивает владельца in-process REST, слушает ли он сейчас. Отвергнут вариант
«сторож явно давит мост» — создаёт состояние, которое надо синхронизировать в
обе стороны.

| Ситуация | REST слушает | Мост |
|---|---|---|
| Рубильник выключен | нет | работает |
| Рубильник включён, REST слушает | да | подавлен — шина одна |
| Рубильник включён, REST не слушает | нет | работает |

### Р6 — сторож REST

По образцу `WakeWordWatchdog`, внутри процесса. Лечение — **локальный**
`restart()`, без касания процесса backend.

**Явно отвергнуто: эскалация в `BackendSupervisor.forceRestartBackend()`.**
Единственный рычаг на Swift-стороне перезапускает весь backend через
`kickstart -k` — цена потерянной диктовки, инцидент 22 июля.

#### Что считается нездоровьем

- тик раз в 10 с: `status().running` при включённом рубильнике;
- раз в 30 с — активная проба `GET /health` на loopback, таймаут 2 с.

**Провалом считаются только таймаут и ошибка соединения** (находка ревью I5).
`/health` не защищён `require_api_key` и лимитирован `120 per minute` по remote
address, а все локальные потребители — Voice Gateway, Swift, сторож — приходят
с `127.0.0.1` и делят один бакет. Любой HTTP-ответ, включая 429 и 5xx,
доказывает, что сервер жив.

**🔴 Требуется серия, а не одно наблюдение (находка ревью I-A).** Лечение
начинается после N ≥ 2 подряд провалов пробы, то есть не менее 60 с нездоровья —
симметрично тридцатисекундному порогу staleness у сторожа wake-word, который
устроен через непрерывный «эпизод», а не через одиночный замер. Одиночный
таймаут — только WARN в лог. Без этого один выброс под нагрузкой (финальная
транскрипция встречи держит CPU) убивал бы здоровый REST и рвал SSE панелей.
Это ровно класс «single observation instead of streak/hysteresis» из `CLAUDE.md`.

**🔴 Порт, занятый снаружи, — не смерть (находка ревью C-A).** `running=false`
из-за конфликта порта неотличимо от «REST умер», а окно «режим включён + порт
держит легаси» существует **по конструкции** волны, пока юнит не выгружен.
Наивный сторож дал бы вечный шторм: каждые 10 с `restart()` → EADDRINUSE → новый
пуш `rest.port_conflict` → три попытки за 600 с → `rest.wedged`. Re-arm не
наступит никогда. Владелец получил бы поток тостов об ошибке при совершенно
здоровом (легаси) REST.

Поэтому: сторож лечит только то, что **хотя бы раз успешно слушало** (флаг
«был живой serve»), а успешный HTTP-ответ пробы при `running=false` трактуется
как «порт обслуживает кто-то другой» → отдельное состояние
`port_held_externally` в диагностике, без лечения и без эскалации.

Плюс сторож **не лечит надгробие** (`tombstone: true`, см. Р5).

#### Контракт `restart()`

Наивная реализация зависла бы на том самом отказе, который ловит (находка ревью
I4): `stop()` зовёт `server.shutdown()`, блокирующийся **без таймаута**, а
барьер `_serving` защищает только «тред ещё не вошёл в цикл». Плюс `start()`
рано возвращает `True` при `self._server is not None` (`rest_inprocess.py:59-60`) —
на залипшем-но-живом сервере повторный `start()` был бы тихим no-op, вечно
рапортующим успех лечения.

Поэтому `restart()` = `stop()` + `start()`, где `stop()` исполняется на отдельном
треде с общим deadline; по истечении сторож идёт сразу к эскалации `rest.wedged`,
не дожидаясь.

#### Терминальная защёлка при остановке

**🔴 Находка ревью I-B.** Single-flight сериализует `stop()` и `restart()`, но не
запрещает сторожу взять флайт **после** того, как `close()` его отпустил. Тогда
shutdown идёт дальше (TTS и адаптеры закрыты), а сторож поднимает REST заново —
ровно тот сценарий, ради которого отклонена буква родительской §4.2. В худшей
ветке владелец получает `rest.wedged`-тост в момент штатного выключения.

Поэтому: остановка сторожа — **самый первый шаг** `_shutdown_backend`, до взвода
`shutting_down`; плюс необратимое состояние `shutting_down` в координаторе, после
которого лечение запрещено (аналог maintenance-окна `openwakeword_adapter`).
Место стопа в `close()` указывается явно — **до** `rest_inprocess.stop()`.

#### Анти-шторм и re-arm

Не более 3 лечений в окне 600 с. После непрерывного здорового периода счётчик
обнуляется (находка ревью I6) — иначе «исчерпание лечений» означало бы «сдаёмся
навсегда», и REST оставался бы мёртвым до ручного вмешательства.

Исчерпание → `rest.wedged` (severity `error`, образец `audio.wakeword_wedged`) +
поле в диагностике.

#### Легитимные паузы — вопрос закрыт

Сторож wake-word однажды принял запись встречи за зависание, поэтому вопрос
обязан быть задан. Ответ: исключений не нужно. `/health`
(`rest_server.py:862-867`) читает единственный атрибут
`deps.engine.quality_profile` — ни локов, ни MLX, ни store.

Остаточный риск — замедление под тяжёлой транскрипцией — покрывается серией из
N провалов (см. выше) и смоком первой длинной записи.

#### Побочное: лог-шум

Проба раз в 30 с проходит через штатное request-логирование (`rest_server.py:280`)
— около 2880 строк в сутки навсегда (находка ревью M-D). Исключить loopback-пробу
из access-лога либо логировать только не-2xx.

### Р8 — смок и замеры

**Проблема.** Смок гоняет 24 конкурентных `GET /health` вместо `POST`, WS не
проверен, критерий «p95 POST не хуже на 15 %» не имеет данных. Плюс выключает
несуществующий ключ `llm_rewriter_enabled` (настоящий — `llm_rewrite_enabled`) и
печатает «окружение облегчено», не проверяя ответ `set_settings`.

**Решение.** Довести до буквы родительской §4.5: `POST`, WS, проверка ответа
`set_settings`, замер RAM через `scripts/memory_baseline.py` и p95 до и после.

Плюс три сценария конкуренции за GPU (§1.3, находка ревью I-G):
- латентность диктовки под конкурентным `POST /v1/stt/transcribe`;
- **лаг снапшота живой встречи** под тем же фоном;
- **лаг live-субтитров** под тем же фоном.

Первый — разовая латентность, два других — накопление отставания, качественно
другой эффект.

**Транзитный дубль на старте (находка ревью M-C).** `service.py:812` импортирует
`rest_server` → на импорте строятся второй `AudioEngine` и второй `StateStore`
(`rest_server.py:712-713`), которые тут же вытесняются
`adopt_external_singletons`. Это удлиняет старт и на секунды создаёт второй
store на живых файлах. Зафиксировать в журнале замеров, чтобы цифры не
превратились в загадку.

### Р10 — остатки

**Строчный ключ `rest_in_process_enabled`.** Есть в `DEFAULT_SETTINGS`, но его не
читает ни один участок прод-кода: рубильник живёт только в pydantic-поле.
`set_settings` рапортует успех и не делает ничего. Родительская §5 при этом
обещает «аварийный откат setting'ом» — обещанного пути не существует. Это
собственная находка при гейтинге.

Для этой волны ключ становится **основным способом включения** (дефолт не
меняется), поэтому он обязан работать. Решение — паттерн волны 58: читать
`self._get_runtime_setting('rest_in_process_enabled', settings.REST_IN_PROCESS_ENABLED)`,
результат передавать параметром `enabled` в `InProcessRestServer`. Рубильник
остаётся читаемым один раз при старте, не live-toggle.

**Докстринг `StaticDeps`** утверждает «Путь M2: BackendService собирает deps из
своих коллабораторов». M2 пошла подменой глобалов. Класс жив, используется
тестами M1. Правка — докстринг.

**`_rest_engine_cleanup`** (atexit, `rest_server.py:769`) читает голое `engine`.
После подмены это объект backend'а — atexit закрывает его GigaAM-адаптер.
Решение: `adopt_external_singletons` получает парную операцию освобождения.

### Р11 — `temp_uploads` вне privacy-purge

`TEMP_DIR = settings.DATA_DIR / "temp_uploads"` (`rest_server.py:783`) не
упоминается нигде в коде очистки. Каталог содержит сырое пользовательское аудио
из `POST /v1/stt/transcribe`. Слияние делает backend его владельцем, а
`handle_purge_all_data` его не трогает. `audit_purge_coverage.py --fail-on-found` —
включённый CI-гейт.

**Решение.** Добавить в purge. Allowlist отвергнут: его политика требует туда
только то, что демонстрируемо не является пользовательским содержимым.

**Верификация обязана быть живой (находка ревью M-B).** Обвязка вычисляет путь от
`settings.DATA_DIR`. Пока юнит не переустановлен, процесс видит
`~/.krab_ear_data` → purge чистит пустой каталог, а настоящий `temp_uploads`
остаётся с аудио. Статический аудит этого не поймает. Требуется проверка на
живом процессе **после** переустановки юнита.

### Р12 — SSE-подписчики не переподключаются (новая, находка ревью I-E)

Проверено: `QuickCapturePanelController.swift:102` создаёт
`SSESessionDelegate { [weak self] line in ... }` — только обработчик строки, без
`onComplete`. Сам делегат в докстринге говорит, что решение о переподключении
остаётся за экраном; экран его не принял.

До включения REST рестартовал редко. После — стримы рвутся при каждом лечении
сторожа и при самом включении. У панели встречи есть poll-фоллбэк, у скретчпада
нет ничего.

**Сценарий:** сторож лечит REST во время диктовки в скретчпад → сентинел →
делегат завершается → задача не пересоздаётся → панель показывает застывший
текст, запись продолжается, диагностика зелёная.

**Решение.** `onComplete` с переподключением и backoff в
`QuickCapturePanelController`. Это же требуется для честности канарейки, которая
иначе проверяет работоспособность партиалов глазами владельца.

## 3. Что разведка нашла сверх списков ревью

### 3.1 Родительская спека устарела в описании Voice Gateway

§5 планирует бриф о том, что их лаунчер спавнит `rest_server.py` через `nohup`.
Неправда с 22 июля: `start_gateway.command:66` и `start_gateway_8091.command:64`
при недоступном `/health` вызывают **наш** `safe_backend_restart.command
--with-rest`, и это закреплено их пиновым тестом, запрещающим им прямой
`launchctl kickstart`.

Настоящий межрепозиторный контракт — наш `safe_backend_restart.command`, в шапке
которого написано: «флаги и exit-коды менять только по координации с VG-сессией».
Под `--with-rest` он делает `kickstart -k` на `ai.krab.ear.rest`.

**В этой волне юнит только выгружается, не удаляется**, поэтому правка
`--with-rest` не требуется: `kickstart` на выгруженном юните вернёт ошибку, а их
вызов защищён `|| true`. Идемпотентность флага переезжает в шаг после канарейки.

Бриф в сессию VG остаётся и становится информационным: что меняется, что делать
не нужно, и почему на время канарейки их путь работает как прежде. Рекомендация
про retry-with-backoff в силе — в их STT- и TTS-клиентах ретраев нет.

### 3.2 Каналы доставки на чужие машины (находка ревью M-F)

`bootstrap_backend.command:139` ставит **только** backend-юнит — rest-юнит
получателям DMG никогда не ставился. То есть у них порт 5005 сегодня мёртв, а
SSE-панели и мост деградированы. После смены дефолта свежая установка впервые
получит работающий REST.

Но отсюда следует требование к шагу после канарейки: **обновление Sparkle меняет
только `.app`**. Если код доедет до чужой машины без переустановки юнита, там
взводится Р3 в чистом виде — REST с `DATA_DIR=~/.krab_ear_data`: пустые
настройки, ненаходимые Bearer-токены. Шаг смены дефолта обязан описать, каким
каналом флип доезжает и почему Р3 там не взводится.

### 3.3 Мелочи инвентаризации

`start_rest_service.command` в корне репозитория — дев-скрипт прямого запуска
standalone REST, в родительской §5 отсутствует. `kill_dup_gigaam.command`
написан против дубля воркера GigaAM, невозможного при общем движке — теряет
причину существования для дефолтной конфигурации, но остаётся для standalone.
`KRAB_EAR_TRANSCRIBE_PROMPT` и `KRAB_EAR_TTS_ENABLED` уже продублированы в
backend-плисте — настройки не потеряются. Всё три — пометки, переезжают в шаг
после канарейки.

### 3.4 Два Flask-приложения в слитом процессе (находка ревью M4)

`rest_server.py:2409` — `app = create_app()` на импорте (нужен контракту
категорий A/B/C, 752 теста); `service.py:823` — второй. Модульный `limiter`
получает `init_app` дважды. Работает, но приложение №1 остаётся мёртвым грузом.
Фиксируется как известное и намеренное. Устранение не в этой волне: снятие
module-level `app` ломает контракт тестов, ради которого M1 строила
`_ModuleGlobalsDeps`.

## 4. Механизм отката

Легаси-юнит **выгружается, но не удаляется**. Это даёт откат одной командой на
всё время канарейки:

- **Откат режима:** `set_settings {rest_in_process_enabled: false}` + рестарт
  backend через `safe_backend_restart.command`.
- **Возврат легаси-REST:** `launchctl bootstrap` того же plist, оставшегося на
  диске.

Оба пути проверяются вживую в задаче 12, до начала канарейки, а не в момент,
когда понадобятся.

## 5. Состав волны

Двенадцать задач в четырёх чанках. Порядок между чанками жёсткий; внутри
чанка 2 задача «мост» обязана предшествовать задаче «сторож» (иначе взводится
двойная доставка).

**Чанк 1 — данные, локи, приватность.**
1. `KRAB_EAR_DATA_DIR` в backend-плист, запуск через `main.py`, source-контракт
   тест, busy-гейт перед переустановкой юнита, журнал ожидаемого поведения всех
   семи потребителей `settings.DATA_DIR` (Р3 + Р9 + I2 + I-D).
2. Инъекция store в `cloud_stt` и `cloud_rewriter` + инвариант-тест на
   вложенные локи разных экземпляров (I-C).
3. `temp_uploads` в privacy-purge + живая верификация после переустановки юнита
   (Р11 + M-B).
4. Надгробие с `tombstone`, `enabled` параметром, код `rest.startup_failed`
   (Р5 + I1 + M-A).

**Чанк 2 — жизненный цикл.**
5. Дренаж: флаг `shutting_down` → 503, реестр запросов, посчитанный бюджет,
   арифметический тест + смок SIGTERM под нагрузкой (Р7 + C3 + I-F + M-E).
6. Динамическое подавление моста по факту работы REST (Р4 + C1).
7. Сторож: серия из N провалов, `port_held_externally`, не лечит надгробие,
   контракт `restart()`, терминальная защёлка первым шагом shutdown, re-arm,
   анти-шторм, исключение пробы из access-лога
   (Р6 + C-A + I-A + I-B + I4 + I5 + I6 + M-D).

**Чанк 3 — клиенты, остатки, замеры.**
8. `onComplete` с переподключением и backoff в `QuickCapturePanelController` (Р12).
9. Остатки: рабочее включение настройкой, `StaticDeps`, освобождение усыновлённых
   объектов (Р10).
10. Смок до буквы §4.5 + замеры RAM и p95 + три сценария конкуренции за GPU
    (Р8 + §1.3 + I-G + M-C).

**Чанк 4 — включение у владельца.**
11. `migrate_to_inprocess_rest.command`: busy-гейт, `bootout` легаси-юнита
    **без удаления plist**, парный `--rollback` (`bootstrap` обратно), верификация
    каталога через `get_diagnostics` (§4 + I-D).
12. Включение у владельца настройкой, проверка обоих путей отката вживую, старт
    канарейки. Информационный бриф в сессию Voice Gateway.

## 6. Definition of Done

**Функциональные:**
- Восемь находок ревью M2, двенадцать находок раунда 1 и пятнадцать раунда 2
  закрыты; каждая с регрессионным тестом, кроме явно названных исключений (M-E).
- Режим включён **у владельца**; `get_diagnostics.rest_in_process` показывает
  `{enabled:true, running:true}` на живом процессе.
- Дефолт `REST_IN_PROCESS_ENABLED` **не изменён**; легаси-plist на диске.
- Оба пути отката проверены вживую до начала канарейки.
- RAM и p95 измерены до и после; результат в журнале волны. Обещание «минус
  сотни МБ» подтверждено числом либо опровергнуто явно.
- Три сценария конкуренции за GPU измерены: диктовка, лаг встречи, лаг
  субтитров (§1.3).
- Живой e2e: `/health`, `POST /v1/stt/transcribe`, WS `/v1/stream`, SSE
  `/v1/events` против слитого процесса.
- Смок SIGTERM под нагрузкой: teardown укладывается в `ExitTimeOut`, маркер
  `runtime_alive.marker` удалён штатно.
- Voice Gateway работает без правок в его репозитории.
- Скретчпад переживает лечение REST без потери живых партиалов.

## 7. Канарейка и шаг после неё

Две недели на владельце, как требует родительская §4.5.

Метрики: латентность диктовки, лаг снапшота встречи, лаг субтитров, RAM,
отсутствие `rest.wedged` и `rest.startup_failed` в ErrorBus, отсутствие
удвоенных событий, работоспособность живых партиалов скретчпада и панели
встречи.

Условие отката — любой сигнал деградировал; механизм в §4.

**Шаг после канарейки** (отдельная небольшая волна, не входит в S3):
- смена дефолта `REST_IN_PROCESS_ENABLED` на `true`;
- удаление легаси-plist, deprecated-заглушка `install_rest_launchagent.command`
  с флагом восстановления;
- идемпотентный `--with-rest` в `safe_backend_restart.command`;
- пометки `kill_dup_gigaam.command`, `start_rest_service.command`,
  gunicorn-пути; адаптация `run_e2e_bridge_smoke.command`;
- документация: `CLAUDE.md`, `README.md`, `docs/IPC_API_REFERENCE.md`;
- описание канала доставки на чужие машины и доказательство, что Р3 там не
  взводится (§3.2).

## 8. Риски

| Риск | Митигация |
|---|---|
| Переустановка юнита убивает активную диктовку | Busy-гейт по образцу `safe_backend_restart.command` перед любым `bootout` (Р3) |
| Вложенные локи разных экземпляров `StateStore` → вечный дедлок | Инъекция store в cloud-модули + инвариант-тест (задача 2) |
| Сторож штормит на занятом порту | Лечит только то, что раз слушало; HTTP-ответ при `running=false` → `port_held_externally` (Р6) |
| Сторож убивает здоровый REST от одного выброса | Серия N ≥ 2 провалов подряд (Р6) |
| Сторож воскрешает REST посреди shutdown | Остановка сторожа первым шагом + необратимый `shutting_down` (Р6) |
| Teardown превышает `ExitTimeOut` → SIGKILL посреди записи | Посчитанный бюджет + арифметический тест + смок SIGTERM под нагрузкой (Р7) |
| VG висит 30 с вместо получения 503 | Флаг `shutting_down` в `before_request`, а не `server.shutdown()` (Р7) |
| Двойная доставка событий при позднем рестарте REST | Динамическое подавление моста; задача 6 предшествует задаче 7 |
| Откат обещан, но невозможен | Юнит выгружен, plist на диске; оба пути проверены вживую (§4) |
| Лечение REST молча убивает партиалы скретчпада | `onComplete` с переподключением (Р12) |
| Отставание встречи и субтитров под конкурентным STT | Три сценария замеров (Р8); канарейка следит за лагом |
| Облачные модули начинают читать канонические настройки | Журнал ожидаемого поведения семи потребителей; гейт `_cloud_rewrite_allowed()` не трогается |

## 9. Не-цели

- **Смена дефолта — не в этой волне** (§1.1). Отдельный шаг после канарейки.
- Удаление легаси-plist, deprecated-заглушка, правка `--with-rest` — там же.
- Снятие module-level `app = create_app()` — ломает контракт 752 тестов (§3.4).
- Удаление standalone-режима, gunicorn-пути, межпроцессного MLX-flock — нет.
- Включение `KRAB_EAR_MLX_INTER_PROCESS_LOCK` — отдельное решение; §1.3 лишь
  фиксирует, что флаг выключен.
- Миграция хрупких тест-файлов на фабрику — по-прежнему не в серии M.
- Правки в репозитории Voice Gateway — только информационный бриф.
- Правка устаревших мест `README.md`, не связанных с REST — отдельной задачей,
  если владелец захочет.
