# Волна S3: флип рубильника и вывод легаси-REST — дизайн

Дата: 2026-07-31 · Статус: **СПЕКА v2** (после adversarial-ревью дизайна) ·
Автор: Opus 5. Ревьюер дизайна: Opus 5, свежий контекст — вердикт FIX-THEN-SHIP,
12 находок, все прогейчены построчно против кода, ложных нет.
Родительская спека: `2026-07-16-m-series-rest-merge-design.md` (серия M целиком).
Предшественники: M1 (app-factory, закрыта 16-07), M2 (опт-ин in-process REST,
закрыта и задеплоена 30-07, PR #1897).
Роадмап: `docs/ROADMAP-2026H2.md` §3.1.

Эта спека **уточняет и в трёх местах отменяет** родительскую. Причина — финальное
adversarial-ревью диффа M2 нашло восемь дефектов, взводящихся именно флипом;
разведка 31-07 показала, что §5 родительской спеки описывает устаревшее состояние
соседнего репозитория; а ревью этой спеки нашло ложную посылку в §4.4 родительской.

## 0. Исходное состояние (проверено лично 30-31 июля)

- Рубильник `REST_IN_PROCESS_ENABLED` живёт в проде и выключен:
  `get_diagnostics.rest_in_process = {enabled:false, running:false, port:null, error:null}`.
- Мост `EventBridge` доказан живыми данными: `state=up, sent=3, dropped=0, failed=0`.
- Отдельный REST-юнит `ai.krab.ear.rest` работает (`KeepAlive=true`,
  `ThrottleInterval` не задан → дефолт launchd, а не 5 с как у backend-юнита;
  `ExitTimeOut` у него тоже не задан, у backend-юнита — 15 с).
- Весь код слияния уже в проде. **S3 — это не новая архитектура, а одна строка
  дефолта плюс закрытие дефектов и операционная зачистка.**

## 1. Инвариант волны и два признанных исключения

Флип не должен менять наблюдаемое поведение системы ни для владельца, ни для
Voice Gateway — кроме исчезновения второго процесса. Порт, схемы ответов,
SSE-подписки, auth, каталог данных обязаны остаться прежними.

Из инварианта следует жёсткий порядок: **флип идёт последним**. Любая задача,
меняющая дефолт до закрытия блокеров, воспроизводит ровно те отказы, ради
которых волна затевается.

Ревью нашло два места, где инвариант **не выполним**, и они фиксируются как
осознанные изменения, а не замалчиваются.

### 1.1 Конкуренция за GPU становится реальной сериализацией

Родительская §4.4 утверждает: «сегодня REST-transcribe и диктовка уже
сериализуются межпроцессным flock — конкуренция не новая». **Это ложная
посылка.** `mlx_inter_process_lock()` возвращает no-op, если нет
`KRAB_EAR_MLX_INTER_PROCESS_LOCK=1` (`core/mlx_inter_lock.py:247-253`), а этой
переменной нет ни в одном из четырёх плистов — ни в шаблонах, ни в
установленных. Проверено грепом: ноль вхождений.

То есть сегодня REST-STT и диктовка бьются за Metal свободно. После слияния они
попадают под общий `mlx_lock()` — глобальный RLock. Диктовка начнёт ждать
завершения чужой транскрипции вместо параллельного исполнения.

Оценка: скорее всего чистый выигрыш — уходит реальный риск SIGSEGV на
конкурентном доступе к GPU, ради которого `mlx_lock` и существует. Но это
изменение того, что владелец может заметить, и оно обязано быть измерено, а не
предположено. Задача замеров получает отдельный сценарий: латентность диктовки
**под конкурентным** `POST /v1/stt/transcribe`, до и после флипа.

### 1.2 Доступность REST падает с гарантии launchd до best-effort

До флипа `ai.krab.ear.rest` имеет `KeepAlive=true` — launchd поднимает REST
после любой смерти, неограниченно. После флипа единственный механизм
восстановления — внутрипроцессный сторож с анти-штормом. Классы отказов,
которые лечились перезапуском процесса (утечка дескрипторов, испорченное
состояние `limiter` или `Sock`), локальным рестартом не лечатся.

Это принятая цена отказа от эскалации в перезапуск всего backend (см. Р6).
Деградация REST предпочтительнее потери диктовки владельца.

## 2. Решения по находкам ревью M2

Нумерация сохранена из отчёта финального ревью M2, чтобы её можно было сверить.

### Р3 — `settings.DATA_DIR` не совпадает с `--data-dir`

**Проблема.** Каталог данных попадает в процесс двумя независимыми,
разнотипными каналами: backend получает его аргументом `--data-dir` (живёт в
локальной переменной `main()` и доходит только до `StateStore`), а всё, что
читает `settings.DATA_DIR`, смотрит на переменную окружения. Сегодня оба канала
случайно указывают в один каталог, потому что rest-плист несёт
`KRAB_EAR_DATA_DIR`, а backend-плист — нет. После флипа REST переезжает под
backend-плист и теряет переменную.

**Радиус поражения шире, чем казалось (находка ревью I2).** Правка меняет
`settings.DATA_DIR` для **всего процесса**, а не для `rest_server`. Полный
список потребителей, каждый обязан быть проверен исполнителем:

| Файл:строка | Что читает | Эффект правки |
|---|---|---|
| `rest_server.py:713` | module-level `StateStore` | фантомный store исчезает |
| `rest_server.py:783-784` | `TEMP_DIR` + `mkdir` | загрузки идут в канонический каталог |
| `rest_server.py:413` | `RestAuth` | Bearer-токены начинают находиться |
| `rest_server.py:481` | bridge-токен | мост находит свой токен |
| `cloud_stt.py:25` | свой `StateStore` → ключи openai/deepgram/assemblyai | **смена семантики** |
| `cloud_rewriter.py:141` | свой `StateStore` → ключи openai/anthropic, провайдер | **смена семантики** |
| `startup_diagnostics.py:279,337,624` | проверки диска, путь сокета | проверяют правильный каталог |

Две последние строки — не побочный эффект, а изменение поведения, которое
обязано быть осознанным. Сегодня `~/.krab_ear_data/settings.json` **не
существует** (проверено), поэтому облачные модули читают пустоту: даже если бы
владелец включил `cloud_rewriter_enabled` через GUI (тот пишет в канонический
файл), облачный переписыватель был бы включён-но-нерабочим. После правки он
начнёт работать по-настоящему и отправлять транскрипты наружу.

На этой машине сейчас не заряжено (`cloud_rewriter_enabled=False`, ключей нет),
и приватностный гейт `engine._cloud_rewrite_allowed()` остаётся на месте — но
это класс, а не единичный случай. Исполнитель обязан зафиксировать в журнале
волны ожидаемое новое поведение каждой из семи строк.

**Решение.** Выровнять `settings.DATA_DIR` с `--data-dir` **до** того, как
`service.py` импортирует `rest_server`:

1. `KRAB_EAR_DATA_DIR` добавляется в `EnvironmentVariables` backend-плиста —
   ровно та же строка, что уже есть в rest-плисте с 16-07.
2. Source-контракт тест проверяет, что в шаблоне путь в `--data-dir` и путь в
   `KRAB_EAR_DATA_DIR` совпадают буквально. Без теста фикс невидим для
   регрессии: любой, кто уберёт строку «для чистоты», тихо вернёт блокер.

**Уточнение после ревью (находка M1).** Первая версия спеки требовала
переписать генератор, «чтобы оба значения выводились из одной шелл-переменной».
Это лишняя работа: `install_backend_launchagent.command:71` уже делает
единственную подстановку `sed -e "s|__HOME__|$HOME|g"`, и обе строки вывелись
бы из одного `__HOME__`. Дублируется только литеральный хвост
`/Library/Application Support/KrabEar`. Защита здесь — именно тест, а не правка
рабочего `sed`.

**Второе уточнение (находка M1).** `install_backend_launchagent.command` уже
умеет `bootout` (62-63) и `bootstrap` (98-99). Migrate-скрипт обязан **звать
этот скрипт**, а не собирать собственную последовательность `launchctl`.
Требование остаётся жёстким: `kickstart -k` **не подхватывает** новые
переменные окружения из изменённого plist.

**Третье уточнение (находка M3).** Улика в разведке атрибутирована неточно.
Живой REST-процесс с 16-07 пишет в канонический каталог — в его плисте есть
`KRAB_EAR_DATA_DIR`. Свежие записи в `~/.krab_ear_data` — след прогонов тестов
и смоков, а не прод-процесса. Сам механизм («что угодно без `--data-dir` и без
переменной попадает в `~/.krab_ear_data`») сформулирован верно, и блокер
реален; неверна только атрибуция. Исполнитель не должен искать не тот процесс.

**Отвергнуто: инъекция каталога через `adopt_external_singletons`.** Она чинит
только перечисленные объекты (`_ADOPTABLE_NAMES` — пять имён) и не достаёт до
`cloud_stt.store` и `cloud_rewriter.store` вообще. Явную инъекцию стоит
рассмотреть отдельной волной hardening — она устраняет класс, а не проявление.

**Объединено с Р9.** Обе правки трогают один и тот же
`ai.krab.ear.backend.plist.template` и обе требуют переустановки юнита. Держать
их в разных чанках означало бы переустанавливать юнит дважды и писать один
source-контракт тест поверх другого.

### Р4+Р6 — мост по факту и сторож REST (единая задача-пара)

**Ревью нашло Critical на стыке (C1): по отдельности оба решения верны,
их композиция ломается.** Поэтому решения изложены вместе, а задачи идут
подряд и в одном чанке.

#### Проблема моста

`EventBridge` сам читает `REST_IN_PROCESS_ENABLED` и выключается по нему.
Стартует мост раньше (`service.py:796`), чем делается попытка поднять REST
(`service.py:827`), и результат `start()` (он возвращает `bool`) игнорируется.
Сценарий: легаси-агент держит порт → in-process REST не встал (fail-open) → но
мост уже выключен → SSE-подписчики Swift на `:5005` глохнут. Это живые партиалы
`QuickCapturePanelController` (без фоллбэка) и `MeetingLivePanelController`.

#### Почему одноразового решения недостаточно

Если подавление вычисляется один раз при старте, а сторож поднимает REST
позже — решение о мосте уже заморожено. Мост жив и начинает постить на
`127.0.0.1:5005/internal/event`, то есть **в собственный процесс**.
`emit_envelope` кладёт конверт напрямую в `_subscribers` (`event_bus.py:210-217`),
минуя листенеров — эха не возникает, no-echo guard работает. Но исходный
`emit()` уже положил тот же конверт туда же. **Каждое событие доставляется
подписчикам дважды.**

Владелец увидит удвоенные строки живых субтитров и дублирующиеся партиалы в
панели встречи и скретчпаде — ровно у тех двух потребителей, которых решение
защищает. Диагностика при этом выглядит совершенно штатной: `running:true`,
мост `state=up`.

**Сценарий проще, чем в отчёте ревью.** Он не требует легаси-агента вообще:
достаточно, чтобы REST не встал при старте по любой причине, а сторож поднял
его через десять секунд.

#### Решение

Подавление моста **динамическое**. Мост перестаёт знать про рубильник и перед
отправкой каждого батча спрашивает владельца in-process REST: слушает ли он
сейчас. Отвергнут вариант «сторож явно давит мост при успешном рестарте» — он
создаёт новое состояние, которое надо синхронизировать в обе стороны; запрос
статуса дешевле и не может рассинхронизироваться.

Поведение в трёх ситуациях, в любой момент жизни процесса:

| Ситуация | REST слушает | Мост |
|---|---|---|
| Рубильник выключен | нет | работает (как сегодня) |
| Рубильник включён, REST слушает | да | подавлен — шина одна |
| Рубильник включён, REST не слушает | нет | работает |

Третья строка — фикс исходной находки; динамичность — фикс находки ревью.

#### Сторож

По образцу `WakeWordWatchdog`, внутри процесса:

- тик раз в 10 с, проверка `status().running` при включённом рубильнике;
- раз в 30 с — активная проба `GET /health` на loopback с таймаутом 2 с. Без
  неё не ловится «тред жив, `running=true`, сервер не отвечает» — класс живого
  инцидента wake-word 13 июля;
- лечение — **локальный** `restart()`, без касания процесса backend;
- анти-шторм: не более 3 лечений в окне 600 с;
- исчерпание → эскалация в ErrorBus кодом `rest.wedged` (severity `error`, по
  образцу `audio.wakeword_wedged`) + поле в диагностике.

**Контракт `restart()` (находка ревью I4).** Наивная реализация зависнет на том
самом отказе, который ловит: `stop()` зовёт `server.shutdown()`, который
блокируется **без таймаута**, а барьер `_serving` защищает только случай «тред
ещё не вошёл в цикл», не «тред в цикле и залип». Плюс `start()` рано возвращает
`True`, если `self._server is not None` — на залипшем-но-живом сервере
повторный `start()` был бы тихим no-op, вечно рапортующим успех лечения.

Поэтому: `restart()` = `stop()` + `start()`, где `stop()` исполняется на
**отдельном** треде с общим deadline; по истечении deadline сторож переходит
сразу к эскалации `rest.wedged`, не дожидаясь. Плюс single-flight между
сторожем и `close()` по образцу `AudioReinitCoordinator` — сейчас ничто не
мешает им войти в `stop()`/`start()` одновременно.

**Семантика провала пробы (находка ревью I5).** `/health` не защищён
`require_api_key` и лимитирован `120 per minute` по remote address — а все
локальные потребители (Voice Gateway, Swift, сторож) приходят с `127.0.0.1` и
делят **один** бакет. Всплеск обращений выбрал бы бакет, сторож получил бы 429
и перезапустил здоровый REST.

Провалом считаются **только таймаут и ошибка соединения**. Любой HTTP-ответ,
включая 429 и 5xx, доказывает, что сервер жив, и провалом не является.

**Re-arm (находка ревью I6).** После непрерывного здорового периода счётчик
лечений обнуляется. Без этого «исчерпание лечений» означало бы «сдаёмся
навсегда», и REST оставался бы мёртвым до ручного вмешательства, а Voice
Gateway — без STT и TTS.

**Явно отвергнуто: эскалация в `BackendSupervisor.forceRestartBackend()`.**
Единственный рычаг на Swift-стороне перезапускает **весь** backend через
`kickstart -k`. Для отказа REST это цена потерянной диктовки или встречи —
инцидент 22 июля, ради которого написан `safe_backend_restart.command`.

**Вопрос легитимных пауз — закрыт проверкой (31-07).** Сторож wake-word
однажды принял запись встречи за зависание, поэтому вопрос обязан быть задан.
Ответ: исключений вводить **не нужно**. `/health` (`rest_server.py:862-868`)
читает единственный атрибут `deps.engine.quality_profile` — ни локов, ни
обращений к MLX, ни к store. Активная запись и встреча его не задевают.

Остаточный риск, который обязан быть проверен смоком: под тяжёлой
транскрипцией процесс занят, и Flask-тред может ответить медленнее обычного.
Таймаут пробы 2 с выбран с запасом на это; смок первой длинной записи обязан
подтвердить, что запаса хватает.

### Р5 — диагностика не отличает «выключено» от «упало»

**Проблема.** Внешний `except` в `service.py:828-831` ставит
`self._rest_inprocess = None`, а `_get_rest_inprocess_summary` на `None` отдаёт
`{enabled:false, running:false, port:null, error:null}` — байт в байт то же, что
при выключенном рубильнике. ErrorBus в этой ветке не пушится.

**Уточнение (проверено лично).** Дыра **уже**, чем описано.
`InProcessRestServer.start()` документирован как «НИКОГДА не бросает» и правда
возвращает `bool` во всех ветках. Значит внешний `except` ловит только сбой
сборки приложения. Самый вероятный в проде отказ (занятый порт) диагностику не
ломает и ErrorBus получает (`rest.port_conflict`). Немым остаётся структурный
сбой сборки.

**Решение.** При сбое сборки поле не обнуляется, а получает лёгкий
объект-надгробие с тем же методом `status()`, возвращающим
`{enabled: <решение владельца>, running: false, port: <порт>, error: <причина>}`.
Плюс пуш ErrorBus новым кодом `rest.startup_failed`. `HealthCheckService` при
этом не меняется вообще — он уже умеет звать `status()` у коллаборатора.

**Рубильник перестаёт быть двухголовым (находка ревью I1).** Сейчас
`InProcessRestServer.__init__` читает `settings.REST_IN_PROCESS_ENABLED`
**сам** (`rest_inprocess.py:38`) и `start()` отказывается стартовать по своей
копии. В связке с Р10 (чтение рубильника из runtime-настройки в `service.py`)
это дало бы два разных ответа: владелец включает настройкой, `service.py`
конструирует сервер, а тот пишет «выключен рубильником» и возвращает `False` —
без единой ошибки, просто REST не появляется никогда. Плюс `status().enabled`
отражал бы pydantic-поле, а надгробие — хардкод.

Поэтому `InProcessRestServer.__init__` принимает `enabled: bool` **параметром**
от владельца и не читает `settings` сам. Источник правды один, `status().enabled`
совпадает с решением, надгробие заполняется тем же значением.

**Почему не строить настоящий сервер при выключенном рубильнике:** его
конструирование требует `create_app()`, а тот тянет импорт `rest_server` со
всем module-level комплектом, включая `AudioEngine`. При выключенном рубильнике
это ровно тот дубль тяжёлого состояния, ради устранения которого затевалась
серия.

### Р7 — нет дренажа запросов, порядок останова инвертирован

**Проблема.** `stop()` не ждёт хендлеры. Проверено на живом окружении:
werkzeug 3.1.8 отдаёт `ThreadedWSGIServer` с `daemon_threads = True`, а
`socketserver._Threads.append` ранним `return` выбрасывает daemon-треды из
реестра — поэтому `server_close()` джойнит пустой список, и `block_on_close =
True` не спасает. Дренажа нет фактически, а не по недосмотру.

**Уточнение к механике вреда (проверено лично).** `stop()` не рвёт уже принятые
соединения — закрывается только слушающий сокет. «Use-after-close» не мгновенный
эффект, а окно до конца teardown. Настоящий риск — аварийная ветка `os._exit()`
в `_shutdown_backend`, где осиротевший REST-тред обрывается интерпретатором в
произвольной точке, включая середину записи в NDJSON. Реально пишут в общий
`store` два эндпойнта: `POST /v1/vocabulary` и `POST /v1/stt/transcribe`.

**Бюджет останова обязан быть посчитан (находка ревью C3).** Первая версия
спеки добавляла дренаж, не проверив, помещается ли он. `ExitTimeOut=15` в
backend-плисте, при этом уже сегодня: `_IPC_DRAIN_BUDGET_SEC = 8.0` плюс
`SHUTDOWN_JOIN_TIMEOUT_SEC = 5.0` плюс закрытие остальных коллабораторов плюс
семь шагов персистенса, включая компактирование истории. Тринадцать секунд
только на двух явных константах.

Хуже: дренируемый REST-запрос — не быстрый `/health`. `POST /v1/stt/transcribe`
штатно работает секунды и десятки секунд (Voice Gateway даёт ему 30 с). Дренаж
такого запроса либо выжигает бюджет, либо бросает его недоделанным.

Последствие превышения: launchd шлёт SIGKILL → обрыв в произвольной точке,
ровно тот вред, от которого дренаж защищает. Плюс переживший
`runtime_alive.marker` на каждом рестарте → бесконечный сбор форензики и ложный
сигнал «прошлая жизнь умерла грязно», который волна R1 строила как **редкий**
диагностический признак.

**Решение.** Admission REST закрывается **первым шагом** `_shutdown_backend`,
до `IPCServer.stop()`. Тогда восемь секунд IPC-дренажа работают одновременно
как окно дренажа REST, а не последовательно с ним. Долгий
`POST /v1/stt/transcribe` получает `503` на входе, а не дренируется.

Порядок внутри `stop()`, вызываемого в `close()`:

1. `server.shutdown()` — перестать принимать новые соединения;
2. рассылка сентинела SSE-подписчикам (колбэк) — чтобы стримы закрылись сами;
3. дренаж активных запросов с бюджетом по образцу `IPCServer.stop()`: реестр
   тредов, единый deadline, `logger.warning` при истечении, `bool` наверх;
4. `server_close()`.

Реестр ведётся через `before_request` и `teardown_request`. Долгоживущие стримы
(`GET /v1/events`, WS `/v1/stream`) в бюджетное ожидание **не входят** — иначе
`stop()` выгорал бы бюджет всегда.

Суммарный бюджет фиксируется в спеке как инвариант и проверяется тестом:
admission-close + IPC-дренаж + REST-дренаж + join + метаданные ≤ `ExitTimeOut`
с запасом. Если не помещается — поднимается `ExitTimeOut` в шаблоне (плист всё
равно правится задачей 1).

**Это отклонение от буквы §4.2 родительской спеки**, которая требует останов
REST в `GracefulShutdownHandler` после сентинела. Обоснование: `shutdown()`
вызывается **после** `service.close()`, то есть после закрытия всех
коллабораторов. Останов REST там означал бы, что REST принимает запросы, когда
TTS-сервис и адаптеры уже закрыты, — обмен известного риска на худший.
Требование «сентинел раньше останова» выполняется, но внутри `stop()`.

**Требует проверки при исполнении:** идемпотентность
`_broadcast_event_bus_sentinel` — после ранней рассылки `shutdown_handler`
разошлёт сентинел повторно для IPC-подписчиков.

### Р8 — смок покрывает меньше спеки

**Проблема.** Смок гоняет 24 конкурентных `GET /health` вместо `POST`, WS
`/v1/stream` не проверен вообще, критерий «p95 POST не хуже на 15 %» не имеет
данных. Плюс смок выключает несуществующий ключ `llm_rewriter_enabled`
(настоящий — `llm_rewrite_enabled`) и печатает «окружение облегчено», не
проверяя ответ `set_settings`, — опечатка невидима.

**Решение.** Смок доводится до буквы §4.5 родительской спеки: `POST` вместо
`GET`, проверка WS, проверка ответа `set_settings` перед печатью, замер RAM
через `scripts/memory_baseline.py` и p95 до и после флипа. Добавляется сценарий
из §1.1: латентность диктовки под конкурентным `POST /v1/stt/transcribe`.

Замеры — не украшение, а гейт канарейки: обещание серии M «минус сотни МБ
дубля» до сих пор не подтверждено ни одним числом.

### Р9 — `service.py` исполняется дважды

**Проблема (подтверждено лично).** Прод-плист запускает
`KrabEar/backend/service.py` напрямую, то есть как `__main__`. При включённом
рубильнике `rest_server.py:37` делает `from backend.service import
BackendService` — и `service.py` исполняется вторым экземпляром модуля, уже как
`backend.service`. В процессе живут два разных класса с одним именем.

Сегодня безвредно. После флипа любой module-level синглтон, добавленный в
`service.py`, тихо раздвоится — и это будет отладка на часы.

**Решение.** Плист запускает `KrabEar/main.py` (существующая точка входа,
делающая `from backend.service import main`) вместо `service.py` напрямую.
**Объединено с Р3** — один и тот же файл шаблона, одна переустановка юнита.

**Требует проверки:** смок гоняет `main.py`, то есть уже правильный путь, —
значит этот дефект смок не воспроизводил. Убедиться, что путь через `main.py`
не ломает разрешение `PYTHONPATH` в плисте.

### Р10 — остатки

**Строчный ключ `rest_in_process_enabled`.** Он есть в `DEFAULT_SETTINGS`, но
его не читает ни один участок прод-кода: рубильник живёт только в pydantic-поле.
`set_settings` отрапортует успех и не сделает ничего. Родительская §5 при этом
обещает «аварийный откат setting'ом» — то есть после флипа обещанного пути
отката физически не существует. Это **собственная находка при гейтинге**,
поднимающая пункт из Minor в блокирующие.

Решение — установленный паттерн (урок волны 58, `CLAUDE.md` «Runtime vs static
settings reads»): читать
`self._get_runtime_setting('rest_in_process_enabled', settings.REST_IN_PROCESS_ENABLED)`
— runtime-значение первым, статическое как фоллбэк. Результат передаётся
параметром `enabled` в `InProcessRestServer` (см. Р5). Рубильник остаётся тем,
чем был — читаемым один раз при старте, не live-toggle.

**Докстринг `StaticDeps`** утверждает «Путь M2: BackendService собирает deps из
своих коллабораторов». M2 пошла другим путём — подменой глобалов. Класс жив, но
используется только тестами M1. Правка — докстринг.

**`_rest_engine_cleanup`** (atexit, `rest_server.py:769`) читает голое `engine`.
После подмены это объект backend'а — atexit закрывает GigaAM-адаптер backend'а,
а не свой. Решение: `adopt_external_singletons` получает парную операцию
освобождения, и atexit не трогает усыновлённые объекты.

### Р11 — `temp_uploads` вне покрытия privacy-purge (новая, находка ревью M2)

`TEMP_DIR = settings.DATA_DIR / "temp_uploads"` (`rest_server.py:783`) не
упоминается нигде в коде очистки — единственное вхождение во всём backend.
Каталог содержит сырое пользовательское аудио: файлы вида
`<12hex>_<basename>.wav` из `POST /v1/stt/transcribe`.

Слияние делает backend владельцем этого каталога, а `handle_purge_all_data` его
не трогает. `scripts/audit_purge_coverage.py --fail-on-found` — включённый
CI-гейт с явным allowlist'ом.

**Решение.** Добавить в purge. Внесение в allowlist рассматривалось и отвергнуто:
политика самого allowlist'а требует туда только то, что демонстрируемо не
является пользовательским содержимым, — сырое аудио этому не отвечает.

## 3. Что разведка нашла сверх списка ревью M2

### 3.1 Родительская спека устарела в описании Voice Gateway

§5 планирует бриф соседней сессии о том, что их лаунчер сам спавнит
`rest_server.py` через `nohup`. Это неправда с 22 июля. Проверено дословно в их
репозитории (дерево чистое, ветка `main`): `start_gateway.command:66` и
`start_gateway_8091.command:64` при недоступном `/health` вызывают **наш**
канон — `safe_backend_restart.command --with-rest`. Более того, они закрепили
это своим пиновым тестом, запрещающим им прямой `launchctl kickstart`.

**Следствие.** Настоящий межрепозиторный контракт S3 — не их спавн-скрипт, а
наш `safe_backend_restart.command`, в шапке которого написано: «флаги
(`--wait`/`--with-rest`) и exit-коды менять только по координации с
VG-сессией». Под `--with-rest` он делает `launchctl kickstart -k` на юните
`ai.krab.ear.rest` — том самом, который волна удаляет.

**Решение.** Правок в чужом репозитории не требуется: их вызов защищён
`|| true`. Наш `--with-rest` становится идемпотентным — пропускает kickstart с
внятным сообщением, если юнит не загружен. Флаг сохраняется как принятый, чтобы
не ломать зафиксированный тестом контракт. Бриф в сессию VG остаётся, но
меняет содержание: он информационный, а не корректирующий. Рекомендация про
retry-with-backoff остаётся в силе — разведка подтвердила, что в их STT- и
TTS-клиентах ретраев нет, только переключение движка на уровне оркестратора.

### 3.2 `start_rest_service.command` в корне репозитория

Дев-скрипт прямого запуска standalone REST, в §5 отсутствует. После флипа его
случайный запуск даст конфликт за порт — переживаемый (обе стороны fail-open),
но сбивающий с толку. Решение: пометить как standalone-путь в шапке скрипта.

### 3.3 `kill_dup_gigaam.command` становится структурно ненужным

Скрипт написан против того, что module-level `engine = AudioEngine()` в
`rest_server.py` спавнит собственный воркер GigaAM. В in-process режиме дубль
невозможен архитектурно — движок общий. Скрипт не «станет no-op», он теряет
причину существования для дефолтной конфигурации. Решение: оставить с явной
пометкой «только standalone» — standalone-режим живёт.

### 3.4 Переменные окружения rest-юнита уже продублированы

`KRAB_EAR_TRANSCRIBE_PROMPT` и `KRAB_EAR_TTS_ENABLED` из rest-плиста уже есть в
backend-плисте. Вывод rest-юнита не потеряет настройки TTS и промпта. Проверено
разведкой — фиксирую, чтобы исполнитель не тратил на это время.

### 3.5 Deprecated-заглушки как паттерна в проекте нет

Оба существующих «deprecated»-скрипта продолжают работать, лишь перенаправляя.
Скрипта, который печатает подсказку и отказывается, в кодовой базе нет ни
одного. Паттерн придётся ввести, и к нему нужен source-контракт тест по образцу
`test_migration_scripts.py`.

**Но заглушка не должна быть глухой (см. §4.1)** — она остаётся единственным
путём восстановления юнита при откате.

### 3.6 В слитом процессе строятся два Flask-приложения (находка ревью M4)

`rest_server.py:2409` — `app = create_app()` на импорте (нужен контракту
категорий A/B/C, 752 теста); `service.py:823` — второй `create_app()`. Модульный
`limiter` получает `init_app` дважды, модульные блюпринты регистрируются в двух
приложениях. Работает, но приложение №1 остаётся мёртвым грузом со ссылками.

Фиксируется как известное и намеренное, чтобы замеры памяти в задаче 8 не
упёрлись в это как в загадку. Устранение — не в этой волне: снятие
module-level `app` ломает контракт 752 тестов, ради которого M1 и строила
`_ModuleGlobalsDeps`.

## 4. Откат: почему он требует отдельной работы

Ревью нашло Critical (C2): первая версия спеки обещала откат настройкой и той
же волной уничтожала его инструмент. После вывода юнита запись
`rest_in_process_enabled: false` + рестарт backend дают **не standalone, а
полное отсутствие REST**: юнит выгружен, plist удалён, единственный установщик
превращён в скрипт, который отказывается работать. Порт 5005 не слушает никто.
Voice Gateway теряет STT и TTS целиком, Swift-панели теряют SSE. Откат из
аварийного превращается во второй инцидент.

### 4.1 Решение

Три требования, все обязательные:

1. **`migrate_to_inprocess_rest.command` получает парный `--rollback`**,
   восстанавливающий юнит из шаблона. Шаблон остаётся в репозитории —
   standalone-режим не удаляется (§8).
2. **Deprecated-заглушка `install_rest_launchagent.command` не отказывается
   глухо**, а требует явного флага и при нём ставит юнит. Без этого пункт 1
   был бы единственной дверью, а заглушка — стеной рядом с ней.
3. **Порядок внутри волны:** флип → проверка отката вживую → снос юнита.
   Первая версия делала флип и снос одной задачей, то есть к моменту проверки
   отката откатывать было бы уже некуда.

Проверка отката вживую — отдельная задача с собственным гейтом, а не пункт
чек-листа.

Две недели на владельце, как требует родительская §4.5. Наблюдаемые метрики:

## 8. Риски

| Риск | Митигация |
|---|---|
| Migrate забывает `bootout`+`bootstrap` → переменная не подхватилась, флип взрывается | Migrate **зовёт** `install_backend_launchagent.command`, который уже делает и то и другое; верификация каталога через `get_diagnostics` после рестарта |
| Сторож принимает легитимную паузу за зависание (класс инцидента wake-word 16-07) | Первая длинная запись и первая встреча — обязательный смок-кейс сторожа |

| Дренаж выгорает бюджет на долгоживущих стримах | Стримы исключены из реестра по конструкции; тест на `stop()` при живом SSE |
| Teardown превышает `ExitTimeOut` → SIGKILL посреди записи NDJSON | Посчитанный бюджет как инвариант + тест; admission-close первым шагом |
| Двойная доставка событий при позднем рестарте REST | Динамическое подавление моста (Р4); задача 5 предшествует задаче 6 |
| Откат обещан, но невозможен | `--rollback` + заглушка с флагом + проверка отката до сноса юнита (§4) |
| Флип на машине, где легаси-юнит ещё жив | `rest.port_conflict` + fail-open уже работают; migrate сносит юнит |
| Правка `--with-rest` ломает контракт с VG | Флаг сохраняется, меняется только тело; их тест проверяет строку вызова |
| Свежая установка из DMG получает старый шаблон | Релиз S3 обязан пересобрать DMG; проверить в чек-листе релиза |
| Облачные модули начинают читать канонические настройки (I2) | Журнал ожидаемого поведения всех семи потребителей в задаче 1; приватностный гейт `_cloud_rewrite_allowed()` не трогается |

## 9. Не-цели

- Явная инъекция `data_dir` в `adopt_external_singletons` — отдельная волна
  hardening после S3.
- Снятие module-level `app = create_app()` — ломает контракт 752 тестов (§3.6).
- Удаление standalone-режима, gunicorn-пути, межпроцессного MLX-flock — нет.
- Включение `KRAB_EAR_MLX_INTER_PROCESS_LOCK` — отдельное решение, не в этой
  волне (§1.1 только фиксирует факт, что флаг выключен).
- Миграция хрупких тест-файлов на фабрику — по-прежнему не в серии M.
- Правки в репозитории Voice Gateway — только информационный бриф.
- Правка устаревших мест `README.md`, не связанных с REST (счётчик методов,
  битая ссылка) — не смешивать скоупы; отдельной задачей, если владелец захочет.
