# R2 — Владение записью: идентичность поколения, гейт остановки, восстановление стопа

Дата: 2026-07-25 · Автор: Opus 5 (max) + владелец · Adversarial-ревью дизайна: Fable 5
Статус: спека утверждённого решения «всё одной волной» (владелец, 2026-07-25)
Предшественники: R1 «Надёжность записи» (закрыта 2026-07-24/25), C3a, PR #1891

## 1. Контекст и мотивация

В Krab Ear **один** экземпляр `AudioRecorder`, которым пользуются четыре независимых
потребителя: диктовка по хоткею, быстрая заметка (quick capture), встреча (meeting) и
call assist. Сегодня «кто владеет текущей записью» выражено единственной строкой
`source`, которую передаёт только meeting **на старте** (`meeting_session_service.py:214`)
и которая используется исключительно как метка в сайдкаре spill-файла
(`recording_core_service.py:306`). Контроля владения нет ни на старте, ни на остановке.

Этот структурный пробел дал **два реальных HIGH за неделю** (оба залатаны точечно, но
причина осталась):

1. **C3a F1** (2026-07-17): быстрая заметка трактовала `already_recording` как успех →
   её последующий стоп останавливал общий рекордер, принадлежавший встрече → воркер
   встречи самофинализировался с `item_id: None`, отчёт встречи терялся.
2. **R1 HIGH-2** (2026-07-24, найден Opus-гейтом): старт встречи поверх идущей диктовки
   безусловно затирал `self._active_spill` → spill-файл живой диктовки навсегда
   оставался в `rescue/` и дублировался следующим rescue-сканом.

Adversarial-ревью этого дизайна (Fable, 2026-07-25) нашло **живой, ещё не залатанный
экземпляр того же класса** — самый опасный из трёх:

3. **F1 (LIVE)**: при идущей встрече одиночный тап Right Option попадает в ветку
   «лечения рассинхрона» (`main+HotkeyRecording.swift:61-71`): агент видит
   `backendRecording && !wasRecordingLocally`, показывает «Найден рассинхрон записи.
   Сначала завершаю зависшую сессию» и зовёт `stopRecording()` — останавливая **запись
   встречи**. Последствия двойные: воркер встречи самофинализируется с `item_id: None`
   (отчёт потерян), а транскрипт целого часа уходит в `handleTranscriptionResult` →
   `pasteToFrontmostApp` (`main+PasteHandling.swift:151`) — **час встречи вставляется в
   активное окно пользователя**. Отдельно: `already_recording` в хоткей-пути
   (`main+HotkeyRecording.swift:118-126`) до сих пор трактуется как «штатная
   идемпотентная синхронизация» — C3a починил ровно это для быстрой заметки, но её
   родного брата в диктовке не тронул (sibling-gate asymmetry, третий случай подряд).

Плюс хвост инцидента 2026-07-22 (владелец потерял две диктовки при рестарте backend):
GUI не ретраит `stop_recording`, когда сокет переподнялся — отдаёт generic-ошибку.

**Отношение к WIP-ветке codex** (`codex/user3-recording-rescue-20260722`): её база
отстала на 55 коммитов и конфликтует по трём файлам с уже принятым PR #1891; самооценка
автора — 82-85% с девятью незакрытыми P1; ревью и прогонов тестов с 21 июля не было.
Мержу как есть не подлежит (это же зафиксировано в спеке R1 §3). Используется **как
референс на чтение**: её двухосевая модель (`capture_owner` + `finalize_owner`) —
полезное наблюдение, что promote меняет «кто финализирует», а не «кто захватил».

## 2. Цель и Definition of Done

**Цель**: сделать владение общей записью явным и проверяемым, чтобы класс «чужой
потребитель останавливает не свою запись» стал структурно невозможным, а прерванная
транспортом остановка — восстановимой без потери результата.

DoD:
1. Тап Right Option при активной встрече/заметке НЕ останавливает чужую запись и НЕ
   вставляет чужой транскрипт; пользователь видит внятное объяснение. Доказано
   автотестом Swift + живым смоком.
2. `already_recording` в хоткей-пути перестаёт быть успехом (зеркало C3a-фикса),
   включая корректный откат audio ducking.
3. Предъявленный токен, не совпадающий с активным поколением, НИКОГДА не останавливает
   рекордер — ни при каких обстоятельствах, включая пустой кэш после рестарта backend.
4. Повторная остановка с тем же токеном возвращает тот же терминальный ответ (без
   повторного персиста и без ложного `already_stopped`).
5. Остановка во время идущей финализации возвращает типизированный `stop_in_progress`,
   а не «запись потеряна».
6. Shadow-телеметрия чиста: при штатных сценариях (включая финализацию встречи и
   promote) — ноль записей `recording.owner_mismatch`.
7. Все существующие сценарии работают без изменений: диктовка, заметка, встреча,
   promote диктовки во встречу, call assist.

## 3. Не-цели (осознанные границы)

- **Privacy-epoch гейты, purge-guard, `discard_recording_generation`, orphan-drain** из
  WIP codex — ноль наблюдённых инцидентов при максимальной инвазивности. Отбрасываем.
- **Call assist bypass НЕ чиним в этой волне.** `CallAssistService` получает тот же
  общий рекордер (`service.py:567-573`, `recorder=self.recorder`) и дёргает
  `recorder.start()` / `recorder.stop()` напрямую (`call_assist_service.py:271, 403`),
  минуя `RecordingCoreService` целиком. Следствия, которые фиксируем письменно:
  (а) записи call assist **не имеют crash-safety R1** (spill не создаётся);
  (б) они невидимы для shadow-телеметрии (стоп не проходит через `handle_stop_recording`);
  (в) «recorder занят, но генерации нет» — достижимое состояние.
  В этой волне закрываем только (в) типизированным отказом `unmanaged_recording`
  (см. §4.3), полную интеграцию call assist выносим отдельной задачей.
- **F8 (таймаут `meeting_stop` 60с короче финализации часовой встречи)** — реальная
  проблема, но независимая от владения; фиксируем как отдельный хвост.
- Wholesale-мерж WIP-ветки codex.

## 4. Архитектура

### 4.1 Поколение записи

При успешном `recorder.start()` `RecordingCoreService` заводит запись о поколении:

```
{token: str(uuid4), owner: "dictation"|"quick_capture"|"meeting",
 state: "capturing"|"finalizing", started_at: float, promoted_from: str|None}
```

Живёт под уже существующим `_recording_lifecycle_lock` (нового лока не вводим —
`start` и `phase_a` уже сериализованы им). Хранится в одном поле
`self._active_generation`.

**Переходы состояния** (однозначно, чтобы не осталось места для трактовок):

- `capturing` взводится при создании поколения.
- `finalizing` — в `phase_a_locked` сразу после успешного забора аудио из рекордера
  (штатный стоп уже необратимо начался, но тяжёлые фазы STT/LLM/диаризации ещё нет).
- **Поколение завершается (удаляется из `_active_generation`, его ответ кладётся в
  кэш §4.4) на ЛЮБОМ терминальном выходе `handle_stop_recording` после забора аудио** —
  не только в конце `phase_e`. Сюда входят ранние выходы phase_b (тишина,
  фоновая речь), phase_c (провал STT) и phase_d (пустой текст): для пользователя это
  такой же окончательный ответ, как успешная запись. Формулировка «в конце phase_e»
  была бы дырой: поколение навсегда осталось бы в `finalizing`, и ретрай с его токеном
  вечно получал бы `stop_in_progress` вместо честного ответа.
- Ветки раннего выхода phase_a **до** забора аудио (`recorder_timeout`,
  `already_stopped`) поколение НЕ трогают — оно остаётся `capturing`, потому что запись
  фактически не завершилась (при `recorder_timeout` воркер может ещё дописывать).
- Отказы самого гейта (`owner_mismatch`, `unknown_generation`, `stop_in_progress`)
  поколение не меняют по определению — они не начинают остановку.

**Токен генерируется ПЕРВЫМ и передаётся в spill-writer** (F7):
`RecordingSpillWriter` получает новый опциональный параметр `session_id` (по умолчанию
генерирует свой, как сейчас). Тогда имя rescue-файла и токен поколения — одна сущность,
и сообщение клиента «запись восстановится при следующем запуске» указывает на конкретный
файл.

**Почему не переиспользуем существующие идентичности** (анти-rebuild, проверено):
`session_tracker.session_id` гейтится privacy-режимом (`recording_core_service.py:454-466`),
`_rt_session_id` гейтится `realtime_partial_enabled` + privacy, `RecordingSpillWriter.session_id`
гейтится настройкой spill. Ни одна не безусловна, а владение обязано работать всегда.
Токен поколения — контракт жизненного цикла на горячем пути; `session_tracker` — аналитика
завершённой записи. Связывать их значит подчинить остановку записи аналитической
подсистеме, которую намеренно выключают в privacy-режиме.

### 4.2 Гейт остановки — порядок операций критичен

**Инвариант (F6)**: гейт — **первая** операция в `_stop_recording_phase_a_locked`, до
`_stop_preview_worker()`. Причина: phase_a сносит preview worker (:1309), `_rt_partial`
(:1326-1338) и RSF (:1342-1357) ДО `recorder.stop()` (:1366). Гейт, стоящий «перед
остановкой рекордера», уже убил бы партиалы и превью живой чужой записи — то есть
«отказ без прикосновения к записи» был бы ложью.

**Инвариант (F2)**: решение принимается по **токену**, а не по кэшу. Кэш — оптимизация
replay'я, а не защита. Порядок разбора:

| Что предъявлено | Решение |
|---|---|
| токен == токену активного поколения, состояние `capturing` | штатная остановка |
| токен == токену активного поколения, состояние `finalizing` | `stop_in_progress` (F4) |
| токен найден в кэше терминальных ответов | replay сохранённого ответа |
| токен предъявлен, но не найден нигде | `unknown_generation`, **рекордер не трогаем** |
| токен не предъявлен вообще (старый бинарь агента) | legacy-путь как сегодня, **никогда не отказ** (F5, two-binary drift) |

Сценарий, который закрывает строка «не найден нигде»: стоп диктовки A ушёл, ответ
потерян транспортом, backend рестартовал (генерации и кэш — в RAM), владелец начал
запись B, ретрай стопа A приезжает с токеном A → без этого инварианта он остановил бы
запись B на полуслове.

### 4.3 Матрица переходов владения

Promote сегодня детектится косвенно, по статусу (`meeting_session_service.py:215`:
`promoted = status == "already_recording"`), и бэкенд не решает, кому переходит владение.
Вводим явную таблицу; всё, чего в ней нет — типизированный отказ **без** смены владельца:

| Текущий владелец | Стартует | Решение |
|---|---|---|
| — (нет записи) | любой | обычный старт, владелец = стартующий |
| `dictation` | `meeting` | **promote**: владелец → `meeting`, токен тот же, `promoted_from="dictation"` |
| `quick_capture` | `meeting` | отказ `owner_conflict` (заметка не должна молча растворяться во встрече) |
| любой | `quick_capture` | отказ `owner_conflict` |
| любой | `dictation` | отказ `owner_conflict` |
| `meeting` | любой | отказ `owner_conflict` |
| запись идёт, генерации нет (call assist) | `meeting` | отказ `unmanaged_recording` |
| статус `recorder_stopping` | любой | отказ (сегодня встреча создаётся и умирает через 0.5с фантомным `meeting.finished`) |

**Promote не создаёт и не подменяет spill** — сохраняется дисциплина ветки not-started,
введённая фиксом R1 HIGH-2: discard'ится только spill собственной неудавшейся попытки,
`_active_spill` живой записи не трогается. На promote дополнительно перезаписывается
meta-сайдкар (`source="meeting"`, `promoted_from="dictation"`), fail-open (F10).

### 4.4 Кэш терминальных ответов

Ограниченный по размеру (3 записи) и TTL (5 минут) кэш `{token → terminal_response}`,
заполняется при записи терминального ответа в phase_e. Инвалидируется полностью при
`handle_purge_all_data` и при включении `privacy_mode_enabled` (F9): ответ phase_e несёт
`text` / `original_text` / `translated_text` целиком, а CI-гард `audit_purge_coverage`
покрывает только file-backed хранилища и RAM-кэш пропустит.

### 4.5 Swift: закрытие живого бага F1

1. `get_recording_state` дополняется полями `owner` и `generation_token` (аддитивно).
2. `performRecordToggle`: авто-heal «зависшей сессии» разрешён **только** при
   `owner == "dictation"`. Чужой владелец → тост «Идёт встреча (или заметка) — запись
   не тронута», без остановки.
3. `already_recording` в `startRecording()` перестаёт быть успехом: это отказ с внятным
   сообщением. Обязательно откатывается audio ducking — сейчас он включается ДО старта
   (`main+HotkeyRecording.swift:111`) и восстанавливается только в defer стопа
   (:159-167); под чужой записью восстановление залило бы системный звук в микрофон встречи.
4. Явная ветка `case "owner_mismatch"` в `stopRecording()` — человеческое сообщение и
   сброс локального состояния вместо `default:` «Неожиданный статус».

### 4.6 Swift: единый helper остановки с ретраем

Сегодня остановку шлют три разных пути с разной семантикой: `callWithRecovery`
(`main+IPCRecovery.swift:16-28`, уже имеет одиночный resend после `restartIfDead()`),
`callAsync` и `callWithReconnect` (`IPCClient.swift:224`, где таймаут **не** transient и
немедленно re-throw). Вводим **один** helper остановки, который:

- предъявляет токен поколения;
- ретраит только транспортную неоднозначность (сокет закрыт, обрыв, реконнект),
  максимум 2 дополнительные попытки;
- **не** ретраит типизированный `ok:false` от бэкенда;
- на `stop_in_progress` — ждёт и переспрашивает (не показывает «потеряно»);
- на `unknown_generation` и на исчерпание попыток — показывает текст живого превью и
  честное «запись восстановится при следующем запуске» (стыковка с R1-rescue).

### 4.7 Прошивка `source` во все вызовы

Пререквизит осмысленной shadow-телеметрии (F5), входит в эту же волну:
внутренний стоп встречи (`meeting_session_service.py:286`, сейчас `{}`), quick capture
старт/стоп/orphan-стоп (`main+QuickCapture.swift:57, 91, 134`, сейчас `[:]`), старт и
стоп диктовки (`main+HotkeyRecording.swift:118, 170-178`).

**Mismatch фиксируется только позитивный** — владелец передан И не совпал. Отсутствие
владельца — debug-лог, никогда не WARNING и не ErrorBus, иначе каждая штатная
финализация встречи спамила бы телеметрию и «неделя чистых логов» не наступила бы никогда.

## 5. Режимы shadow и enforce

Настройка `recording_owner_enforce` (по умолчанию `False`).

- **shadow** (дефолт): при позитивном mismatch — WARNING со структурным контекстом +
  ErrorBus-код `recording.owner_mismatch` (severity `warn`); поведение не меняется.
- **enforce**: типизированный отказ `{"status": "owner_mismatch", "owner": <владелец>,
  "requested": <проситель>}`; рекордер не тронут.

Токенные инварианты §4.2 (`unknown_generation`, `stop_in_progress`) действуют **в обоих
режимах безусловно** — это защита от потери данных, а не политика владения.
Отсутствие owner/token не отвергается никогда ни в одном режиме.

Флип на enforce — отдельным решением владельца после недели чистой телеметрии.

## 6. Тестирование

TDD по конвенции проекта, RED до кода. Обязательные кейсы:

- **Регресс promote** (критический): диктовка → старт встречи → `meeting_stop` работает
  в обоих режимах, ноль mismatch, токен сохраняется, spill не подменяется.
- Матрица §4.3 целиком, включая `unmanaged_recording` и `recorder_stopping`.
- Токенные инварианты: чужой токен не останавливает активную запись; двойной стоп с
  одним токеном → один ответ, один персист; стоп в окне finalizing → `stop_in_progress`.
- Порядок гейта: отвергнутый стоп НЕ убил preview/`_rt_partial`/RSF (проверяется
  состоянием коллабораторов после отказа).
- Отсутствие токена → legacy-путь, никогда не отказ.
- Инвалидация кэша при purge и при включении privacy.
- Swift: авто-heal не срабатывает при чужом владельце; `already_recording` — отказ с
  откатом ducking; ретрай только на транспорте; `owner_mismatch` имеет свою ветку.
- ubuntu-parity на всех новых тест-файлах; `make audit-all`; полный `swift test`.

**Живой e2e**: диктовка → promote во встречу → `meeting_stop` (один терминальный ответ,
ноль ложных mismatch); обрыв сокета в момент стопа → ретрай → replay результата;
тап Right Option при активной встрече → запись встречи цела, вставки не произошло.

## 7. Риски

| Риск | Митигация |
|---|---|
| Сломать горячий путь диктовки | shadow по умолчанию; promote-регресс — обязательный тест; токенные инварианты только добавляют отказы там, где сегодня молча ломается |
| Старый бинарь агента против нового бэкенда | отсутствие токена/owner никогда не отвергается (§4.2, §4.7) |
| Отвергнутый стоп убивает партиалы живой записи | гейт первой строкой phase_a (§4.2, F6) |
| RAM-кэш переживает privacy-purge | инвалидация при purge и при включении privacy (§4.4) |
| Call assist остаётся вне модели | задокументировано как известный bypass (§3), закрыт только достижимый отказ `unmanaged_recording` |
