# Чтение настроек не должно вставать в очередь за историей

Дата: 2026-08-12. Повод — живой инцидент владельца 14:0x: субтитры на видео
показали текст (F3 сработал), но бэкенд всё равно лёг, агент его
форс-рестартнул. Разбор показал причину, к live-субтитрам отношения не
имеющую.

## 1. Корень (доказан логом, не гипотеза)

`StateStore.load_settings()` (`backend/state_store.py:455`) читает
`settings.json`, но берёт `self._lock()` — а это
`self.lock_path = self.data_dir / "history.lock"` (строка 100), тот же
эксклюзивный flock, что охраняет всю историю.

Privacy-гейт обязателен почти в каждом IPC-хендлере (CLAUDE.md,
«Privacy-mode gate pattern») и читает настройки через `cached_settings()`;
на промахе 5-секундного TTL идёт в `load_settings()` → в очередь за историей.

Живая цепочка (`backend.log`, 2026-08-12):

```
14:01      тост «Не хватило памяти» (MLX OOM)
14:08:04   MLX watchdog timeout 120.0s (model=whisper-large-v3-mlx)
14:07:45   StateStore._lock(): state_store.py:1408:_load_active_items_with_lock
           держал эксклюзивный flock
14:07:44   ×20+  state_store.py:457:load_settings ждёт эксклюзивный flock
14:07:41   ×11   handle_request завис дольше 180с (live_subs_ingest и др.)
14:07:48   GracefulShutdownHandler — агент форс-рестартнул бэкенд
```

Держателя назвала диагностика из `2acd9de8` — она отработала ровно как
задумана. Но 30-секундный bounded acquire оттуда всё ещё выше практического
порога: Swift-агент объявляет бэкенд зависшим раньше.

**F3 (backpressure live-субтитров) эту проблему не закрывает вовсе**: там
`ingest` вис не на STT, а на общем локе ещё до начала работы. Моё
утверждение «после F3 зависаний нет» было верно на момент проверки и
устарело после теста владельца — фиксирую честно.

## 2. Почему НЕЛЬЗЯ просто дать настройкам свой лок

Есть задокументированный путь, берущий историю ПЕРЕД настройками:
`migrate_history_encryption` держит `_lock()` и синхронно зовёт
`progress_cb` → `event_bus.emit` → `event_replay._is_privacy_mode` →
`cached_settings` → `store.load_settings()`. Ровно ради него делали
per-thread реентерабельность (#1872).

Отдельный `settings.lock` создаёт классический lock-ordering риск:
history→settings в этом пути и settings→history в любом другом = дедлок.
Разделение локов требует явной дисциплины порядка захвата, аудита всех
~50 call sites и собственного гейта — это отдельная волна с решением
владельца, НЕ эта.

## 3. Решение: ограничить ОЖИДАНИЕ read-path настроек

Не новый лок, не смена порядка захвата — только верхняя граница ожидания
для чтения настроек.

- `SettingsService.cached_settings()` на промахе TTL пробует прочитать
  настройки с КОРОТКИМ бюджетом ожидания лока (`settings_read_lock_timeout_sec`,
  дефолт **0.5**). Не уложились — отдаём последнее известное значение
  (пусть слегка устаревшее) вместо блокировки.
- Экспозиция любого хендлера к чужой контенции падает со 180с/30с до
  полусекунды. Медленная операция с историей больше не кладёт весь бэкенд.
- Реализация опирается на уже существующий bounded-acquire механизм
  (`StateStore._lock(timeout=...)` из `2acd9de8`) — новых примитивов не
  вводим.

### 🔴 Направление отказа — fail-closed по приватности

Отдать «дефолты» при неудачном захвате НЕЛЬЗЯ: если владелец включил
privacy_mode, а мы под контенцией подставили дефолтный `False`, транскрипты
потекут в аналитику/экспорт. Правило:

1. Есть последнее известное значение (даже протухшее) → отдаём ЕГО.
2. Известного значения нет вообще (холодный старт + контенция) → отдаём
   дефолты, НО с принудительным `privacy_mode_enabled=True`.

То есть неизвестность всегда трактуется как «приватность включена».

## 4. Осознанно НЕ в скоупе

- Разделение локов settings/history (см. §2) — отдельная волна.
- Root cause самого MLX-зависания под OOM (whisper-large-v3 + LM Studio на
  36 ГБ) — вопрос среды и выбора модели, не локов.
- Долгие операции с историей (`_load_active_items_with_lock`) сами по себе:
  этот фикс делает их безвредными для ОСТАЛЬНЫХ хендлеров, но не ускоряет.

## 5. DoD

- Под удерживаемым чужим потоком локом `cached_settings()` возвращается за
  ~timeout, а не блокируется (тест с реально захваченным flock).
- Возвращается последнее известное значение; при его отсутствии — дефолты
  с `privacy_mode_enabled=True` (тест на обе ветки).
- Свежий путь (лок свободен) читает настройки как раньше, без изменения
  поведения и без лишних чтений файла.
- Таймаут настраиваемый; `0` = прежнее поведение (ждать сколько нужно).
- TDD RED→GREEN; pytest-кластер + flake8 + ubuntu-parity.
- Живая проверка: занять flock из отдельного процесса на 10с и убедиться,
  что `ping`/`get_settings` продолжают отвечать.
