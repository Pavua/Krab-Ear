# W1327 — AudioRecorder audit

**Branch:** `audit/recorder-W1327`  
**File audited:** `KrabEar/backend/recorder.py`  
**Date:** 2026-05-27  
**Status:** 5 findings

---

## Summary

`AudioRecorder` is a thread-safe start/stop audio capture wrapper around `sounddevice.InputStream`. Overall design is sound for typical short recordings (seconds to a few minutes). Five findings surfaced, rated by severity.

---

## Findings

### F1 — HIGH: Unbounded `_chunks` list grows to ~220 MB on 1-hour recording (W1170 F2 still open)

**Location:** `recorder.py:39, 149`

`_chunks` is an unbounded `list[np.ndarray]`. Each 100 ms chunk is 1600 samples × 1 channel × 4 bytes = 6.4 KB. After 1 hour: 36 000 entries × 6.4 KB = **~220 MB** pinned in RAM until `stop()` is called.

This is the known W1170 F2 open issue — confirmed still unaddressed in the current code.

Additionally, `snapshot_audio()` (called every ~3 s by `RealtimePartialTranscriber`) concatenates the **entire** `_chunks` list before slicing the last 12 s (line 114). On a 1-hour recording this allocates a ~220 MB temporary array on every call, causing sustained GC pressure even though only 192 KB of audio is actually used.

**Fix:** Implement a rolling deque capped at a configurable `max_record_sec` (e.g. 30 min). For `snapshot_audio`, slice from the tail of the deque without concatenating the full buffer — store a separate ring-buffer of the last N seconds.

---

### F2 — HIGH: No device parameter; user-selected input device is silently ignored

**Location:** `recorder.py:136–141`

`sd.InputStream` is opened with no `device=` argument. PortAudio always uses the system-default input. The GUI offers device selection (`list_audio_inputs` / `get_audio_devices`) and the user can pick a device, but `AudioRecorder.__init__` has no `device` parameter and `_worker` never passes one to `InputStream`. The selected device ID is never forwarded.

```python
# current
with sd.InputStream(
    samplerate=self.sample_rate,
    channels=self.channels,
    dtype="float32",
    blocksize=self.chunk_size,
) as stream:
```

**Consequence:** On a system with multiple inputs (e.g. USB headset + built-in mic), the user's device preference is always ignored at the PortAudio level.

**Fix:** Add `device: int | str | None = None` to `__init__`, store it, and pass `device=self.device` to `sd.InputStream`. When `device` is `None` (default), PortAudio picks the system default as before.

---

### F3 — MEDIUM: `snapshot_audio()` acquires `_lock` while iterating chunks, creating lock contention on long recordings

**Location:** `recorder.py:107–119`

`snapshot_audio()` holds `_lock` only to copy the chunk list reference (line 107–109), which is correct and fast. However `np.concatenate(chunks, ...)` at line 114 happens outside the lock — and on a long recording this takes measurable time (O(N) copy of all chunk data). This is correct for correctness but the shallow `list(self._chunks)` copy on line 109 does not copy the chunk arrays themselves; if `stop()` competes and calls `self._chunks = []` after the shallow copy, the already-referenced numpy arrays remain alive. This is benign but worth noting.

More importantly: `stop()` at line 77 re-acquires `_lock` and replaces `self._chunks = []` **after** joining the thread, while `snapshot_audio` might have a stale reference. No data corruption occurs, but a concurrent `snapshot_audio` call during `stop()` can return audio from a session that has already been finalized and cleared. No guard prevents this.

**Fix:** Document the intended behaviour explicitly — `snapshot_audio` is only valid while `is_recording` is `True`. Add a guard at the top of `snapshot_audio` to return an empty result if `not self._is_recording`.

---

### F4 — MEDIUM: USB device unplug mid-recording: `_is_recording` resets but caller gets no signal

**Location:** `recorder.py:161–165`

When `stream.read()` raises `OSError` (e.g. USB device unplug), the `except Exception` at line 161 logs the error and the `finally` block sets `_is_recording = False`. The worker exits silently.

The caller (e.g. `BackendService._handle_stop_recording`) has no way to distinguish a normal stop from a device-error stop. There is no callback, event, or flag that indicates recording ended abnormally. The UI does not display an error.

`_push_buffer_overflow_error` exists for overflow events (line 167), but no analogous path exists for device disconnection or stream errors. The `error_bus` is injected post-construction and could carry a `audio.device_disconnect` error code, but this is not wired.

**Fix:** Add an `on_error` callback parameter (similar to `on_audio_level`) or push an error via `_error_bus` with a dedicated `audio.device_disconnect` code when `_worker` exits abnormally (i.e. when `_stop_event` was not set by the caller before the exception).

---

### F5 — LOW: Test coverage gap — no test for `snapshot_audio` GC / memory behaviour during concurrent `stop()`

**Location:** `KrabEar/tests/test_recorder.py`, `test_audio_recorder_lifecycle.py`

Existing tests cover: basic start/stop, double-start/stop safety, device unavailable, device disconnect mid-recording, concurrent-start serialisation, tail trim, snapshot isolation, and clear-buffer safety after failure. That is strong coverage overall.

**Gap:** No test exercises `snapshot_audio` being called concurrently with `stop()` from a separate thread — the scenario where a stale reference is returned after the buffer is cleared (F3 above). No test asserts that `snapshot_audio` returns an empty result after `stop()` has completed.

**Fix:** Add a test in `test_audio_recorder_lifecycle.py` that calls `snapshot_audio()` from a background thread while `stop()` runs on the main thread, asserting that the returned array is a valid `float32` ndarray (no crash, no corrupted dtype) regardless of timing.

## Verdict

No data-corruption or crash-level bugs in typical use. The two HIGH findings (unbounded RAM growth on long recordings, and silently ignored device selection) are the most actionable. F4 (no error signal on USB unplug) is the next priority for production reliability. F1 directly tracks the open W1170 F2 item.
