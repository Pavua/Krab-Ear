## Summary

`core/mlx_lock.py` is a 40-line module that wraps a single `threading.RLock` instance behind a
factory function `mlx_lock()`. It is the central serialization primitive for all intra-process MLX
GPU access in Krab Ear (PR #71, 2026-04-19 SIGSEGV fix). The module is simple but carries
project-critical responsibility: any miss in coverage causes the same class of GPU corruption that
caused the original production crash.

Audit covers: singleton correctness, RLock vs Lock choice, timeout support, deadlock potential with
`mlx_inter_process_lock`, call-site coverage, profile-switch locking, `mx.clear_cache()` position
discipline, watchdog interaction, Sentry breadcrumbs, SIGTERM behavior, and test coverage.

**5 findings** (1 MED, 2 LOW, 2 INFO).

## F1 — MED: `mx.clear_cache()` at engine.py:981 is outside `mlx_lock()` context

**File:** `KrabEar/core/engine.py` lines 971–983  
**Pattern:** `_transcribe_with_fallback_impl` (the main transcribe path) calls
`_transcribe_model` (which holds `mlx_lock()`) and then invokes
`_maybe_run_diarization()` — which writes to the audio file and calls PyAnnote (PyTorch, not MLX).
After diarization returns, the code calls `_mx.clear_cache()` at line 981 with no
`mlx_lock()` held. This is intentionally outside the lock (PyAnnote does not need it), but if
another thread schedules a new `_transcribe_model` call after `_transcribe_model` returned and
before line 981 executes, `clear_cache()` races with live MLX Metal state in the concurrent thread.

The W63 rule (CLAUDE.md and `test_whisper_mlx_adapter_clear_cache_W1368.py`) requires
`mx.clear_cache()` to execute *inside* the `mlx_lock()` block. The `stt_whisper_mlx_adapter.py`
adapter follows this correctly (line 135 is inside the `with mlx_lock():` block). The
`engine.py:981` post-diarization flush does not.

**Risk:** On multi-threaded use (REST server + IPC server running concurrently), the post-diarization
`clear_cache()` may invalidate Metal heap allocations owned by a concurrently executing
`_transcribe_model` call, leading to `libmlx.dylib` assertion failures or silent result corruption.

**Suggested fix:** Either (a) move the post-diarization `clear_cache()` call to happen inside
`_transcribe_model` after the `mlx_lock()` block exits — effectively combining it with the lock
period — or (b) wrap the post-diarization flush in its own `with mlx_lock(): _mx.clear_cache()`
block. Option (a) is cleaner because diarization (PyAnnote/PyTorch) does not require the MLX lock
and should not block MLX serialization.

## F2 — LOW: `mlx_subprocess` watchdog daemon thread escapes `mlx_lock()` — acknowledged race, no Sentry breadcrumb

**File:** `KrabEar/core/mlx_subprocess.py` lines 116–172  
The `run_with_timeout()` watchdog spawns a daemon thread that calls `fn()` (which internally calls
`mlx_whisper.transcribe()`) *outside* the `with mlx_lock():` block held by the caller. The module
comment (W1358 F1) acknowledges the race and implements the mitigation: unbounded `thread.join()`
before raising `MLXTimeoutError`, ensuring the daemon completes before the lock is released by the
caller.

The mitigation is correct, but has a gap: if `MLXTimeoutError` is raised by the caller and caught
by a higher-level except clause *before* the unbounded join completes (possible if the join itself
is interrupted by a KeyboardInterrupt or SIGTERM delivered to the main thread during the wait), the
lock is released prematurely and the daemon may still be running.

Additionally, the watchdog timeout path calls `_notify_sentry_timeout()` and `_push_watchdog_hang()`
(Sentry + error bus), but there is no `add_breadcrumb()` call at the point of timeout detection for
the Sentry breadcrumb trail — so a subsequent crash report will not show which model was hanging
when the process was restarted.

**Suggested fix:** Add a `capture_exception`-level breadcrumb in the timeout branch:
```python
add_breadcrumb(
    category="mlx_watchdog",
    message="mlx_whisper timeout — waiting for daemon join",
    data={"model": model_name, "elapsed_sec": elapsed},
)
```

## F3 — LOW: Profile-switch `clear_cache()` (engine.py:606) runs without `mlx_lock()`

**File:** `KrabEar/core/engine.py` lines 590–608 (`switch_profile` method)  
When the quality profile changes (balanced ↔ max), the code calls `_mx.clear_cache()` to release
Metal GPU buffers from the old model. This call is not protected by `mlx_lock()`. If a transcription
thread holds `mlx_lock()` and is actively using MLX Metal buffers at the same time as another thread
calls `switch_profile()`, the `clear_cache()` call may corrupt the active inference.

CLAUDE.md notes: "Profile switches (balanced↔max) trigger model reload in MLX → protect these too."
The model-name assignment (`self.current_model = new_model`) on lines 600–601 is also unprotected —
a race between `switch_profile()` and `_transcribe_model()` reading `self.current_model` could cause
a transcription to run against a stale model name.

**Suggested fix:** Wrap the `clear_cache()` call (and the model-name mutation) in
`with mlx_lock(): ...`.

## F4 — INFO: No Sentry breadcrumb on `mlx_lock()` contention events

**File:** `KrabEar/core/mlx_lock.py` (design-level)  
The current `mlx_lock()` implementation is a bare `threading.RLock` with no instrumentation.
When Thread B waits for Thread A to release the lock (contention), there is no log line, no Sentry
breadcrumb, and no metric increment. The only observability is the downstream silence: IPC requests
pile up and the HealthMonitor detects backend unresponsiveness after ~6 seconds (2 × 3 s ping
interval).

CLAUDE.md records that Sentry breadcrumbs are the primary diagnostic tool for crash reports.
Without a breadcrumb at lock acquisition or contention, a SIGSEGV that happens while the lock is
held carries no information about which code path held the lock or for how long.

**Suggested fix (optional):** Wrap `_mlx_lock` in a thin `ContextManager` class that logs at DEBUG
level and emits a Sentry breadcrumb when contention is detected (e.g., `acquire(blocking=False)`
fails and the thread falls back to blocking acquire):
```python
if not _mlx_lock.acquire(blocking=False):
    add_breadcrumb(category="mlx_lock", message="contention — blocking acquire", ...)
    _mlx_lock.acquire()
```
This adds ~1 µs overhead per uncontested call and provides actionable Sentry context.

## F5 — INFO: `mlx_lock()` function return type annotation is `threading.RLock` but contracts `contextlib.RLock` interface

**File:** `KrabEar/core/mlx_lock.py` line 32  
The function signature is:
```python
def mlx_lock() -> threading.RLock:
```
`threading.RLock` is a factory function, not a class; `threading.RLock()` returns a private
`_RLock` instance. The correct type hint is `threading.RLock` as a nominal type only — this works
at runtime, but static type checkers (mypy, pyright) may warn that `threading.RLock` is not a
proper type annotation for the return value because `RLock` is defined as a function returning
`_RLock`. The correct annotation would be `threading._RLock` (private) or the nominal alias
`threading.RLock` with a `# type: ignore` comment.

This is annotation-only and carries no runtime risk, but may produce false mypy warnings if strict
mode is ever enabled in CI.

## Singleton correctness

VERIFIED: `_mlx_lock = threading.RLock()` is module-level — Python module singleton semantics
guarantee one instance per interpreter. All calls to `mlx_lock()` return `is`-identical object
(confirmed by `test_mlx_lock.py:TestMlxLockBasic.test_module_level_singleton`).

## RLock vs Lock

VERIFIED: `RLock` is the correct choice. The fallback chain in `_transcribe_model` calls
`mlx_whisper.transcribe()` in a retry loop while holding the lock. If any internal MLX path
re-acquires `mlx_lock()` (e.g., a model-reload callback), a plain `Lock` would deadlock. `RLock`
allows same-thread re-entry safely.

## Timeout / blocking-forever

No timeout support. By design — STT serialization must never be skipped to avoid GPU corruption.
The only timeout mechanism is the downstream MLX watchdog (`mlx_subprocess.py`) which raises
`MLXTimeoutError` after the configurable `MLX_TRANSCRIBE_TIMEOUT_SEC` (default 60 s) and then
performs an unbounded join before releasing the lock. BackendSupervisor covers the case where the
process stalls indefinitely.

## SIGTERM behavior

Python RLock releases automatically when the holding thread exits (OS thread cleanup). If SIGTERM
hits while `mlx_lock()` is held, the default signal handler interrupts the main thread, which
raises `SystemExit`. The `with mlx_lock():` context manager `__exit__` is called during stack
unwind, releasing the lock. Standard Python behavior — no special handling needed.

## Test coverage

Three dedicated test files cover `mlx_lock.py`:
- `test_mlx_lock.py` — RLock semantics, singleton, concurrency, re-export (Wave 175)
- `test_mlx_concurrency.py` — static source-text checks that all call sites import and use the lock
- `test_mlx_thread_safety.py` — concurrent thread serialization, singleton identity

Call-site enforcement is purely static (grep-based source checks in `test_mlx_concurrency.py`),
not runtime instrumented. This means new call sites added without the lock are caught only if the
test file is updated. The `engine.py:981` gap (F1) is not caught by existing tests.
