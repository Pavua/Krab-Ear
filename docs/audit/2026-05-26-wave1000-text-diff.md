## 1. Алгоритм

**Реализация:** `difflib.SequenceMatcher` из стандартной библиотеки Python — алгоритм
Ratcliff/Obershelp (не Myers, не patience diff). Применяется дважды:

- **char-level** — для `similarity_ratio` (точнее отражает близость строк).
- **word-level** — для построения списка `DiffChange` (`get_opcodes` → `equal/replace/delete/insert`).

**Производительность:** `SequenceMatcher` имеет сложность O(N×M) в худшем случае
(N, M — длины списков слов). Для типичных LLM rewrite-выходов (100–500 слов) это
приемлемо. Риск появляется только при длинных транскриптах >2000 слов; встроенная
эвристика `SequenceMatcher` (`autojunk=True` по умолчанию) отбрасывает частые токены
и ускоряет вычисление примерно в 2–4× — `autojunk` не отключён явно, значит
работает. **Вывод: для текущего use-case проблем нет.**

## 2. Токенизация слов

Используется `str.split()` без аргументов — разбивает по любому Unicode-пробелу
(пробел, таб, `\n`, `\r\n`). Это согласуется с другими модулями (`TextUtils`,
`FuzzySearcher`): одна и та же простая граница. Следствия:

- Пунктуация **прилипает** к словам: `"дела."` ≠ `"дела"` → при добавлении точки
  SequenceMatcher считает слово изменённым. Тест `test_punctuation_only_change`
  покрывает этот сценарий, но не утверждает конкретный счётчик — тест проходит
  независимо от поведения.
- Нет нормализации регистра: `"Это"` ≠ `"это"` (отражено в тесте
  `test_unchanged_words_counted` с `"BETA"` ≠ `"beta"`).

**Вывод (FINDING-1):** пунктуация прилипает к токенам — LLM rewrite, добавляющий
запятые/точки, будет показывать ложные remove+add пары вместо 0 изменений.
Это cosmetic issue для отображения diff'а, не функциональный баг.

## 3. Unicode / Кириллица / испанские акценты

`str.split()` и `SequenceMatcher` работают на уровне строк Python (Unicode codepoints).
Кириллические слова (`привет`, `мир`) сравниваются побайтово по codepoint —
комбинирующие диакритики (U+0300–U+036F) **не нормализуются** (нет NFC/NFD
нормализации). Испанские акценты (`café` vs `cafe`) трактуются как разные слова.

**Практика:** mlx-whisper возвращает NFC-нормализованный текст, LM Studio тоже —
на практике расхождений нет. Теоретический риск если источник данных не нормализован.

**Вывод (FINDING-2):** отсутствие Unicode-нормализации безопасно для текущего
pipeline (оба входа приходят от ML-инструментов с NFC), но fragile при ручном вводе.

---

## 4. Нормализация пробелов

`str.split()` схлопывает множественные пробелы, ведущие/хвостовые пробелы и
переносы строк — всё это тестами подтверждено (`test_handles_whitespace_changes`,
`test_handles_leading_trailing_whitespace`, `test_handles_newlines_as_whitespace`).
`"hello   world"` и `"hello world"` → идентичные списки слов → 0 изменений.

**Вывод:** whitespace-нормализация корректна и покрыта тестами.

---

## 5. Пустые входы

Оба случая обработаны через `(original or "").split()`:
- `""` → `[]` → `words_added=0, words_removed=0, summary="no text"`.
- `None` обработан через `or ""` (нет аннотации, но защита есть).

Три теста покрывают: both empty, original empty, rewritten empty. **Graceful.**

---

## 6. Схема вывода (OutputFormat)

`TextDiffResult` — стабильный `@dataclass` с полями:
```
changes: List[DiffChange]   # [{type, text, position}, ...]
similarity_ratio: float     # 0.0–1.0, rounded to 4 decimal places
words_added: int
words_removed: int
words_unchanged: int
summary: str
```

`engine.py` сериализует **только** скалярные поля в IPC-ответ (`llm_diff` dict):
`similarity_ratio`, `words_added`, `words_removed`, `words_unchanged`, `summary`.
Список `changes` в IPC **не передаётся** — это критически важно для PII (см. п. 10).
Схема стабильна с момента создания модуля.

## 7. Memory bound

`changes` список содержит по одному `DiffChange` на каждое слово обоих текстов
(O(N+M) объектов). При 5000-слов транскрипте — ~10000 объектов × ~100 байт ≈ 1 MB.
DP-таблица `SequenceMatcher` внутренняя, ~O(N×M) в RAM.

**Вывод (FINDING-3):** для транскриптов > 5000 слов (редкий случай) возможен
временный пик ~25–50 MB RAM для DP-таблицы. Не критично для M4 Max 36 GB, но
объект `TextDiffAnalyzer` создаётся на каждый вызов (`TextDiffAnalyzer()` — новый
инстанс в `engine.py:998`) — нет state leak между вызовами.

## 8. Wire Status (продакшн)

**Активно используется** в `core/engine.py`:
- `import` на строке 105.
- Вызов на строке 998: `TextDiffAnalyzer().compute_diff(cleaned_text, llm_result.text)`
  после каждого LLM rewrite (в основном пути транскрипции).
- Результат хранится в `self._last_llm_diff` и включается в IPC-ответ `transcribe`.

Других callers нет (ни в backend, ни в Swift side).

**Вывод:** модуль в продакшн-критическом пути, но логика fallback-safe: при ошибке
`llm_diff=None` возвращается без краша (try/except в engine.py).

## 9. Тестовое покрытие

8 тест-классов, ~35 методов, включая:
- Identical, empty, partial edit, full replace.
- Русский текст (Кириллица).
- Японский Unicode (similarity_ratio range check).
- Whitespace edge cases (3 варианта).
- Thread-safety (20 потоков параллельно).
- `DiffChange` / `TextDiffResult` dataclass structure.

**Пробелы:**
- Нет теста на пунктуацию с явным ожидаемым счётчиком (FINDING-1 не пойман тестами).
- Нет теста на `None` вход (хотя `or ""` защищает).
- Нет теста на очень длинный текст (>1000 слов) для проверки производительности.

**Вывод:** покрытие хорошее для happy path и edge cases, слабое для purity документации
пунктуации.

## 10. PII / Privacy

`compute_diff` получает на вход **полный текст транскрипции** (до и после LLM rewrite)
и возвращает каждое слово в `DiffChange.text`. Если транскрипция содержит имена,
телефоны, адреса — они попадут в `changes` list.

**Критически важно:** `engine.py` сериализует в IPC только агрегированные числа
(`words_added`, `words_removed`, `similarity_ratio`, `summary`) — **не `changes`**.
Сам объект `TextDiffAnalyzer` живёт только в памяти Python-процесса, не логируется.

**Вывод (FINDING-4):** PII остаётся в RAM до GC — нет утечки в логи или IPC. Риск
минимален. При включённом Sentry `breadcrumbs` политика privacy-respectful соблюдена
(breadcrumbs содержат только metadata, не текст — `backend/observability.py`).

## Итоговые findings (топ-5)

| # | Severity | Описание |
|---|----------|----------|
| F-1 | LOW | Пунктуация прилипает к токенам (`str.split`): запятая/точка = ложная замена слова |
| F-2 | INFO | Нет Unicode NFC-нормализации — safe для текущего pipeline, fragile для ручного ввода |
| F-3 | INFO | O(N×M) RAM для DP-таблицы при длинных текстах; не патологично для реального use-case |
| F-4 | OK | PII не утекает в логи/IPC — только агрегаты в ответе, полный `changes` list остаётся в RAM |
| F-5 | OK | Wire status: один caller (engine.py), fallback-safe, схема вывода стабильна |

**Статус модуля: HEALTHY.** Все критические пути покрыты, PII-risk под контролем.
Единственное улучшение низкого приоритета: токенизация с сохранением пунктуации
(или strip перед split) для точного подсчёта изменений при LLM rewrite.
