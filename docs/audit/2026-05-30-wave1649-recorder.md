## Context

`AudioRecorder` is a thread-safe blocking recorder: `start()` spawns a daemon
worker thread that calls `sounddevice.InputStream.read()` in a loop, appending
`data.copy()` chunks under `self._lock`.  `stop()` signals `_stop_event`,
joins the worker (3 s timeout), then concatenates all chunks into a flat
`float32` array.  The class has no callbacks into sounddevice's own callback
mechanism — it uses the *blocking* read API exclusively, which is correct.

## Findings

### F1 — HIGH: `_error_bus` is never wired into `AudioRecorder` in production

**File:** `KrabEar/backend/service.py` (init block ~line 287–300) and
`KrabEar/backend/recorder.py` (`_push_max_duration_error`, `_push_buffer_overflow_error`).

`service.py` injects `self._error_bus` into four collaborators at startup:

```python
self._llm_rewriter._error_bus = self._error_bus      # ✓ wired
self.transcriber._error_bus   = self._error_bus      # ✓ wired
_mlx_sub._error_bus           = self._error_bus      # ✓ wired
self._startup_diagnostics._error_bus = self._error_bus  # ✓ wired
```

The `AudioRecorder` instance (`self.recorder`) is **absent from this list**.
Both `_push_max_duration_error()` and `_push_buffer_overflow_error()` guard
with `getattr(self, "_error_bus", None)` and silently return when it is `None`,
which is always the case in production.  A 4-hour recording cut-off or an
audio-buffer overflow therefore produces a log warning but **never reaches the
error bus or Sentry**.  The one test that wires the bus
(`test_error_bus_phase_b_wave60.py:185 recorder._error_bus = bus`) works only
because it sets the attribute manually.

**Fix:** Add one line after the existing wiring block in `service.py`:
```python
self.recorder._error_bus = self._error_bus
```

### F2 — MED: Audio data and memory are silently lost when MAX_RECORDING_SAMPLES is hit

**File:** `KrabEar/backend/recorder.py` lines 212–222 and `stop()` lines 79–81.

When the worker detects that the chunk would exceed `MAX_RECORDING_SAMPLES`:

1. It sets `self._is_recording = False` (under lock).
2. Calls `_push_max_duration_error()` (see F1 — silently no-ops in prod).
3. Breaks out of the loop; the worker thread exits.

Any subsequent call to `stop()` immediately returns `None` because
`_is_recording` is already `False` (line 81: `return None`).
`RecordingCoreService._stop_recorder_guarded` propagates `None` back to
`handle_stop_recording`, which returns an `"already_stopped"` sentinel.

Consequences:
- The entire audio accumulated so far (up to ~880 MB at 4 h) is **discarded**
  — `self._chunks` is never drained.
- The list of `np.ndarray` chunks stays allocated until the **next** `start()`
  call (line 68: `self._chunks = []`), creating a transient memory spike that
  can persist for minutes if the user does not immediately re-record.
- The upper-layer service has no way to return partial audio to the transcriber.

**Fix:** In the `MAX_RECORDING_SAMPLES` branch, save a reference to the
accumulated chunks into a dedicated `_pending_chunks` field, then expose them
via a `drain_pending()` method (or return them via a custom exception/return
value from `_worker`).  At minimum, the worker should set
`self._chunks = []` before breaking to release memory immediately.

### F3 — MED: `_push_max_duration_error` called while holding `self._lock`

**File:** `KrabEar/backend/recorder.py` lines 212–221.

The docstring of `_push_max_duration_error` correctly notes it is "called from
`_worker` under `self._lock`".  Tracing the call chain:

```
recorder._lock held
  → error_bus.push()          # acquires error_bus._lock
    → event_bus.emit()        # acquires event_bus._lock (outside error_bus lock)
      → SSE subscriber callbacks (arbitrary code)
```

`error_bus.push()` is designed to avoid re-entrancy: it releases its own lock
before calling `event_bus.emit()`.  However, `recorder._lock` is still held
throughout the entire chain, including the SSE subscriber callbacks.  Any SSE
subscriber (or future code) that attempts to call `recorder.is_recording`,
`recorder.snapshot_rms()`, `recorder.get_duration_sec()`, or any other
lock-acquiring method on the same `AudioRecorder` instance will **deadlock**
because `threading.Lock` is not re-entrant.

`_push_buffer_overflow_error()` at line 211 avoids this issue entirely — it is
called *before* the `with self._lock:` block, which is the correct pattern.

**Fix:** Extract the error-push calls to *after* the lock is released, matching
the `_push_buffer_overflow_error` placement.  Example:
```python
with self._lock:
    ...
    if over_limit:
        self._is_recording = False
        should_push_max_duration = True
        break
    ...
if should_push_max_duration:
    self._push_max_duration_error()
```

### F4 — MED: `snapshot_rms` uses a chunk reference captured under lock, but numpy work runs outside

**File:** `KrabEar/backend/recorder.py` lines 180–190.

```python
def snapshot_rms(self) -> float:
    with self._lock:
        if not self._is_recording or not self._chunks:
            return 0.0
        last_chunk = self._chunks[-1]       # reference captured under lock
    flat = last_chunk.reshape(-1).astype(np.float32)   # work done outside lock
```

`last_chunk` is a reference to the same `np.ndarray` object that was
`data.copy()`'d by the worker and appended to `self._chunks`.  Because the
worker always calls `data.copy()` before appending, and `stop()` replaces the
entire `self._chunks` list atomically (it does `chunks = list(self._chunks)`,
then `self._chunks = []`), the numpy array referenced by `last_chunk` is never
mutated in-place after it is appended.  **There is no data-corruption risk with
the current code.**

However, if a future change were to pass the raw `data` buffer (without
`.copy()`) directly to `_chunks`, this pattern would silently alias a
sounddevice-managed memory region.  The pattern is fragile and should be
documented with an explicit comment.

**Note for future contributors:** The `.copy()` call at line 223 is
**load-bearing** for `snapshot_rms` thread safety.  Do not remove it.

### F5 — LOW: `stop()` duration includes `thread.join()` wait time (up to 3 s)

**File:** `KrabEar/backend/recorder.py` lines 85–90.

`stop()` sets `_stop_event`, then calls `thread.join(timeout=3.0)`.  Only
*after* the join completes does it read `time.monotonic() - self._started_at`
to compute `duration`.  If the worker is blocked in `stream.read()` and takes
the full 3-second timeout to unblock, the reported duration will be inflated by
up to 3 seconds.  Normal PortAudio behaviour: `stream.read()` blocks for
exactly one `blocksize` period (0.1 s at 16 kHz with `chunk_size = 1600`), so
in practice the join completes quickly.  However, on a heavily loaded system or
if PortAudio stalls (e.g. device disconnected mid-read), the reported duration
could be off by up to `timeout_sec`.

**Fix:** Capture the stop timestamp immediately before `_stop_event.set()` and
use that for duration:
```python
stop_ts = time.monotonic()
self._stop_event.set()
thread.join(timeout=timeout_sec)
duration = max(0.0, stop_ts - self._started_at)
```

### F6 — LOW: No test covers the `stop()` → `None` path when max-duration auto-stop fires

**Files:** `KrabEar/tests/test_audio_recorder_bounded_W1331.py`,
`KrabEar/tests/test_audio_recorder_lifecycle.py`.

`test_audio_recorder_bounded_W1331.py` tests that the worker *sets
`_is_recording = False`* when `MAX_RECORDING_SAMPLES` is reached, but there is
no test that verifies:

1. A subsequent `stop()` call returns `None` (not `(audio, duration)`).
2. `self._chunks` is cleared (or at least not growing after auto-stop).
3. `RecordingCoreService.handle_stop_recording` returns the
   `"already_stopped"` sentinel rather than raising.

The first two are directly observable without integration infra; the third
requires a fake recorder that simulates the auto-stop state.
