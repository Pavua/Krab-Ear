# Аудит AudioFingerprinter — Wave 1063

**Дата:** 2026-05-26  
**Аудитор:** Sub-agent W1063 (read-only)

## Резюме

`AudioFingerprinter` — лёгкий детектор дублирующихся аудиозаписей на основе 4 признаков (спектральный центроид mean/std + ZCR mean/std), квантованных в uint16 и хешированных через SHA-256. Класс **подключён** к production-коду через `AudioAnalyticsService` и IPC-метод `check_audio_duplicate`. Тесты присутствуют (21 кейс), но фундаментальная проблема в методе `compare()` делает систему практически бесполезной для реального обнаружения дубликатов.

---

## Находки

### F1 — КРИТИЧНО: `compare()` использует Hamming-расстояние на SHA-256 — метрика бессмысленна

**Файл:** `core/audio_fingerprint.py`, строки 56–86  
**Серьёзность:** Высокая (логическая ошибка)

Метод `compare()` вычисляет число совпадающих битов Хэмминга между двумя SHA-256 хешами. SHA-256 — криптографическая хеш-функция с лавинным эффектом: минимальное изменение входа полностью перемешивает все 256 бит выхода. Два разных хеша будут иметь ~50% совпадающих битов по вероятности, независимо от того, насколько близки или далеки исходные аудио.

**Эмпирическое подтверждение:**
```
Белый шум (seed=1) vs белый шум (seed=2): similarity=0.47
Синус 440 Hz + шум SNR~60дБ (почти идентичны): similarity=0.51
Синус 100 Hz vs синус 7000 Hz (совершенно разные): similarity=0.47
Случайные SHA-256 пары: mean=0.499, std=0.032
```

**Следствие:** Метод `is_duplicate_audio()` с `threshold=0.95` (дефолт) детектирует только точные копии (совпадение до бита). Любое реальное отличие (кодек, шум, нормализация) даёт similarity ≈ 0.5, что всегда ниже порога. Метрика сходства бинарна (0.5 для всех разных, 1.0 для идентичных), а не градуальна.

**Исправление:** Сравнивать нужно либо (а) сами 4 числовых признака (Euclidean/cosine distance), либо (б) применять перцептивный хеш (perceptual hash / locality-sensitive hash) типа `simhash` из признаков вместо SHA-256. Пример правильного подхода:

```python
def compare(self, fp1: str, fp2: str) -> float:
    # Хранить [sc_mean, sc_std, zcr_mean, zcr_std] напрямую,
    # или декодировать uint16 обратно из raw bytes перед SHA-256
```

### F2 — ВЫСОКАЯ: Чрезмерно грубое пространство признаков — только 4 числа на всё аудио

**Файл:** `core/audio_fingerprint.py`, строки 133–174  
**Серьёзность:** Высокая (качество алгоритма)

Вектор признаков состоит ровно из 4 float-значений: `[sc_mean, sc_std, zcr_mean, zcr_std]`. Для 1-часового аудио (3 600 × 16 000 / 512 ≈ 112 500 фреймов) вся информация агрегируется в 4 числа. Это означает:

- Два совершенно разных разговора могут иметь одинаковый SC-mean ≈ 2000 Hz и ZCR ≈ 0.15 → **коллизия** при одинаковых квантизованных значениях.
- Порядок звуков игнорируется: первые 30 мин тишины + 30 мин речи = 30 мин речи + 30 мин тишины.
- **Эффективное пространство:** 65 536⁴ = 2⁶⁴ теоретических хешей, но практически речевые файлы занимают крайне малый подпространство, сильно повышая вероятность коллизий.

**Исправление:** Использовать multi-frame feature vector (например, MFCC-статистики по 13 кепстральным коэффициентам) или разбивать аудио на сегменты с отдельными fingerprints для каждого.

### F3 — СРЕДНЯЯ: Неверный диапазон scale для `sc_std` в квантизаторе

**Файл:** `core/audio_fingerprint.py`, строка 182  
**Серьёзность:** Средняя (теряется половина разрешения)

```python
scales = [8000.0, 8000.0, 1.0, 1.0]  # по паре mean/std для SC и ZCR
```

`sc_std` масштабируется к диапазону `[0, 8000]`, но для речевого аудио стандартное отклонение центроида практически никогда не превышает ~4000 Hz. Эмпирически:

```
Широкополосный шум: sc_std=73.2 (нет ни одного реального случая >4000)
Речеподобный сигнал: sc_std=263.4
```

Следствие: верхняя половина диапазона uint16 для `sc_std` никогда не используется, эффективно урезая разрешение этого признака до ~15 бит из 16.

**Исправление:** Откалибровать `scales` на реальных данных. Разумная оценка: `sc_mean` → 8000, `sc_std` → 3000, `zcr_mean` → 1.0, `zcr_std` → 0.5.

### F4 — СРЕДНЯЯ: Нет хранения фингерпринтов в `StateStore` — дубликаты не проверяются при записи

**Файл:** `backend/audio_analytics_service.py`, строки 195–228  
**Серьёзность:** Средняя (функциональный пробел)

IPC-метод `check_audio_duplicate` требует передачи **двух аудио-массивов** напрямую через IPC. Фингерпринты не сохраняются в `StateStore` при транскрипции. Это означает:

- Нет автоматической проверки дублей при импорте нового аудио.
- Для сравнения с историческими записями нужно загружать все .wav файлы в память.
- `DuplicateDetector` (`core/duplicate_detector.py`) работает по текстовому сходству — аудиофингерпринт к нему не подключён.

Фактически модуль — утилита «сравни два массива», а не «проверь дубль при импорте».

### F5 — СРЕДНЯЯ: Отсутствие тестов робастности к реальным трансформациям

**Файл:** `KrabEar/tests/test_audio_fingerprint.py`  
**Серьёзность:** Средняя (пробел тестирования)

Тесты покрывают детерминированность, короткое аудио, многоканальный ввод и потокобезопасность. **Не покрыто:**

- Реальное сжатие (MP3/AAC re-encode): ожидаемый результат неизвестен, но после F1 — similarity будет ≈ 0.5.
- Ресемплинг: 440 Hz при 48 кГц vs 16 кГц даёт similarity=0.5 (тест W1063 подтвердил).
- Добавление тишины в начало/конец (padding).
- Изменение темпа (pitch-shift / time-stretch).

Тест `test_slightly_noisy_copy_similarity` (строка 175) явно не устанавливает нижнюю границу сходства («проверяем только что метрика вычислена») — то есть разработчик знал о проблеме, но не закрепил требование.

### F6 — НИЗКАЯ: Производительность на 1-часовом аудио приемлема, памяти не хватает для IPC

**Файл:** `backend/audio_analytics_service.py`, строки 208–228  
**Серьёзность:** Низкая (эксплуатационное ограничение)

Эмпирически: fingerprint 10 с аудио занимает ~4 мс → 1 ч аудио ≈ 1.4 с CPU. Производительность хорошая.

**Проблема IPC:** Аудио передаётся как `list[float]` через Unix socket. 1 час моно-аудио при 16 кГц = 57 600 000 float32 = ~460 МБ в JSON (каждое число ~8 байт текста). Это практически невозможно передать через IPC. На практике метод применим только к коротким фрагментам (<30 с), но документация и тест IPC этого не указывают.

---

### F7 — НИЗКАЯ: Приватность — фингерпринт необратим, но compare() возвращает его открытым

**Файл:** `backend/audio_analytics_service.py`, строки 222–224  
**Серьёзность:** Низкая (незначительный privacy риск)

Финальный хеш SHA-256 — необратим: восстановить аудио по 64-символьной строке невозможно. Это правильно.

Однако IPC-ответ `check_audio_duplicate` возвращает `fingerprint1` и `fingerprint2` открытым текстом в ответе. Если фингерпринты хранятся в логах/истории, злоумышленник с доступом к логам может установить факт появления одного и того же аудиофайла в разное время (linkability attack). Для голосового транскрибера с режимом конфиденциальности это потенциальный privacy leak.

## Рекомендации

1. **Срочно (F1):** Заменить `compare()` на Euclidean distance по 4 числовым признакам (или хранить признаки отдельно от SHA-256 хеша).
2. **Среднесрочно (F2):** Расширить вектор признаков до 12–20 значений (MFCC-статистики).
3. **Среднесрочно (F4):** Сохранять fingerprint в `HistoryItem` при транскрипции; подключить к `AutoDeduplicator`.
4. **Быстро (F3):** Откалибровать `scales[1]` с 8000 → 3000.
