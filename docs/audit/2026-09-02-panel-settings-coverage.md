# Покрытие настроек панелью Krab Ear.app — замер 02.09.2026

**Повод.** Владелец спросил: «а где я могу включить следование за курсором?»
Переключателя не было и появиться не мог: ключ `overlay_follow_cursor`
разбирался в `AgentSettings.init(from:)`, но отсутствовал в `toPayload()`, а
панель сохраняет настройки только через него. Настройка, включаемая лишь сырым
IPC-вызовом из терминала, для владельца равна отсутствующей.

Дальше — требование, которое стоит понимать буквально: **всё, что настраивается,
должно настраиваться из панели.**

## Метод

Три источника «панель может ЗАПИСАТЬ ключ» на стороне Swift:

| путь | что это |
|---|---|
| `AgentSettings.toPayload()` | общий путь панели (`persistSettingsPayload`) |
| `applySettingsPatch([...])` | точечный патч поверх общего пути |
| `ipcClient.call("set_settings", …)` | прямой вызов из отдельной секции |

Ключ, не встреченный ни в одном, панель изменить не может. Отдельно считаются
ключи, которые в Swift лишь **упоминаются** — их показывают, но не редактируют.

Живой список ключей снят у работающего backend'а через `get_settings`, а не из
`DEFAULT_SETTINGS`: расхождение между статическим словарём и живыми настройками
— самостоятельный класс ошибок (урок Wave 58).

## Результат

| состояние | ключей | доля |
|---|---:|---:|
| редактируется из панели | 86 | 33 % |
| включается только пакетом, выключить нельзя | 7 | 3 % |
| только показывается | 3 | 1 % |
| панель не знает вовсе | 162 | 63 % |
| **всего живых настроек** | **258** | |

Двое из 86 редактируются не через `set_settings`, а через собственный
IPC-метод: `history_encryption_enabled` (`set_history_encryption`) и
`stt_hotwords` (`add_stt_hotword` / `remove_stt_hotword`). Первый замер этого
канала не считал и записал их в «панель не знает» — ошибка исправлена, и в
методе теперь три канала записи, а не два.

🔴 **Односторонний пакет.** Кнопка «рекомендованная настройка»
(`apply_recommended_setup`) включает разом 15 ключей, и для семи из них
отдельного контрола в панели нет:

`action_items_auto_extract`, `auto_dedup_enabled`, `auto_save_transcripts`,
`calendar_link_enabled`, `realtime_silence_filter_enabled`,
`smart_silence_skip_enabled`, `stt_sensevoice_enabled`.

Их можно включить одним нажатием и уже нельзя выключить — обратной дороги из
панели нет. Асимметричное управление хуже отсутствующего: пользователь считает,
что вернёт как было, а вернуть нечем.

🔴 **Мёртвая цепь авточистки.** Дашборд приватности печатает
`auto_cleanup_enabled` / `auto_cleanup_after_days` как политику хранения, но
исполнять её некому — цепь оборвана в трёх местах сразу:

| звено | состояние |
|---|---|
| `StateStore.auto_cleanup_old()` | реализован, покрыт тестами, **ни одного вызова в проде** |
| событие `disk.auto_cleanup_requested` | `DiskSpaceMonitor` его шлёт, **подписчиков нет** |
| настройки `auto_cleanup_*` | читаются только чтобы напечатать их на дашборде |

Живая ретенция — соседняя: `auto_purge_*`, её крутит `PurgeScheduler`, и у неё
есть контролы. То есть дашборд показывает одну политику, а работает другая.
Дороже всего здесь класс «тест подтверждает дыру»: `auto_cleanup_old` покрыт
тестами, они зелёные, и зелёными останутся, пока метод никто не зовёт.

Решение требует выбора владельца, потому что варианты расходятся по смыслу:
**достроить** (подписчик на событие + гейт по настройке + громкое уведомление,
дефолт остаётся выключенным — дорогие части уже написаны и протестированы) либо
**удалить** цепь целиком. Автоудаление истории по нехватке места — необратимое
действие, поэтому подключать его молча нельзя.

## Закрыто этой волной

* `overlay_follow_cursor` доехал до `toPayload()` и получил переключатель
  «Оверлей за курсором» в **обоих** вариантах дизайна (вариант выбирается
  UserDefaults-ключом `KrabEar_UseClaudeDesign`, поэтому «работает у меня»
  ничего не доказывает — правка в один вариант оставляет второй мёртвым).
* Гард `scripts/audit_agent_settings_symmetry.py` — `init(from:)` и
  `toPayload()` обязаны покрывать один набор ключей. Обратная асимметрия хуже
  прямой: значение уходит на backend, но эхо ответа его не читает, и контрол
  ведёт себя как «щёлкнул — вернулось обратно».
* `OverlayFollowCursorWiringTests` — source-контракт на четыре независимых
  участка проводки. Проверен мутацией: снятая строка `addArrangedSubview`
  роняет тест (построенная, но не добавленная строка — ровно тот класс
  декоративной проводки, что месяцами держал мёртвым `setupErrorBus`).

## Что делать с остальными 171

Ручные контролы на каждый ключ — не тот масштаб: настройки прибавляются
быстрее, чем секции панели, и следующий `overlay_follow_cursor` появится тем же
способом. Предлагаемый порядок:

1. **Секция «Все настройки»** — таблица с поиском, типовым редактором на строку
   (переключатель / поле / шаг), строится прямо из `get_settings`. Новая
   настройка backend'а появляется в панели сама, без правки Swift.
2. **Первоклассные контролы** — тем ключам, которыми владелец пользуется
   регулярно (уведомления, шумоподавление, семантический поиск, параметры
   встречи), в их тематических секциях.
3. **Секреты** (`hf_token`, `llm_api_key`, `smtp_*`, `lm_studio_api_key`) — в
   общей таблице только как «задано / не задано»: `get_settings` отдаёт их
   как `REDACTED`, и запись этой строки обратно затёрла бы живой ключ (защита
   на стороне backend'а уже есть, но показывать звёздочки честнее).
