# Wave 906 — Аудит recording-модулей

**Дата:** 2026-05-26  
**Модули:** `recording_merger`, `recording_comparison`, `recording_insights`, `recording_scheduler`

---

## recording_merger.py (~272 LOC)

**Назначение:** Объединяет несколько history-записей в одну.

**Ключевые детали:**
- Публичный API: `merge_items()` + `preview_merge()` (без записи в store).
- Store не хранится в конструкторе — передаётся явно в каждый метод (паттерн остальных сервисов).
- Объединение текста — хронологическое (сортировка по `item.ts`), разделитель `\n\n` по умолчанию, настраивается через IPC.
- Агрегации: длительность суммируется, confidence усредняется, diarization-сегменты конкатенируются, теги дедуплицируются, language/translation берётся у первой записи с непустым значением.
- `delete_originals=True` — помечает originals tombstone после успешного merge.
- Результат содержит `merged_from: [ids]` и `deleted_originals: bool`.

**Замечания:** Нет защиты от merge записи с самой собой (дубликаты в item_ids не проверяются). `_format_ts_label` тихо возвращает сырую строку при ошибке парсинга — приемлемо.

## recording_comparison.py (~229 LOC)

**Назначение:** Side-by-side сравнение до 10 записей (TF-IDF cosine similarity).

**Ключевые детали:**
- Лимит MAX_ITEMS=10; дубликаты в item_ids отвергаются (ValueError).
- Матрица сходства NxN заполняется симметрично (вычисляет только верхний треугольник).
- TF-вектор — бинарный (1/n), без IDF-взвешивания. Подходит для коротких транскрипций.
- Статистика (min/max/avg/std) по `audio_duration_sec` и `confidence` через `_stat_dict()`.
- `common_words` = пересечение токен-множеств ВСЕХ записей; `unique_words_per_item` = токены, отсутствующие в остальных.
- `_view_to_dict()` — сериализатор IPC-ответа (модуль-уровень, не метод класса).

**Замечания:** `_build_tf` делит на `len(tokens)` (размер множества, не длину текста) — при коротких текстах нормировка немного смещена, но функционально корректна. `common_words` при `n=1` возвращает все токены единственной записи (edge case явно задокументирован).

## recording_insights.py (~637 LOC)

**Назначение:** Эвристические инсайты по истории без LLM — 6 типов анализа.

**Ключевые детали:**
- Минимальный порог: 3 записи в окне (иначе пустой список).
- Типы инсайтов: `peak_productivity` (час-пик), `language_shift` (смена доли языка), `quality_improvement` (изменение confidence), `recording_streak` (серия дней), `most_discussed_topic` (кластеры ключевых слов RU/ES/EN), `speaking_pace_change` (изменение WPS).
- Каждый инсайт несёт поле `confidence: float` (0–1), вычисляемое из размера выборки и величины изменения.
- `_TOPIC_CLUSTERS` — 5 тематических кластеров (технологии/работа/здоровье/образование/финансы) с ключевыми словами на трёх языках.
- `get_daily_insight()` выбирает инсайт с максимальной уверенностью.
- Вспомогательные геттеры (`_get_ts`, `_get_confidence`, etc.) поддерживают как объекты HistoryItem, так и dict — хорошая гибкость.

**Замечания:** `_compute_recording_streak` вычисляет серию дней в наивном цикле O(N) по дням — корректно, но при streak > 365 может быть медленным. Стоп-словный список RU/ES/EN полный (~100 слов), но не разделён по языку — возможны редкие коллизии.

## recording_scheduler.py (~214 LOC)

**Назначение:** Планировщик будущих записей с персистентностью в JSON.

**Ключевые детали:**
- Хранилище: `{data_dir}/scheduled_recordings.json` (list или dict, оба формата поддерживаются при загрузке).
- Статусы: `pending` → `completed` / `cancelled`.
- `check_and_trigger()` — polling-метод: возвращает задание если текущее время попадает в окно `[start_time, start_time + 5s]`; само переводит статус в `completed`. Вызывающий код несёт ответственность за реальный старт записи.
- `get_next_scheduled()` — ближайшее pending-задание в будущем.
- `_parse_datetime()` — явно заменяет `Z` на `+00:00` для совместимости Python < 3.11.
- Thread-safe через `threading.Lock` на все операции записи/чтения.

**Замечания:** `check_and_trigger()` за вызов обрабатывает только одно задание (первый совпавший `break`-эквивалент через `return`). При одновременных заданиях с разницей < 5 с запустится только одно — остальные останутся `pending` и пропустят своё окно. Нет автоочистки старых `completed/cancelled` записей — файл растёт неограниченно.
