## 0. Положение дел (снимок 2026-07-07)

Продукт feature-complete как локальный голосовой комбайн для macOS:
- STT (mlx-whisper + GigaAM RU + SenseVoice/Parakeet/sherpa опционально), диаризация (pyannote/MPS),
  перевод RU↔ES/EN, LLM-полировка (LM Studio, gemma-4-e4b + cloud-fallback опционально), TTS (Silero/Kokoro/say).
- Wake word «hey jarvis» ЖИВОЙ в проде (openWakeWord, IPC-поллинг) — A2 карты идей закрыт 2026-07-05.
- Sparkle auto-update ЖИВОЙ: CI-релиз по тегу/dispatch, EdDSA, GitHub Releases, appcast на ветке —
  C1 закрыт 2026-07-07 (PR #1847, первый релиз v2.4.0).
- ~360 IPC-методов, 18 извлечённых сервисов, ~6500+ тестов, набор CI-guard'ов (8+ аудит-скриптов) против классов регрессий.
- Экосистема: Voice Gateway (сосед-проект, WS/REST мост готов), Main Krab (мозг, Telegram userbot).

Ключевые архитектурные состояния и известные долги:
1. **2-EventBus гэп ЗАКРЫТ Волной 2** — IPC- и REST-процессы по-прежнему имеют разные шины,
   но production `EventBridge` переносит события через loopback/HMAC и переживает недоступность REST.
   Не восстанавливать старый polling и не строить второй мост; оставшийся долг — само слияние процессов (M2).
2. **Дубль тяжёлого состояния**: `rest_server.py:472-476` держит собственные AudioEngine/StateStore/
   Transcriber/TTSService → лишняя RAM, межпроцессные MLX-локи, два launchd-агента.
3. Нотарификации нет (самоподпись «Krab Ear Dev Local») — для владельца ок, для внешних юзеров трение.
4. Русская wake-модель «Краб»: обучена (recall 0.80, fp/час 0.0 на валидации), но при живом включении
   2026-07-12 дала **шторм ложных срабатываний** сначала на клики клавиатуры, затем на собственное
   TTS-эхо через колонки → откачена на `hey_jarvis` (прод-дефолт). **T5b (дообучение с hard-негативами)
   ЗАКРЫТ как отрицательный результат 2026-07-13, PR #1875 (не мержится)**: три раунда fine-tune
   (batch 512/256/256 → 640/384/128 → 768/256/128) — recall плато 0.70-0.714 (гейт ≥0.75 не взят), а
   TTS-эхо-детекции неизменны (117→117→117) при любом весе негативов. Клавиатура улучшилась (62→5), TTS
   не сдвинулся — это потолок DNN(128)+100%-синтетический-позитив-корпус, не гиперпараметры. Два UX/арх-
   фикса **закрыты**: (a) детекция воровала фокус клавиатуры → PR #1873 (`3fd722ea`, non-activating
   путь); (b) self-echo → **арх-фикс паузы wake word на время своего TTS, PR #1876** (`WakeWordPauseReason
   .ttsPlayback` + `AVAudioPlayerDelegate`-трекинг). Дальнейший путь к `krab_ru` в проде: реальные (не
   синтетические) позитивные записи голоса владельца — отдельная волна, не приоритет.
5. `service.py` всё ещё ~3900 LOC (после −72% от пика) — извлечение продолжать оппортунистически.

## 1. Принципы исполнения волн (post-Fable)

Порядок любой волны размера M+ (проверен волнами wake word и Sparkle end-to-end):
1. **Брейнсторм → спека** (`docs/superpowers/specs/`) → **план** (`docs/superpowers/plans/`).
2. **Subagent-исполнение** плана (Sonnet-воркеры, worktree-изоляция, циклы implementer → spec-review → quality-review).
3. **Ультракод-ревью всего диффа перед мержем** — гейт находок лично (не воркером). Окупился ×3 подряд.
4. **Живой e2e-смок** на реальных данных (`scripts/run_e2e_smokes.command` + сценарный смок фичи).
5. Мерж по зелёному CI (**поллинг строго по SHA коммита**) → деплой `build_and_deploy.command` из
   main checkout → parity-коммит → **Sparkle-релиз** (`gh workflow run release.yml -f version=X.Y.Z`).

Жёсткие правила (сводка, детали в `~/.openclaw/krab_runtime_state/free_workers.md` и CLAUDE.md):
- Воркерам НЕЛЬЗЯ запускать собранный агент-бинарь (SingleInstanceGuard убьёт прод) — только `codesign --verify`/`otool`.
- Git-мутирующий воркер = только `isolation: worktree`; точные списки `git add`, никогда `-A`.
- CI-ожидание: `gh run list --json headSha,status --jq 'select(.headSha|startswith("<SHA>"))'` —
  агрегатное «все чеки терминальны» ложно срабатывает на пустом списке (пропущенный webhook — реальный случай).
- Privacy: `privacy_mode_enabled` всегда побеждает; новые transcript-читающие хендлеры получают гейт.

### Волна 4 — Пакет A-болей — **ПОЛНОСТЬЮ ЗАКРЫТА 2026-07-09**
Разведка (3 параллельных read-only агента) скорректировала объём — 2 из 3 пунктов оказались почти/полностью
готовы, реальной постройки с нуля не потребовалось. Все три задачи выполнены параллельно в изолированных
worktree через subagent-driven-development.
- **A3 — Память исправлений** (PR #1859, смёрджен): оказалась УЖЕ РАБОЧЕЙ end-to-end (Cmd+Shift+R →
  `replace_word_in_last_transcript` → `_maybe_auto_learn_word()` → `stt_hotwords`, флаг в A1-пресете).
  Добавлен E2E regression-тест на цепочку без моков + явный feedback (menu-bar заголовок реально показывает
  «Слово «X» выучено в словарь STT.» вместо статичного «✓», по прецеденту `main+Bookmarks.swift` — 1-й
  раунд ревью поймал, что фидбек изначально уходил только в лог-файл, невидимый пользователю).
- **A4 — Streaming paste** (PR #1860, смёрджен): debounce/укрупнение чанков по границе слов + полная замена
  диапазона вместо молчаливого пропуска при ревизии partial. **4 раунда ревью, каждый нашёл реальную
  проблему**: (1) spec ок → code-quality нашёл 2 Critical — `handleFinal()` структурно недостижим в реальном
  stop-flow (SSE закрывается до IPC-ответа, хвост текста терялся тихо на каждой диктовке с debounce-флашем)
  + оптимистичный state-commit при провале paste/delete (риск отката чужого текста в другом приложении);
  (2) фикс обоих Critical → новый Important — фикс #2 отключил debounce-throttle при повторных провалах,
  риск retry-storm на main thread (проект уже страдал от AppHang такого класса — AGENT-K/M); (3) фикс через
  отдельный `lastFailureAt` backoff → узкий Important — тот же backoff случайно глушил единственный вызов
  ревизии в `handleFinal`; (4) `bypassBackoff`-параметр для единственного вызова → APPROVED. Явно вне
  скоупа: идеальный атомарный «один Cmd+Z = вся фраза» в произвольном стороннем приложении — недостижимо
  через AX/keystroke-симуляцию, цель «предсказуемо», не «атомарно».
- **A5 — Smart silence skip**: закрыто без кода — уже включён безусловно для всех через A1-пресет
  (`_RECOMMENDED_UNCONDITIONAL`). Формулировка «для длинных записей, порог из A1» подразумевала gate по
  длительности, которого никогда не было; владелец подтвердил — оставить как есть, порог не нужен.

Задеплоено, живой агент перезапущен (UUID 2991B0F8). Урок волны: **не доверяй первичной разведке на слово —

## 2026-08-07 — 🔴 Волна SIGSEGV-обработчика: прод лежал 8 часов молча

**Как нашлось.** Не по алерту. При проверке состояния после вчерашней
перезагрузки: launchd показывал юнит `ai.krab.ear.backend` как `running`
(pid 1057, аптайм 8ч), а IPC отвечал `ConnectionRefusedError`. Процесс жёг
CPU и не реагировал на SIGTERM — лечило только `kickstart -k`.

**Корень** (найден `sample <pid>` на живом зависшем процессе — по коду этого
не увидеть): `install_signal_handlers()` в `backend/observability.py` вешал
**Python-обработчик на SIGSEGV/SIGABRT**, чтобы послать событие в Sentry перед
смертью. CPython не исполняет такой колбэк в момент сбоя — C-уровень ставит
флаг и ВОЗВРАЩАЕТСЯ, ядро повторяет сбойную инструкцию → бесконечный ре-сбой.
Улики: поток записи 1902 сэмпла из 1966 в `_sigtramp` на
`PaUtil_ReadRingBuffer` (отсюда «AudioRecorder worker не завершился за 3.0 с»
в логе), главный поток — **46 вложенных** `handle_signals`.
**Честный крэш, после которого launchd поднял бы бэкенд за пару секунд,
превращался в многочасовой ТИХИЙ простой.** Sample сохранён:
`.remember/forensics/backend-1057-sigsegv-storm-2026-08-07.sample.txt`.

**Фикс:** `faulthandler.enable(all_threads=True)` — то же самое, но C-уровня и
signal-safe. Доказано живьём в изолированном процессе: старый обработчик →
процесс жив на 100% CPU через 8с; faulthandler → мгновенная смерть с кодом 139
и полным трейсбеком всех потоков.

**Два адверсариальных ревью подряд** (Opus, свежий контекст). Первое
подтвердило диагноз независимо + 2 MEDIUM / 4 LOW; главная находка — волна
убирала обработчик, который ХОТЯ БЫ НАМЕРЕВАЛСЯ послать crash-событие, не дав
замены: вердикт `shutdown_forensics.check_and_collect()` молча выбрасывался.
Добавлены `BackendService._report_unclean_restart()` + код
`system.unclean_restart` (severity=**error**, не warn: warn-tier батчится и
сбрасывается только при штатном завершении, которого в крэш-лупе не будет).
Второе ревью поправило переуверенность в формулировках: «дедлок в
`sentry_sdk.flush()`» уликами не подтверждён, равно согласован лайвлок —
докстринги переписаны на доказанное.

**Смежная находка того же дня — внешний монитор слеп.**
`~/.openclaw/krab_runtime_state/krab_ear/ear_watcher.json`:
`python_backend_down_count: 10013` при `last_alert: 96` — то есть ~103 дня
подряд «бэкенд лежит» и ни одного алерта. Причины: (1) `EAR_SOCKET_PATH` по
умолчанию `~/.krab_ear/ipc.sock`, которого не существует (реальный —
`~/Library/Application Support/KrabEar/krabear.sock`), env-override plist не
задаёт; (2) `check_python_backend()` проверяет `Path.exists()`, хотя докстринг
обещает «exists + responsive» — во время простоя файл сокета СУЩЕСТВОВАЛ.
Файл живёт в репозитории главного Краба (грязное дерево — не правила), бриф:
`.remember/FOR_KRAB_ear-watcher-blind-2026-08-07.md`.

**Открытые хвосты (задачи заведены, не в этой волне):**
1. **Swift self-heal не лечит заклиненный бэкенд.**
   `HealthMonitor.hangFiredForCurrentEpisode` сбрасывается ТОЛЬКО успешным
   пингом, а `BackendSupervisor.restartIfDeadDetailed()` на живом-но-заклиненном
   процессе возвращает `.alreadyAlive` и ничего не делает → ровно одна
   безрезультатная попытка, дальше тишина навсегда (sticky state without an
   exit). Лечение — эскалация к `forceRestartBackend()` под уже существующим
   `WedgedEscalationTracker`. 🔴 Обязательный дискриминатор: эскалировать только
   при `IPCError.socketConnectFailed` (отказ соединения = завис), НЕ при
   `.timeout` — здоровый-но-медленный бэкенд соединение принимает, и его рестарт
   уничтожит активную диктовку (инцидент 2026-07-22).
2. **Сам сегфолт в `PaUtil_ReadRingBuffer` не разобран** — фикс превратил вечное
   зависание в честный крэш с автоперезапуском (строго лучше), но теперь это
   станет ВИДИМЫМ crash-loop'ом. С `faulthandler` следующий крэш даст полный
   трейсбек в `logs/krab-ear-backend.err.log` — ждать первого дампа дешевле,
   чем гадать.

### Дополнение по итогам 2-го и 3-го раундов ревью (та же волна)

Раунды дали ещё 3 MEDIUM, каждый — реальный:

* **Вердикт форензики выбрасывался.** Волна убирала обработчик, который ХОТЯ БЫ
  НАМЕРЕВАЛСЯ послать crash-событие, не дав замены: `check_and_collect()`
  возвращал вердикт, а вызывающая сторона его игнорировала; единственным следом
  оставалась WARNING-строка, которую `sentry_sdk` по умолчанию превращает в
  breadcrumb, а не в issue. Добавлен `BackendService._report_unclean_restart()`
  + код `system.unclean_restart`.
* **Заявленный дедуп физически не мог сработать.** `_report_unclean_restart`
  зовётся ровно один раз за жизнь процесса, а дедуп `ErrorBus` — in-memory,
  умирает вместе с процессом. launchd (`KeepAlive=true`, `ThrottleInterval=5`)
  поднимает до ~720 раз в час → шторм в Sentry, как уже было на
  PortAudioError-лупе. Добавлен кросс-рестартовый лимит на диске.
* **Сам лимит был no-op ровно в целевом отказе.** Голый `write_text` усекает
  файл до записи: ENOSPC (полный диск — типовая причина таких смертей) или крэш
  между шагами оставлял нулевой файл, читавшийся как «отчётов не было» —
  ревьюер воспроизвёл 10 отчётов из 10 «рестартов». Класс «read-modify-write
  without a fail-safe». Фикс: `tmp` + `os.replace`, направление отказа
  развёрнуто на fail-closed, плюс защита от метки времени из будущего
  (скачок NTP давал вечное молчаливое подавление).

**Живой e2e новой цепочки пройден** на одноразовом инстансе: `kill -9` → маркер
выжил → следующий старт собрал форензику, записал файл лимита и положил в шину
`system.unclean_restart` (severity=error, `verdict=unclean_collected`).
🔴 Побочное наблюдение для будущих смоков: тред `startup-recovery` живёт
**дольше 25 секунд** (в `check_and_collect` два subprocess-вызова с таймаутами
по 30с) — первый прогон смока провалился именно потому, что процесс убили
раньше, чем тред дошёл до отчёта.

**Отдельным хвостом:** лимит ограничивает только ОТПРАВКУ события. Стоимость
самого лупа не тронута — каждый подъём по-прежнему целиком прогоняет
`check_and_collect()` (два subprocess'а + новый каталог `forensics/<ts>/`,
retention 5) до ~720 раз в час. Кандидат в отдельную мини-волну.
