# Шпаргалка: модели распознавания/синтеза речи (август 2026)

Собрано для двух задач: (1) архивный проект транскрибации — испанский/английский
приоритет, точность важнее скорости; (2) Krab Ear + Voice Gateway — живой
переводчик звонков, задержка важнее всего. Все модели ниже реально существуют
на Hugging Face на дату сборки этой шпаргалки (проверено поиском и, где
отмечено "ПРОВЕРЕНО ЖИВЬЁМ", реальным запуском на твоём MacBook M4 Max).

---

## TL;DR — что делать в первую очередь

1. **Архив (испанские/английские записи):** как только досчитается саммари —
   гнать через `mlx-community/whisper-large-v3-mlx` (уже есть в проекте, просто
   поправить `language=`) + параллельно A/B на тех же файлах через
   `mlx-community/parakeet-tdt-0.6b-v3` (ПРОВЕРЕНО ЖИВЬЁМ, работает и быстро,
   и на русском не хуже прод-Whisper).
2. **Krab Ear / Voice Gateway — realtime:** самый интересный кандидат —
   **Qwen3-ASR** (52 языка, есть MLX-порт, Apache 2.0) — не успел протестировать
   живьём (см. "Из-за чего не домотал" ниже), но по бумаге закрывает и
   ru, и es, и en одной моделью. Moonshine — быстрее всех, но БЕЗ русского в
   STT (только в TTS-списке) — не годится как единственное решение для
   двуязычного ru↔es/en переводчика.
3. **Krab Ear / Voice Gateway — НЕ realtime (батч, Telegram голосовые и т.п.):**
   тот же список, что для архива — large-v3 или Parakeet, приоритет точности.
4. **Перевод (сейчас Gemini):** по независимому замеру WMT25 (человеческая
   оценка) Gemini 2.5 Pro выиграл 14 из 16 языковых пар — это реально
   топ-модель для перевода на сегодня, не просто "облако по умолчанию".
   Заменять её локальной моделью (SeamlessM4T v2) — это сделка "чуть хуже
   качеством, зато локально/быстрее/бесплатно", не апгрейд качества. Ты сам
   предложил держать Gemini как фоллбэк на случай сбоя локальной — это,
   по-моему, правильная архитектура: пробовать локально первым, падать в
   Gemini только при ошибке/низкой уверенности, а не наоборот.

**Обновление (второй заход, тот же день):** доделал изоляцию по venv
(каждый пакет — в своём), нашёл точный API `qwen3-asr-mlx` (языковая карта
подтверждена — 68 языков, включая `ru`/`es`/`en`) и починил `.m4a`→WAV для
Voxtral. Оба реально запустились, но оба упали на БАГАХ САМИХ ПАКЕТОВ (не
окружения):

- **mlx-voxtral**: `model.generate(inputs, ...)` падает с
  `ValueError: Cannot index mlx array using the given type` внутри
  `_merge_input_embeddings` — похоже на несовместимость квантованного чекпоинта
  `mzbac/voxtral-mini-3b-4bit-mixed` с установленной версией `mlx`/`mlx-lm`.
- **qwen3-asr-mlx**: `Qwen3ASR.from_pretrained("aufklarer/Qwen3-ASR-0.6B-MLX-4bit")`
  падает при загрузке весов — `Missing 96 parameters` (не хватает слоёв 18-23
  энкодера целиком). Похоже, у этого конкретного 4-битного чекпоинта на HF
  либо битый/неполный аплоад, либо рассинхрон версий между чекпоинтом и кодом
  пакета.

На этом остановился — не потому что не пробовал, а потому что своп упал до
**564МБ свободных из 25.6ГБ** (проверял `sysctl vm.swapusage` до и после).
Это ровно тот сценарий, о котором ты предупреждал весь этот разговор — решил,
что дальше жать рискованно, убил тестовые процессы, дал memory отдохнуть.
`summary.py` не пострадал, прогресс не потерян.

**Что это значит для следующего захода:** Parakeet-MLX — единственный из
новых кандидатов, который заработал СРАЗУ и без танцев. Voxtral и Qwen3-ASR
теоретически сильные (по языкам и WER), но конкретные протестированные
чекпоинты/пакеты имеют баги — стоит попробовать (а) другую версию
`mlx`/`mlx-lm`/`transformers`, (б) официальный неквантованный чекпоинт
(`mlx-community/Qwen3-ASR-1.7B-bf16` вместо стороннего 4bit), или (в) другой
MLX-порт Voxtral, если появится. Не факт, что сама модель плохая — просто
конкретная обёртка на сегодня сырая.

## B. Krab Ear / Voice Gateway — REALTIME (живой переводчик звонков)

Текущая архитектура (нашёл через read-only разведку по проекту, ничего не
менял): Twilio PSTN + iOS CallKit → **KrabEar STT** (mlx-whisper large-v3/turbo)
→ **перевод через Gemini** (облако) → **TTS дыра** (Piper мёртв, чинится через
KrabEar Silero/Kokoro — уже есть готовая спека `VOICE_GATEWAY_TTS_WIRING_SPEC.md`
в проекте, план описан, просто не реализован).

**Важная честная поправка:** ни Parakeet, ни Moshi в проекте реально НЕ
установлены и не используются — единственное упоминание Moshi было как
незаполненная заглушка (`moshi_engine.py`, "но не реализованы") для будущего
streaming TTS, не для распознавания. Так что "не тестировали ещё" — это,
похоже, было про идею, а не про уже вставленный код.

есть MLX-порт), и параллельно посмотреть SeamlessM4T v2 как локальную замену
Gemini для перевода. Moonshine и Kyutai Moshi — красивые по задержке, но
языково не закрывают твою реальную задачу целиком, разве что как ускоритель
для одной конкретной языковой пары.

## C. Krab Ear / Voice Gateway — НЕ realtime (батч: голосовые в Telegram и т.п.)

Тут ограничение по задержке не критично — значит действуют те же кандидаты,
что и для архива (раздел A): large-v3, Parakeet-MLX, возможно Qwen3-ASR-1.7B
(более точная версия, чем 0.6B). Учитывая, что KrabEar УЖЕ гоняет large-v3/turbo
— может быть проще всего просто добавить Parakeet как второй бэкенд для
сравнения качества на реальных голосовых сообщениях, благо векторно это тот же
паттерн, что уже есть в `perceptor.py` (fallback между бэкендами).

## D. Железо

**MacBook M4 Max, 36ГБ unified memory** — хватает с запасом на все модели из
списка выше вплоть до ~7B в 4-битном кванте (столько же, сколько уже жуёт
Qwen2.5-7B в rewrite.py). Даже Canary-Qwen-2.5B (при том что он английский-only
и потому не приоритет) официально подтверждён как "works well... no GPU VRAM
limits" на M4 Max.

**Windows-ноутбук, RTX 4070 mobile 8ГБ VRAM** — заметно теснее. Что стоит иметь
в виду на будущее, если решишь распределять нагрузку между машинами:
- Официальные NVIDIA-модели (Parakeet, Canary) на этом железе получают
  РОДНОЕ ускорение через NeMo/CUDA/TensorRT — то, чего на Mac нет в принципе
  (там всё идёт через community MLX-порты, не от самого NVIDIA).
- `faster-whisper` (CTranslate2, CUDA-бэкенд) — единственный по-настоящему
  зрелый, проверенный годами вариант под эту видеокарту, но 8ГБ VRAM — жёсткий
  потолок: large-v3 в fp16 не влезет, нужен int8-квант.
- Canary-Qwen-2.5B в Q4_K_M кванте (~2ГБ) — с запасом влезет, но это
  английский-only, так что для твоей задачи (ru/es приоритет) он не главный
  кандидат в принципе, независимо от железа.
- Это раздел "на будущее" — не проверял живьём ни одну модель на этой машине
  (у меня к ней сейчас нет доступа из этой сессии), просто фиксирую
  теоретические ограничения, чтобы не открывать заново при следующем заходе.

## D2. Облачные варианты (для сравнения — приоритет всё равно локальным)

Ты просил поискать и облачные варианты тоже — держать в уме на случай, если
локальное решение окажется несравнимо хуже. Вот что нашёл по трём категориям:

**Перевод:**
- **Gemini 2.5 Pro** — уже используется, и по WMT25 (человеческая оценка,
  независимый замер) реально лучшая модель для перевода на сегодня, топ по
  14 из 16 языковых пар. Держать как есть/фоллбэк — разумно.
- GPT-4.1, Claude 4, Cohere CommandA — близкие конкуренты, но не настолько
  лучше Gemini, чтобы имело смысл переключаться ради качества.
- DeepL — специализированный переводчик, сильно проигрывает фронтир-LLM по
  человеческой оценке на живой разговорной речи (хотя формально близок по
  BLEU) — не кандидат на замену Gemini.

**Облачный STT (для сравнения с локальными кандидатами из раздела B/A):**
- **Deepgram Nova-3** — 5.26% WER батч / 6.84% streaming, $0.0043/мин батч,
  $0.0077/мин streaming — один из самых точных и дешёвых вариантов, если
  вообще понадобится облако.
- **ElevenLabs Scribe v2 Realtime** — задержка <150мс, 93.5% точность на 30
  языках — самый быстрый облачный realtime-вариант, конкурент по задержке
  локальным Qwen3-ASR/Moonshine.
- **OpenAI gpt-4o-transcribe** — ~8.9% WER, $6/1000 мин — заметно менее точен,
  чем Deepgram/Canary, не выделяется ничем особенным для наших языков.
- **AssemblyAI Universal-2** — ~14.5% WER на сложных смешанных датасетах —
  слабее остальных в этом списке, не приоритет.

**Реалтайм "всё в одном" (STT+перевод+TTS одним API, для контраста с
собранным вручную локальным пайплайном):**
- **OpenAI Realtime API** и **Gemini Live API** — оба поддерживают
  многоязычный голосовой диалог "из коробки", но ни один явно не
  специализирован под "перевод в реальном времени внутри чужого разговора"
  (это больше voice-agent API, чем call-interpreter). Точных цифр задержки
  под конкретно перевод не нашёл — нужно тестировать вживую, если дойдёт до
  сравнения с локальным пайплайном.

**Мой вывод по облаку:** ни один из облачных STT/перевод вариантов не
настолько лучше локальных кандидатов (особенно Parakeet и, когда починится,
Qwen3-ASR), чтобы это оправдывало отказ от локальности — разница в WER
единицы процентов, а не разы. Раз приоритет локально (как ты и сказал) —
облако держим строго как фоллбэк-сеть, а не как основной путь. Единственное
исключение — перевод через Gemini, там реальный, измеримый разрыв в качестве
в пользу облака, так что твоя идея "локально + Gemini фоллбэк" для перевода
конкретно оправдана данными, не просто осторожностью.
